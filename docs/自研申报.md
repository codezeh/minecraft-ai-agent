## 申报 01 · 2026-10-24 · L2 编排层（plan / runSteps）

- **要解决的问题**
  复合技能里"决定下一步做什么"和"执行这一步"糊在一起。`task_collect.js` 707 行、3 条挖掘路径、4 处 `collectDrops`，就是这个病的症状。后果：报错只能定位到"整个采集失败"，无法回答"第几步、哪个原子、什么码"。

- **已检索的候选**

  | # | 候选 | 结论 |
  |---|---|---|
  | 1 | 项目内已有执行器 | **无**。`grep -rn "runSteps\|stepIndex\|taskQueue\|sequence" src/agent/` = 0 命中 |
  | 2 | `behavior3js`（行为树） | 不选。为长周期 AI 设计，状态与 tick 概念重；我们的需求是"一次性步骤序列 + 每步读世界校验"，抽象不匹配，还得引入新 DSL |
  | 3 | `xstate`（状态机） | 不选。适合有生命周期、需要持久化的状态；一次采集是短生命周期线性序列，状态机是降维打击 |
  | 4 | `bull` / 进程外队列 | 不选。单 bot、单进程、几十步，用不上外部队列与重试基础设施 |
  | 5 | 直接抄 `mineflayer-collectblock` 的 `Targets` | 不选。它是"目标集合 + 逐个消费"，没有"每步前置断言/后置校验/降级动作"，正是我们要补的东西 |

- **为什么都不够**
  需要的抽象只有三件事：**纯函数产出步骤序列**、**逐条执行并在每步读世界校验**、**失败返回步骤号**。上面每个候选都比这个重，且没有一个和我们的 `atom_contract` 信封对齐。引入它们要付"学新抽象 + 写适配层"两份成本。

- **拟自研范围**
  - 一个文件（`src/agent/library/step_runner.js`），约 60~90 行
  - 无新依赖
  - 不改任何现有出口；`task_*.js` 通过它跑，行为不变
  - 契约见规划 §5.3（`steps[]` / `{ok, code, data:{doneSteps, failedStep}}`）

- **回收条件**
  若将来出现多 bot 并发、或需要跨进程持久化任务队列，则改引入现成方案，本模块废弃。

- **结论：已批准**（2026-10-24，用户在 P0 授权时选择「批准自研 step_runner」）

## 申报 08 · 2026-10-24 · atom_locate.js（定位：她/玩家/实体/方块在哪）

- **要解决的问题**
  全库有 **196 处**直接读 `bot.entity.position` / `bot.players[name].entity.position`，各写各的判空。
  典型后果：「玩家在 48 格外」这件事在 5 个地方被处理成 5 种样子——有的报"看不见"、有的崩、
  有的静默返回 null。而"看不见"和"不在线"是两回事，现在混在一起。

- **已检索的候选**

  | # | 候选 | 结论 |
  |---|---|---|
  | 1 | `atom_perceive.playerPos()`（已有） | 不够。只查 `bot.players[name].entity`，返回 null 就结束，无距离、无最后已知位置、无维度判断 |
  | 2 | **`task_follow.js` 的 `PlayerTracker` + `resolveTarget`（已有）** | **采用并上提**。它已把「可见 / 只剩记忆 / 离线 / 完全没线索」四态分开，只是埋在跟随逻辑里，别的模块用不到 |
  | 3 | `mineflayer` 的 `bot.players` / `bot.entities` | **采用**，作为数据源 |
  | 4 | 走地图（`chunk_map`）推算玩家位置 | 不选。地图是离线快照，不适合"人现在在哪" |

- **为什么都不够 / 怎么复用**
  **不重写逻辑**：`PlayerTracker` / 四态判定直接上提到原子层，`task_follow` 改为调用原子。
  新增只有四件它现在缺的：
  1. 统一返回信封（`ok/fail` + 错误码），而不是内部 `{kind:...}` 裸对象
  2. 距离字段（`distFeetToEntity` / `distEyeToBlock`）
  3. 支持实体、方块（最近的一个），不只玩家
  4. **RCON 数据源**（见下，这是关键补充）

- **改名与范围调整**（2026-10-24，用户拍板）
  原定名 `atom_locate`（定位），改为 **`atom_query`（查询信息）**。
  理由：它返回的不只是坐标，还有在不在线、可不可见、距离、信息年龄、维度。
  叫"定位"会让人以为只给一个点，进而又在调用点自己补状态判断——那正是要消灭的重复。

- **RCON 接入**（2026-10-24 用户质疑后核实）
  用户质疑："怎么会超出跟踪范围？F3 不是什么都能读到吗"。核实结果：
  - **F3 显示的是自己的坐标**，不显示他人位置
  - **客户端协议确实拿不到**：玩家超出跟踪范围（约 48 格）后服务端发 `entity_destroy`，
    `bot.players[name].entity` 变 null（`mineflayer/lib/plugins/entities.js:288-297`）
  - **但服务端始终知道**：实测把玩家 `tp` 到 500,500（bot 在 -8,-4），
    `data get entity <name> Pos` 仍返回 `[500.5d, -59.0d, 500.5d]`

  所以 `atom_query` 采用**两级数据源**：RCON 优先（任意距离精确），客户端兜底（48 格内）。
  返回里带 `source: 'rcon' | 'client' | 'memory' | 'none'`，让上层知道数据可信度。

- **拟自研范围**
  - `atom_query.js`：约 280 行
  - `rcon_client.js`：约 140 行（见申报 09）
  - 无新依赖（用 node 内置 `net`）

- **回收条件**：若 mineflayer 未来提供"最后已知位置"或服务端位置查询的官方 API，
  本模块退化/删除。RCON 客户端若被上游库覆盖，也一并回收。

- **结论：已批准**（2026-10-24，用户"接，原子技能改为：查询信息"）

  2. **攀爬一次只上 1 格**（上一格必须也可爬），但**下降可以一次到底**

- **为什么必须单独一个原子**
  它的失败可以干净归因为 `NOT_CLIMBABLE`（不在藤蔓上）/ `TIMEOUT`（按了但没上去），

- **拟自研范围**：约 240 行，单文件，无新依赖。

  在自建梯子柱（6 格，y=63~68，接地）上实测：

  | 动作 | 结果 |
  |---|---|
  | 向上爬 4 格 | ✅ y 62.00 → 66.21 |
  | 向下到底 | ✅ y 66.21 → 63.00（降 3.21） |

  `OUT_OF_ZONE` / `NO_DATA` / `BLOCKED` / `NO_TOOL` / `TOO_MUCH` / `NO_FLOOR` / `LIQUID_RISK`。

- **顺带解决的老问题**
  "先挖后走"让掉落物正好落在要站的那格，走过去自动捡起 ——
  实测 `ensureScaffold` 挖 6 个方块背包只有 0 个（掉落物在 2~3 格外吸不到）。

- **拟自研范围**：约 280 行，单文件，无新依赖。

- **真机验证（2026-10-29 补做完整爬升链路）**

  自建场景：6 格高实心台地（x=60~68、y=63~68 全石），台上立原木柱（y=69~71），
  她站在台地外侧地面（y=63）。

  ```
  起点 (58, 63.0) → 终点 (63.5, 68.25)
  上升 5.2 格，22 步，挖掉 25 格方块
  tunnel-climb-arrived
  眼到原木 1.11 格 ✅ 够得到
  ```

  这一轮补验证抓出 **4 个真 bug**（都是只有真机能发现）：

  1. **"往上挖"排在候选列表最后**：前面的水平方向全都能成功，永远轮不到它 →
     掘进 20 步、挖 8 个方块，**高度一格没上去**。
     改成按"还差多少高度"动态排序，要爬时先试往上。

  2. **`checkStep` 的地板检查对"往上"用错了位置**：往上挖时它检查目标格下方，
     而台地内部是实心的、那格正是刚挖开的空洞 →
     每步都报 `NO_FLOOR`，20 步 dug=0。
     改成往上挖时检查"她当前站的方块"（起跳支撑）+ 目标格的落脚支撑。

  3. **`tunnelStep` 用 `moveToXZ` 进目标格，而它只管水平**：
     往上挖的台阶它上不去，于是"挖通了但位置不变"→ 判 ok → 无限空转。
     加了垂直处理：水平对齐后按住 jump 等高度到位。

  4. **`ok` 不等于"有进展"**：她能在两个已挖空的格之间来回横跳，
     每步 `dug=0`、位置不变，但 `tunnelStep` 都返回 ok → 一直空转到超时。
     改成按"位置真的变了 或 dug>0"判进展，否则把该方向标记为"已通"换下一个。

  另外确认了一件事：**"原地向上挖"物理上不成立** —— 挖掉头顶跳上去没有落脚点，
  会直接掉回来。真正能爬的只有**斜上挖台阶**（挖斜上方那格，落点下方仍是实心地面）。

- **结论：已批准**（2026-10-29，用户"可以试试在挖之前搞个安全范围…相当于我们的战棋格的精细小范围版"）

## 申报 29 · 2026-10-29 · atom_boat.js（载具：上船 / 开船 / 下船）

- **要解决的问题**
  她造得出船、放得下水，但**上不去**。`bot.mount()` 在 Paper 1.21.8 上被服务端静默忽略。

- **查证过程（GitHub + 实测）**
  找到 [PR #4089](https://github.com/PrismarineJS/mineflayer/pull/4089)（仍 open），它指出
  `bot.mount` 只发**单个 interact**、命中点在**脚底**，而原版客户端发的是
  **`interact_at` + `interact` 一对**。

  按它实测了四种包变体，**全部失败**（服务端静默无反应）：

  | 变体 | 结果 |
  |---|---|
  | 单 `interact` (mouse:0) | ❌ |
  | 单 `interact_at` (mouse:2) | ❌ |
  | `interact_at` + `interact`（PR #4089 原版做法） | ❌ |
  | `bot.mount()` 原生 | ❌ |

  已排除的干扰项：包结构正确（查过 1.21.8 的 `packet_use_entity` schema：
  mouse:2 时 x/y/z 是 f32、hand 是 varint、sneaking 是 bool）、
  没被踢、客户端与服务端位置偏差 **0.00 格**、实体选对（按距离选 2 格内刚召唤的船）。

  **结论：协议包挂载在 1.21.8 上不通，不是我的包写错。**

- **改用可行路径（实测有效）**

  | 步骤 | 做法 | 实测结果 |
  |---|---|---|
  | 上船 | `/ride <玩家> mount <载具>`（服务端命令，**需 op**） | ✅ `bot.vehicle` 有值，服务端回 `set_passengers` |
  | 开船 | `bot.moveVehicle(0, 1)` | ❌ 位移 0.00 |
  | 开船 | **`bot.setControlState('forward', true)`** | ✅ **前进 5.65 格** |

- **已检索的候选**

  | # | 候选 | 结论 |
  |---|---|---|
  | 1 | `use_entity` 各种包变体（含 PR #4089） | 不选。四种全失败，服务端静默忽略 |
  | 2 | `bot.moveVehicle` | 不选。实测位移 0.00 |
  | 3 | `/ride` 命令 + `setControlState` | **采用**。两条都实测有效 |
  | 4 | `followEntity` 跟船（旧绕法） | 保留但降级为兜底：她不在船上，只是跟着船走 |

- **为什么必须单独一个原子**
  失败可干净归因，且每条都对应一个真实的世界状态：
  `NO_VEHICLE` / `RIDE_FAILED` / `NO_PERMISSION` / `NOT_MOUNTED` / `DRIVE_FAILED`。

- **记下的一个测试陷阱**
  `kill @e[type=oak_boat]` 之后**客户端实体列表还留着旧船**。
  早期测试按下标取 `boats[0]`，取到的其实是几次之前遗留的实体，
  命令打过去当然没反应 —— 这个假象让我误判了好几轮。
  所以 `findVehicle()` 强制**按位置+距离筛**，并校验坐标是有限数。

- **真机验证（2026-10-29）—— 抓到一条硬边界**

  对照实验（同一套 `/ride`，逐一改条件）：

  | 载具位置 | 她上船时的状态 | 结果 |
  |---|---|---|
  | 船在**干地** | 站陆地 | ✅ 稳定（服务端持续确认在骑 2.4s+） |
  | 矿车在**铁轨** | 站陆地 | ✅ 稳定 |
  | 船**浮在水面** | 站岸上、脚下实心、`inWater=false` | ❌ **秒弹** |
  | 船**浮在水面** | 泡在水里 `inWater=true` | ❌ **秒弹（29~45ms）** |

  **结论：不是"人在水里"的锅，是"载具浮在水面"时服务端不让她骑。**
  表现：服务端先发 `set_passengers {passengers:[她]}`（挂上），
  紧接着 `set_passengers {passengers:[]}`（卸下），只隔 29~45 毫秒。

  **所以"用船渡水"这条路线在 Paper 1.21.8 上走不通。**
  能用的只有"干地上的载具"。渡水请用 `executor.walkTo` ——
  她能浮在水面走（实测跨湖 0 次失败），比船可靠。

- **顺带修了 mineflayer 一个「客户端以为还在骑」的假象**
  `node_modules/mineflayer/lib/plugins/entities.js` 第 793 行：
  ```js
  if (passengers.includes(bot.entity.id)) {   // 空列表里没有她 → 整块跳过
      if (entityId === -1) { bot.vehicle = null }
  ```
  服务端卸载发的是 `{entityId: 船id, passengers: []}`，**不是 `entityId: -1`**，
  所以 `bot.vehicle` 永远不会被清空 —— "服务端已经把她卸下、客户端还以为在骑"。
  这正是 [PR #4093](https://github.com/PrismarineJS/mineflayer/pull/4093) 要修的（至今未合并）。
  本模块自己装了个 `set_passengers` 监听补上这一步，并提供 `isReallyRiding()`
  作为"服务端视角"的判断，避免再被 `bot.vehicle` 的假象骗。

- **记下的第二个测试陷阱**
  前几轮 `driveTo` 报"位移 7.5 格/5.65 格"看似成功，其实她**根本没在船上**，
  是被 `bot.vehicle` 的假象骗了、把"她在水里漂"当成了"船在开"。
  加上 `isReallyRiding()` 之后才看清：船一步没动。

- **拟自研范围**：约 280 行，单文件，无新依赖。
- **结论：已批准**（2026-10-29，用户"好"——同意把 `/ride` + `setControlState` 包成技能）
