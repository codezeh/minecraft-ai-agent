## 开场必读（只记 5 条）

1. **状态标志不可信，要读世界** —— `onGround` / `lookAt` 返回值 / `isValid` 都可能骗人
2. **外部瞬移（tp / spreadplayers）会破坏客户端状态** —— 坐标变 NaN、onGround 卡死、被踢
3. **测试用例必须自带干净场地** —— 测试服会被几十轮测试打脏，"修一个坏一个"多半是这个
4. **断言写错会掩盖缺陷** —— 「必须返回 A」比「不许谎称 B」更容易写错方向
5. **别在一个任务里追到另一层** —— 修原子时跑去看复合层，会两头都做不完

## 一、状态与真相

### 1.1 只信标志位不够，要读世界

| 案例 | 标志说 | 实际 |
|---|---|---|
| 挖掘 | `bot.entity.onGround = false` | 脚下明明是实心方块；`bot.dig` 因此永不触发 |
| 转向 | `bot.lookAt()` 正常返回 | 目标被挡时**静默不转** |
| 采集 | 挖掉方块返回 ok | 掉落物可能没进背包 |
| 树叶站位 | `standableAt` 说能站 | 叶子消失后摔 4 格被踢（R3-08） |

**对策**：判据优先用"读世界"（方块、角度、背包增量），标志位只作辅助。

### 1.2 报数必须等于背包增量

唯一可信的成功判据是**背包实际增量**，不是返回值、不是实体消失、不是"挖到了"。
本项目的采集从 0/8 修到 9/9，靠的就是这条判据。

### 1.3 `partial` 不是 bug

目标不可达但推进 >3 格时返回 `ok + partial:true` —— 这是 Baritone 的 partial path 设计。
正确的断言是「不许**谎称到达**」，而不是「必须返回 NO_PATH」。

## 二、外部瞬移的连锁伤害（最坑的一类）

### 2.0 最终解法：升级依赖，不是自己打补丁（2026-10-24）
**结论：`mineflayer` 4.33.0 → 4.39.0，一个版本号，业务代码零改动，问题消失。**

| | 4.33 | 4.39 |
|---|---|---|
| tp 20/60 格 | ❌ NaN 永不恢复 | ✅ 正常 |
| 连续 tp 5 次 | ❌ 第一次就崩 | ✅ 全正常 |
| tp 后走路 | ❌ 0.2 格/秒 | ✅ 1.9 格/秒 |
| 主服采集被踢 | 前两轮必踢 | ✅ 3 轮 0 次 |

**教训（本会话最值钱的一条）**：
花了 3 小时在服务端配置（`moved-wrongly-threshold`、`moved-too-quickly-multiplier`）、
位置包节流、`onGround` 判断、自己写物理兜底——**全都没解决**。

真正解决只做了一件事：**查 npm 上有没有新版本**。

**下次的顺序应该是**：
1. 先查依赖有没有新版本（`https://registry.npmjs.org/<pkg>/latest`）
2. 再查上游仓库有没有对应 issue/fix
3. 最后才考虑自己打补丁

自己打补丁的代价：`position_guard` 不但没解决问题，还引入了
"坐标看着正常但物理死了"这种更难查的状态。

### 2.1 一句话结论（历史记录，保留供对照）

**tp 超过约 5 格，客户端物理就算出 NaN，永不自愈。**
之后位置包不合法 → 服务端判 `invalid_player_movement` → 踢人。
用户观感是「她有点卡卡的」。

**服务端没问题，是客户端自己崩了。** 完整证据见 [bugs/BUG-001-tp物理崩溃.md](../bugs/BUG-001-tp物理崩溃.md)。

### 2.2 距离阈值（实测）

| tp 距离 | 结果 |
|---|---|
| 5 格 | ✅ 正常 |
| 20 格 | ❌ NaN |
| 60 格 | ❌ NaN |

自己走路 3 秒走 12.91 格（4.3 格/秒）完全正常 —— **只有被外部瞬移才会崩**。

### 2.3 试过但无效（别再试）

| 方案 | 结果 |
|---|---|
| `moved-wrongly-threshold` 0.0625→0.5 | 仍然被踢 |
| `moved-too-quickly-multiplier` 10→100 | 仍然被踢 |
| 位置包节流合并 | 无关（包稀疏是结果不是原因） |
| 故意设坐标为 NaN | 不踢（服务端不是对 NaN 敏感，而是对突变位移序列敏感） |

### 2.4 一个错误修法（已废弃，教训）

**当初**：每 tick 检查 NaN，用最后的 position 包恢复坐标。

**为什么错**：只拉回坐标，**物理还是死的**。表现为"有坐标但走 5 秒只移动 1.2 格"，
比直接报错更难查，而且半死状态照样被踢。

**现在**：监听官方 `forcedMove` 事件重建物理（速度清零 + 清控制键 + `jumpTicks=0`）。
但**仍未根治** —— `physics.js` 的 `timeAccumulator`/`lastSent` 是闭包变量，外部改不到。

### 2.5 当前做法：不瞬移

- bench：走进森林后**连续跑**，不每轮 tp
- 测试：每个测试只 tp 到**自己区域内**（5 格内安全），或走位过去
- 运维：**tp 超过 5 格后必须重连 bot**（物理已死，无法就地修复）

## 四、契约与命名

| 坑 | 教训 |
|---|---|
| 一个字段名两个意思 | `place` 的 `block` 成功时是"我放的"、失败时是"那里的" → 拆成 `placedBlock`/`occupiedBy` |
| 距离不带参照点 | `dist` 曾有三种含义（眼到方块/脚到点/脚到实体）→ 拆成三个名字 |
| 原子**之间**的调用最易漏 | `useBlock` 给 `openContainer` 传 Vec3，编译期查不出，只有跑测试才暴露 |
| 同一原子不同成功路径字段不一致 | `place` 的 `existed:true` 分支漏了 `support`，上层拿到 `undefined` |
| 读一刀切、写分两步 | `data` 字段改名可以一次全改（错了会静默，必须彻底）；坐标传参 17 处要分两步（改错会立刻报错，但一次全改无法定位） |

## 五、工具与流程

### 5.1 长任务必须脱离当前会话

后台作业会跟着工具调用中断而**被杀掉**。跑服务器/长测试要用：

```
cmd /c start "窗口名" /D "工作目录" cmd /c "命令 > 日志 2>&1"
```

**实测**：用 `Start-Process` 起的服务器，在我这边工具中断时被一起清理了两次。

### 5.2 沙箱限制（本机实测）

| 限制 | 表现 | 绕过 |
|---|---|---|
| node 写文件 | `EPERM`（`src/`、`backups/` 下） | 用文件工具写，或 `node ... --print > 文件` 走 shell 重定向 |
| `execFileSync` 取管道输出 | `spawnSync git EPERM` | 把输出写进临时文件再读 |
| shell 写非 `tmp/` 目录 | `Permission denied` | 用文件工具 |

### 5.3 用 git 恢复代码会带回已删内容

`git show HEAD:file` 恢复时，**之前明确删掉的补丁会一起复活**。
实测：「跳一下捡东西」那段被用户要求删了两次。
**对策**：恢复后立即全文搜一遍已删内容的关键词。

### 5.4 审计机制自己也会坏

裸常量基线原来按 `file:line:value` 比对 —— 改一行注释就报"新增"。
改成按 `file:value` 才稳。**棘轮机制要能容忍正常编辑。**

## 十四、藤蔓攀爬：一个"凭特性表下结论"的连环错误（2026-10-25）

### 现象

用户反馈：丛林里她去砍树，路上碰到树冠垂下的藤蔓，楞一会后**沿着藤蔓爬到树顶**，
跳下来，又碰到藤蔓再爬，循环几次后放弃目标树。

### 我犯的四个错（按严重程度排）

| # | 错误 | 后果 |
|---|---|---|
| 1 | 看到 `prismarine-physics/features.json` 里 `climbUsingJump` 只写到 `"1.21"`、没有 `"1.21.8"`，就断言"库不支持悬空藤蔓攀爬" | **结论完全反了**。1.21.8 通过 majorVersion 匹配生效，实测能爬 6.2 格 |
| 2 | 用 `tp` 到藤蔓格后**立刻**测、拿 `maxY - y0` 当"升高" | 测出 5.2 格假阳性（她其实在掉落），据此又下了错结论 |
| 3 | 在 `climbTo` 里加 `bot.look()` 朝向方块 | 干扰攀爬，从 6.2 格掉到 0.9 格 |
| 4 | 反复改代码试错 5 轮，没先做最小复现 | 最后梯子也坏了，越修越乱 |

### 正确的实测（干净数据）

```
climbing=false（藤蔓当空气）: y -60 → -58.83 → 落回 -60     ← 爬不上去
climbing=true （藤蔓当梯子）: y -60 → -53.80（升 6.2 格）   ← 稳定上升
```

**条件：只按 `jump`**（`climbUsingJump`），不需要贴着方块，也不需要 forward。

### 固化下来的规则

| 规则 | 内容 |
|---|---|
| R3-09 | 藤蔓攀爬：只按 jump 就能沿藤蔓上升，不需要贴方块；碰撞箱 empty 可穿过 |

### 教训（最重要）

**① 特性表缺失 ≠ 不支持。** 必须先跑探针，再下结论。
`features.json` 是按 majorVersion 写的，`1.21.8` 会匹配 `1.21`。

**② 测量方法错了，结论一定错。** 测"能不能爬"必须：
- 先让她落地站稳（等 `onGround`）
- 记录**绝对 y 序列**，不是相对差
- 同时打印方块状态（藤蔓柱是不是真的建成了）

我的多次"爬不上去"都是因为：藤蔓柱没建成（`.......`）、或 tp 后还在掉落。

**③ 三次失败必须停。** 我在 `climbTo` 上改了 5 轮，最后把原本能用的梯子也弄坏了。
现在的做法：**撤掉未稳定的原子，只保留已验证的部分**。

### 最终落地

| 产物 | 状态 |
|---|---|
| `src/sim/vine_physics.js` | ✅ 已验证（7/7）：走路当空气（升 0.00 格）、要爬当梯子（升 6.59 格）、梯子不受影响 |
| `atom_climb.js`（climbTo） | ❌ **已删除**。它想一次做"爬 6 格 + 超时 + 站立判定 + 朝向"，不是最小原子 |

### 关于"原子必须最小"（用户 2026-10-25 定的标准）

用户原话：**「原子技能应该都是最小的技能」**，但随后补充：

> 「还是A吧，其他的过于小了，反而不好维护，基础技能就可以了」

**所以标准不是"越小越好"，而是"最小可用且好维护"**。判断依据：

| 拆法 | 评价 |
|---|---|
| 一个大 `climbTo`（爬N格+超时+站立判定+朝向） | ❌ 太大，职责混杂，失败无法归因 |
| `climbPress()` / `climbRelease()` | ❌ 用户明确否决："过于小了，反而不好维护" |
| **`climbTo(targetY)`：按住爬到指定高度** | ✅ **基础技能，可维护** |

### 为什么藤蔓不能拆成"爬一格"（决定性证据）

实测（`tools/_dbg_climb_hold.mjs`）：

```
按住 jump 6 秒 → 稳定升到 y=-53.80（升 6.2 格），到顶停住
松手           → 2 秒内滑落回地面 y=-60
```

**藤蔓不承重，松手就掉。** 所以"按一下爬一格然后松手"在藤蔓上物理不成立 —— 她会立刻滑回去。

这不是"懒"，是**被游戏机制逼出来的原子边界**：`按` 和 `到哪` 必须绑在同一个动作里。

对照：**梯子能停住**，所以梯子理论上可以拆成"爬一格"；但为了一致性，还是用同一个 `climbTo`。

### 本次事故的最终状态

| 产物 | 状态 |
|---|---|
| `src/sim/vine_physics.js` | ✅ **保留**，7/7 通过（走路当空气升 0.00 格 / 要爬当梯子升 6.59 格 / 梯子不受影响） |
| `atom_climb.js`（climbTo） | ❌ **删除**。逻辑方向对（A方案），但测试环境搭不干净，改了 3 轮越改越乱，按"三次失败就停"撤掉 |
| 全套测试 | ✅ **18/18 全绿** |

**藤蔓攀爬能力仍然可用**：调 `bot.vinePhysics.setClimbing(true)` + 按住 jump，实测能爬 6.2 格。
只是没有独立原子包装 —— 等以后单独做干净的测试环境再补。

### 修复效果的实测对比（证据脚本 `tools/diag_vine_column.mjs`）

在用户给的真实位置（`-233/67/-284`，旁边有 8 格藤蔓柱）做对照：

## 2026-10-28：清理时踩的坑 —— 别只看文件名就删

### 事故
清理临时脚本时，按「`tools/_` 前缀 = 一次性调试脚本」的约定删了 6 个。
其中 `tools/_dbg_climb_hold.mjs` **被 `docs/经验教训.md` 引用为证据脚本**
（记录"按住 jump 能爬、松手就滑落"这个关键发现），删掉后文档里的引用就悬空了。
已从 git 恢复。

### 教训
删除任何脚本前，先做一次引用检查：

```bash
grep -rn "<脚本名>" docs/ src/ tools/ | grep -v "\.git"
```

被 `docs/` 引用的脚本**不能按命名前缀一刀切**。命名约定只说明"谁创建的"，
不说明"还有没有人依赖它"。

## 2026-10-29：真机验证不能省 —— 一次补验证抓出 3 个单元测试的盲区

### 背景
`atom_climb.js`（攀爬梯子/藤蔓）交付时只做过**单元测试**（21 项全过），
真机从来没成功爬上去过 —— 当时测的那根藤蔓是悬空的，实际测的是"爬不上去"。
后来补做真机验证，一次抓出 **3 个真 bug**，全是单元测试碰不到的。

### 三个 bug 与它们为什么躲过了单元测试

| # | Bug | 为什么单元测试发现不了 |
|---|---|---|
| 1 | `waitUntil(predicate, { timeoutMs })` 传成了 `{ timeout }` | 单元测试直接调 `climbUp` 并用假 bot，`waitUntil` 的内部默认值根本走不到；只有真机"等 1.5 秒就不动了"才暴露 |
| 2 | 谓词返回 `false` 被 `waitUntil` 当成"完成" | 假 bot 的 `position.y` 是我手写的常量，**不会变化** → 谓词永远返回同一个值，测不出"false 被当完成" |
| 3 | 下梯子按 `sneak`（实测几乎不动，应该什么都不按） | 假 bot 没有物理引擎，**按键不会产生任何位移**，只能测"调用了哪个 API"，测不出"按了会不会动" |

### 关键认知：假 bot 测的是"逻辑"，测不出"物理"
单元测试的 `fakeBot` 里：
```js
entity: { position: { x: 0, y: 64, z: 0 } }     // 常量，永不变化
```
这意味着所有**依赖状态随时间变化**的代码路径都是盲区：

- 等待类逻辑（`waitUntil` / 轮询 / 超时）→ 测不到
- 物理交互（跳跃、攀爬、下落、液体浮力）→ 测不到
- 服务端行为（tick 延迟、位置包、反作弊）→ 测不到

### 实践结论（以后怎么分工）

| 测试类型 | 能覆盖什么 | 不能覆盖什么 |
|---|---|---|
| 单元测试（假 bot） | 几何判断、参数校验、错误码分支、纯函数 | 等待/超时、物理引擎、服务端交互 |
| **真机测试** | 以上全部 + 状态随时间变化的一切 | 边界条件覆盖度低（跑一次要几十秒） |

**所以：凡是"等一个状态变化"或"按键产生物理位移"的能力，必须有真机验证。**
这类能力包括：攀爬、跳跃、挖方块、放置方块、游泳、开关门、捡掉落物。

### 顺带记住的三个具体坑

1. **`waitUntil` 的谓词必须返回 `undefined` 表示"继续等"**，不要返回 `false`。
   判据是 `value !== undefined && value !== null` 就算完成。
   正确写法：`() => cond ? true : undefined`
   （`atom_drops` / `atom_wait_item` 都是这么写的，`atom_climb` 当时是唯一的例外）

2. **`waitUntil` 的选项名是 `timeoutMs`，不是 `timeout`**。传错了会静默用默认 1500ms。

3. **下梯子什么都不按最快**（实测 Δ-2.93/4s），`sneak` 几乎不动（Δ-0.83/4s）。
   上梯子按住 `jump`（Δ+5.2/10s）。

### 数据留档（同一根 6 格梯子，各 4 秒）
| 方式 | 高度变化 |
|---|---|
| 什么都不按 | **Δ-2.93**（自然下滑，最有效） |
| `back` | Δ-2.29 |
| `sneak` | Δ-0.83（几乎不动） |

修完后：向上 4 格 `y 62.00 → 66.21` ✅，向下到底 `y 66.21 → 63.00` ✅。

## 2026-10-29：潜水与骑乘 —— 查 GitHub 后的实测结论

### 一、潜水：不是协议问题，是我自己的等待时间写错了

**GitHub 上没有可用方案**：mineflayer 关于水的 issue 全是 2017~2023 的旧问题且都已关闭
（#814 讲浮上去防溺水、#2423 是进水包崩、#2999/#788 是水推人、#2426/#2057 问怎么用水移动）。
没有一个给出"怎么让她下潜"的做法。

**实测（15 格深水池，逐秒采样）：**
```
起点 y=65.70
2s → 64.73 / 4s → 63.70 / 6s → 62.70
8s → 61.70 / 10s → 60.68 / 12s → 59.70
```
**稳定 1 格/秒，持续 12 秒没有停。**

而且四种方式速度**完全一样**：什么都不按 / sneak / 看向下+前进 / sneak+看向下+前进。
说明**水中下沉是默认重力，不需要按任何键** ——
查 `prismarine-physics/index.js` 证实：水中分支（第 472~495 行）
没有任何对 sneak 的特殊处理，只有**梯子**分支才有 `sneak ? 0 : -ladderMaxSpeed`。

**所以之前记的"执行层没有潜水能力"是错的。她能潜，只是慢（1 格/秒）。**

真正的 bug：`executor.js` 里水下等待**写死 6000ms**。
速度 1 格/秒 → 高差超过 6 格就永远沉不到 → 每轮 break →
报 `HEIGHT_MISS 该降到 y=58，实际停在 y=62`。
修：按实际高差算 `needDrop * 1000 + 2500`，上限 30 秒。

**教训：把"测了一次没成功"当成"能力不存在"是错的。**
先测清物理事实（多长的窗口、多快的速率），再判断是能力缺失还是参数不对。

### 二、骑乘：上不去是服务端不认包，但 /ride + setControlState 能走

**GitHub 上找到了确切根因**：[PR #4089](https://github.com/PrismarineJS/mineflayer/pull/4089)（仍 open，2026-10-27 更新）
> `bot.mount` 以前只发**单个 `interact`**，命中点固定在**实体脚底**。
> 原版客户端发的是 **`interact_at` + `interact` 一对**。

**我按这个补丁实测了四种变体，全部失败：**

| 方式 | 结果 |
|---|---|
| 单 `interact` (mouse:0) | ❌ 服务端无反应 |
| 单 `interact_at` (mouse:2) | ❌ 服务端无反应 |
| `interact_at` + `interact`（PR #4089 原版做法） | ❌ 服务端无反应 |
| `bot.mount()` 原生 | ❌ 服务端无反应 |

已排除的干扰项：
- 包结构正确（查过 1.21.8 的 `packet_use_entity` schema：mouse:2 时 x/y/z 是 f32，hand 是 varint，sneaking 是 bool）
- 不是被踢（这次一个 kicked 都没有）
- 不是距离（客户端与服务端位置偏差 **0.00 格**）
- 不是选错实体（按距离选中 2 格内、刚召唤的那条船）

**注意一个测试陷阱**：`kill @e[type=oak_boat]` 之后，**客户端实体列表还留着旧船**。
早期测试我取 `boats[0]`，实际是几条之前测试遗留的**已死实体**，
`use_entity` 打过去当然没反应 —— 这曾让我误判了好几次。选目标必须按位置+距离，不能按下标。

**但它确实能骑——换一条路：**

| 步骤 | 做法 | 结果 |
|---|---|---|
| 上船 | `/ride <玩家> mount <载具>`（服务端命令，需 op） | ✅ `bot.vehicle` 有值，服务端回 `set_passengers` |
| 开船 | `bot.moveVehicle(0, 1)` | ❌ 位移 0.00 |
| 开船 | **`bot.setControlState('forward', true)`** | ✅ **前进 5.65 格** |

**结论：**
- 靠 `use_entity` 挂载在 Paper 1.21.8 上不通（不是我的包写错，是服务端不认）
- 但 `/ride` 能上船、`setControlState` 能开船 —— **在自己有 op 的服务器上，船是可以用的**
- `moveVehicle` 不可用（这就是原先 PR #4063 那条线）

**教训：一个"协议层不支持"的结论要先穷尽替代路径再下。**
"挂不上"和"开不了"是两个独立问题，我原先把它们捆在一起判死了。
