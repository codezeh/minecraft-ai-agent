## 0. 四条不可谈判的约束（你定的）

| # | 约束 | 落到代码上的含义 |
|---|---|---|
| C1 | **规则以《我的世界》的真实规则为准，不许拿想象当规则** | 每条游戏规则必须有出处（注册表 / 源码 / 探针实测）。没有出处的规则，代码里不允许出现；必须写成待验证项 |
| C2 | **要有标准流程改良项目** | 改任何东西都走同一套八步闭环，每步有产物、有门禁。没有基线的改动不算改进 |
| C3 | **原子化技能 → 复合型技能，字段统一、可分段执行** | 三层架构 + 统一信封 + 复合技能先产出可检查的步骤序列再执行，报错能定位到「第几步」 |
| C4 | **不重复造轮子；要自创必须先通知你、一起商量** | 动手前先做复用审查；确实要自研的，写申报单等你点头，否则不许写 |

四条互锁：**C1 决定事实，C4 决定零件从哪来，C2 决定节奏，C3 决定形状。**

## 1. 现状证据（为什么必须换方法）

不是"代码丑"，是**同一个错误在重复发生**，而且现有流程拦不住。

| 现象 | 证据 | 根因 |
|---|---|---|
| 采集慢且不稳 | `tmp/dct4.log`：11 次选树 → 7 次失败（`TIMEOUT`/`OUT_OF_REACH`/`NO_PATH`，每次 8 秒）→ 只有 4 次挖成功，90 秒拿 3 个。`dct3.log`：`KICKED` + 报数 1 | 瓶颈在**站位/寻路**，不在挖掘循环 |
| 换官方插件也不行 | `official2.log` PASS(6格/30s)、`official3.log` FAIL(1格/9s/Timeout)、`hybrid2/3.log` **0/6** | `CollectBlock.js:30` 用 `GoalLookAtBlock` **未传 reach**（默认 4.5）+ 要求射线命中，正是我们自己花三次调参绕开的限制 |
| 反复"修好了又坏" | 交接文档 §7.1 自述：24 小时改 12 次、8 个 bug；凭空想象"树会塌"写了 `tree_strategy.js` | 没有规则基线 → 猜；没有验收器 → 猜完也不知道对错 |
| 同一能力多套实现 | `collect` 707 行（文档写 678，实际 707）里有 **3 条挖掘路径**、4 处 `collectDrops` 调用；交接文档 §4.2 列了 7 组重复 | 没有分层约束，也没有复用纪律 |
| 判据无法自动判定 | `test_real_terrain.mjs` 只跑**一次** S2；`baseline_s2.mjs` 是测试服超平坦自造树 | "主服 10 次成 8 次"这个唯一标准没有 runner |

**结论**：C2 的本质不是"写文档"，而是**把"查—改—测—记账"变成不可跳过的流水线**。

## 2. 支柱一：规则基线（C1）

### 2.1 规则来源分三级，权重不同

| 级别 | 来源 | 用法 | 例子 |
|---|---|---|---|
| **R1 注册表** | `bot.registry` / `minecraft-data` 1.21.8（运行时派生，不写死） | 可直接用于决策 | `oak_log.harvestTools` = **undefined**（任何工具都能挖）；`stone.harvestTools` = 877,882,887,892,897,902（六种镐）；`oak_leaves.states.distance` = 1..7；`player` 宽 0.6 / 高 1.8 |
| **R2 库源码** | `node_modules` 里 mineflayer / pathfinder / collectblock / prismarine-physics | 必须引用文件:行号 | `GoalLookAtBlock` 默认 `reach 4.5`（`goals.js:160`），`reach` 可传；`collectAll` 未传 reach（`CollectBlock.js:30`） |
| **R3 探针实测** | 主服/测试服上跑的脚本，结果落盘 | 唯一可以推翻 R1/R2 结论的级别 | 服务端基本不校验交互距离（6.11 格能挖）；挖方块不需要视线；掉落物拾取半径 |

**关键区分（已实测）**：`eyeHeight = 1.62` **不在 registry 里**，来自 mineflayer 运行时。所以"眼高"是 R2/R3，不是 R1。把它写成 R1 就是想象的开始。

### 2.2 规则表的形状

`rules/game_rules.json`（新建）：

```json
{
  "id": "R3-07",
  "claim": "挖方块的限制是 pathfinder GoalLookAtBlock（4.5 + 射线），不是 dig()",
  "source": "R3",
  "ref": "tools/test_reach_boundary.mjs + goals.js:148-205",
  "mc_version": "1.21.8",
  "verified_at": "2026-10-23",
  "evidence": "tmp/reach.log",
  "usable_in": ["digBlock", "planRoute"]
}
```

同时生成 `rules.runtime.js`：把能从 registry 算的规则做成 getter（`harvestToolsOf(name)`、`isGravityBlock(name)`、`leavesDecayRange()`），**代码里不许再写字面量 5.1 / 1.62 / 4.317**。

### 2.3 把"不许想象"变成机器检查

`tools/preflight.mjs` 增加第 3 层 `rules_audit`：

1. 扫描 `src/agent/library/**`，命中已知游戏常量表（`0.6, 1.8, 1.62, 1.25, 4.317, 5.612, 4.5, 5.1, 0.2, 13, 15` 等）的每一处，**必须**在同一行或上一行带 `// rule:Rx-xx` 注释；
2. 没注释 → `FAIL: 裸常量 <value> @ file:line`；
3. 注释指向的 id 必须真实存在于 `game_rules.json`，否则 fail。

**效果**：以后谁（包括我）想写"树会塌所以要从上砍"，先得在规则表里立一条 R3 探针记录，跑不过就写不进去。

## 3. 支柱二：标准流程（C2）

### 3.1 八步闭环

| 步 | 做什么 | 产物 | 门禁（不过不许进下一步） |
|---|---|---|---|
| **0** | **复用审查**（见 §4.1） | 申报单一条结论：复用 / 已申报 / 不需要 | 候选检索记录在案；要自研的已获你批准 |
| 1 | **立规则** | `game_rules.json` 新增/修订条目 | 来源级别 + 出处可查；R3 必须能复跑 |
| 2 | **立基线** | `tmp/bench/<日期>-<场景>.jsonl` + 一行汇总 | 至少 10 轮：pass、报数 vs 背包差、耗时、失败码直方图 |
| 3 | **定契约** | 该 skill 的 `plan()` 输出样例（步骤序列）+ 字段清单 | 字段全部来自 §5.2 字典；新增字段要改字典并说明 |
| 4 | **改原子/复合** | 代码 | 只动这一层；跨层改动必须拆成两个任务 |
| 5 | **分段验证** | `tmp/bench/<日期>-<场景>-seg.jsonl` | 每个 atom 单独可跑；每个 step 有独立结论 |
| 6 | **整体验收** | 主服真机 N 轮 | 场景判据（S0–S3）达标，且**报数 = 背包实际增量** |
| 7 | **记账** | 更新 `验收记录.md` + `交接文档.md` | 数字、日期、提交号；结论与第 2 步基线对比 |

**第 2 步和第 6 步必须是同一脚本、同一锚点、同一判据**，否则不算对比。

### 3.2 明令禁止（来自 §7.1 的教训）

- 没有基线数字就动手改（"我觉得会更快"）
- 一次改两层（原子和复合一起改）
- 测试服通过就当主服通过
- 改完不跑 `preflight.mjs`
- 失败就调参不读源码（交互距离改三次那次）
- **没走复用审查就新建模块**（C4）
- 在同一文件里打补丁超过 2 轮 → 停下回到第 3 步重新定契约

### 3.3 任务粒度

一个改动 = 一个可单独验收的单元。判断标准：**能不能独立回答"改之前 X，改之后 Y"**。不能，说明粒度过大。

## 4. 支柱三：复用优先（C4）

### 4.1 判定顺序（先左后右，能停就停）

1. **项目里已有且够用** → 直接用，不改
2. **项目里已有但不够用** → 先改它，不新建
3. **npm 生态/官方插件有** → 用；只借零件就只借零件
4. **都没有，或多个候选都不合** → **写自研申报单，等你点头**
5. 你点头后 → 自研，并写清"以后什么条件可以回收"

判定只看一个问题：**这个能力由谁负责最省总成本**（包括以后维护、调试、教给模型）。"我写得更顺手"不算理由。

### 4.2 本项目的复用清单（已核对，不是估计）

| 能力 | 项目内已有 | 生态已有 | 现状 | 结论 |
|---|---|---|---|---|
| 走/寻路 | `atom_move`（1.21.8 实测）、`heatmap`、`task_hop`+`path_long`+`path_short` | pathfinder、`skills.planRoute` | **三套并存** | 短期用 `atom_move`；另两套 P3 收敛，不新增第四套 |
| 站到能挖位置 | `findStandSpot`（手写） | `GoalLookAtBlock`（可传 reach） | 自研 | **复用**，`reach` 从规则表取 |
| 整棵树/矿脉洪泛 | 无（`collect_planner` 按列聚类，2×2 枝干会漏） | `findFromVein` | 自研且更差 | **复用**，但必须限 `maxDistance`（`official2` 里 200 格把整片林都吞了） |
| 掉落物拾取 | `collectDrops`（轮询，实测漏约 1/3） | `itemDrop` 事件 | 自研且更差 | **复用事件** |
| 背包满存箱 | 无 | `emptyInventoryIfFull` | 缺 | **复用** |
| 自动换工具 | `tool_prep.ensureAxe` | `bot.tool.equipForBlock({getFromChest:true})` | 自研 | **复用**；造工具链路保留 `skills.craftRecipe` |
| 铺平台 | `task_platform` | `skills.fillAreaSafely` | 重复 | P2 二选一，不并存 |
| 建筑/蓝图 | `schematic.js` | `skills.buildFromSchematic` + mineflayer-schem | 重复 | **复用** |
| 交易/村民/门/床/熔炉 | 部分 | `skills.tradeWithVillager`、`useDoor`、`loadFurnace`… | 已有 | **复用**，不重写 |
| 区块地图/地形 | `chunk_map`（271）、`mca_import`（175） | 无 | 自研 | **保留自研**（§4.3 已申报理由：生态无等价物） |
| 垫脚方块清理 | `scaffold_cleanup` | 无 | 自研 | **保留自研**（官方插件不拆垫脚） |
| **L2 编排层**（plan/runSteps） | **无**（已 grep：无 `runSteps`/队列/步骤执行器） | behavior3js、xstate、bull | 无 | **待申报**（见 §4.3） |

### 4.3 自研申报单

新建 `自研申报.md`（与交接文档并列，因为它是流程的一部分）。每条一页，格式固定：

```md
## 2026-10-24 · L2 编排层（plan/runSteps）
- 要解决的问题：复合技能里"决策"和"执行"糊在一起，报错只能定位到整个技能
- 已检索的候选：
  1. 项目内 —— 无（grep runSteps/taskQueue/sequence = 0 命中）
  2. behavior3js —— 行为树，状态与日志形态与我们的信封不匹配，且要学新 DSL
  3. xstate —— 状态机，适合长生命周期状态，不适合"一次性步骤序列+逐步校验"
  4. bull/队列 —— 进程外队列，单 bot 进程内用不上
- 为什么都不够：需要的是"纯函数产序列 + 逐条执行 + 每步读世界校验"，上面三者的抽象都比这个重
- 自研范围：约 60~90 行，单个文件，无新依赖
- 回收条件：若后续出现多个 bot / 需要持久化任务队列，改为引入现成方案
- 结论：**待用户批准**
```

**规则**：`自研申报.md` 里"待用户批准"的条目，不许开始写代码。

### 4.4 机器检查（让 C4 不只是口头）

`preflight.mjs` 增加第 4 层 `new_module_guard`：

- 列出 `src/agent/library/**` 下相对上次提交**新增**的文件；
- 每个新增文件必须在 `自研申报.md` 中有一条 `结论：已批准` 的记录，且文件名匹配；
- 否则 fail，提示"这个模块没有申报记录"。

轻量、不阻塞——但它能保证"顺手又造一个轮子"这种事在提交前被拦下。

## 5. 支柱四：原子 → 复合（C3）

### 5.1 三层，职责不重叠

| 层 | 职责 | 禁止 | 现有对应 |
|---|---|---|---|
| **L1 atom** | 一次尝试；前置断言；后置**读世界**校验；无重试 | 循环、换目标、考虑 deadline | `atom_move / atom_dig / atom_place / atom_perceive / atom_items` |
| **L2 skill** | 只编排 atom：先 `plan()` 出步骤，再 `run()` 逐步执行 | 直接调 `bot.dig` / `bot.pathfinder` / `bot.inventory` | **缺失**（已确认无步骤执行器） |
| **L3 task** | 目标级：deadline、失败降级、黑名单、进度汇报 | 自己实现挖掘/寻路细节 | `task_collect / task_follow / task_platform` |

`task_collect.js` 707 行的问题就是 **L2 不存在**，L1 和 L3 直接糊在一起，所以"改一处忘两处"。

### 5.2 统一信封与字段字典

沿用现有 `atom_contract.js` 的 12 个错误码（`OK/NO_TARGET/NO_PATH/OUT_OF_REACH/NO_TOOL/NO_ITEM/OCCUPIED/NO_SUPPORT/BLOCKED/TIMEOUT/INTERRUPTED/INTERNAL`），**不新增同义词**。`data` 字段收口为白名单：

| 字段 | 类型 | 含义（唯一口径） | 替代掉的 |
|---|---|---|---|
| `pos` | `{x,y,z}` 整数 | 方块/格子坐标 | `at` / `cell` / 裸 `pos` / `Vec3` |
| `dist` | number | **方块中心 → 眼睛** 的直线距离 | `advanced` / 各自算的 dist |
| `count` / `want` | number | 已完成 / 目标数量 | `collected` / `got` / `placed` / `want` |
| `failed` | `[{pos, code, message}]` | 失败明细（每个失败目标一条） | 只有 platform 有的 `failed` |
| `costMs` | number | 该层自身耗时 | 各处口径不一 |
| `step` | number | **复合技能里的步骤序号（1 起）** | 无（新增，用于分段定位） |

字段只能从这张表取；要加字段先改本表并说明理由。`data` 出现表外键 = 契约违反，`contract_audit` 报错。

### 5.3 可分段执行（C3 的核心）

复合技能统一拆成两个纯函数 + 一个执行器：

```js
// 1) 规划：纯函数，无副作用，可单测、可打印、可人工检查
planCollect(bot, {blockNames, want, near}) -> {
  steps: [
    { step: 1, atom: 'moveTo',   args: {target: {...}, tol: 2},
      expect: {at: 'block'},           // 后置断言（读世界）
      onFail: [{code:'NO_PATH', action:'replan'}] },
    { step: 2, atom: 'digBlock', args: {pos: {...}},
      expect: {block: 'air'}, onFail: [{code:'OUT_OF_REACH', action:'restep'}] },
    ...
  ]
}

// 2) 执行：只按序列跑，不重新决策
runSteps(bot, steps) -> {
  ok, code, message,
  data: { count, want, failed: [...], doneSteps: n, failedStep: m }
}
```

**这才是"分段执行"的含义**：先产出一份**能看、能存、能回放**的步骤序列，再逐条执行。

- 报错不再是"collect 失败了"，而是 `step 7 / digBlock / OUT_OF_REACH`
- 单步可重放：拿 `steps[7]` 单独跑，不用复现整场
- 可 diff：两次运行的 steps 序列不同 → 一眼看出决策变了
- 可降级：`onFail` 表就是降级策略，不再散在 `if-else` 里

### 5.4 事件与代价

事件统一 `{phase, step, code, ...}`，`phase ∈ {plan, move, dig, pickup, cleanup, report}`。这样 `dct*.log` 那种时间线可以直接按 phase 聚合出"每层花了多少时间、失败在哪一层"。

### 5.5 机器可检查的 4 条架构约束

写进 `tools/contract_audit.mjs`（扩展），CI 式跑：

1. **分层**：`skill_*.js` / `task_*.js` 里出现 `bot.dig(`、`bot.pathfinder.`、`bot.inventory.` 直接调用 → fail
2. **信封**：所有 `return` 必须经 `ok()/fail()`；裸 `{ok:true}` → fail
3. **字段**：`data` 的键必须在 §5.2 白名单内
4. **规则**：§2.3 的裸常量检查

这 4 条把 C1 和 C3 从"约定"变成"提交前错误"——不通过就提交不了。

## 6. 分期

| 期 | 内容 | 产物 | 门禁 |
|---|---|---|---|
| **P0** 规则+测量基座（1~1.5 天） | §2.4 清账；`game_rules.json`；`rules.*` getter；`preflight` 第 3、4 层；`bench_s2_main.mjs`（主服 10 轮，JSONL） | 规则表 + 基线数字 + 申报单（空表） | 规则表每条有出处；基线 10 轮跑完（有数字，哪怕很差） |
| **P1** collect 样板（2~3 天，**需先批 L2 申报**） | `skill_collect.js`：`planCollect` + `runSteps`；三条挖掘路径合成一个 `digOne`；站位改用 `GoalLookAtBlock`；掉落物改 `itemDrop` | 可打印的步骤序列 + 分段日志 | 主服 ≥8/10、平均 <8 分钟、报数=背包差；`contract_audit` 全绿 |
| **P2** 同模板推广（2~3 天） | `follow`、`platform` 按 P1 模板重写；`task_*.js` 退化为薄壳 | 同结构 | S1、S3 不退化（各自 bench） |
| **P3** 清理与统一（1~2 天） | 删 `tree_strategy.js`、`collect_planner` 的树型分支；`task_hop/path_long/path_short` 在 `task_follow` 迁完后删；字段全量对齐；26 种事件加 phase 前缀 | 更小的库 | 107 PASS 套件全绿 + 各 bench 不退化 |
