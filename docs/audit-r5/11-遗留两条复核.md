## E) 「离线服 uuid 由名字派生，同名者不可区分」——**仍成立，且 R4 表述准确**

### E.1 机制是否已实现：**是**（面板发码 → `!claim` → `identity.json`）

```bash
$ ls mindcraft/src/agent/commands/identity.js mindcraft/src/mindcraft/identity_store.js
mindcraft/src/agent/commands/identity.js
mindcraft/src/mindcraft/identity_store.js

$ grep -n "identityList" mindcraft/src/agent/commands/index.js
5:import { identityList } from './identity.js';
60:const commandList = queryList.concat(actionsList, identityList);
```

`identity_store.js` 自己的设计说明（原文）：

```
 * 现在：面板（已过 token 门）下发**一次性绑定码**；玩家在游戏里 `!claim <码>`；
 * 码核销后写 `bots/<agent>/identity.json`，之后按 **uuid 优先、名字其次** 定级。
 * 名字只在"没启用绑定"（或显式打开兼容回退）时才有意义。
```

### E.2 定级顺序：**uuid 优先、名字其次（且有防回退）**

`resolveBinding`（`identity_store.js:365-381`）原文：

```js
let binding = null;
if (u) binding = s.bindings.find((b) => b.uuid === u) ?? null;
// ★★★ 名字回退**只认"没有 uuid 的绑定"**。
//   否则：主人绑定了 uuid+name，冒名者改个客户端名字叫 Zeh（uuid 不同）就能命中
//   这条 fallback ⇒ 直接拿 owner —— 那等于把本机制要堵的洞又开了一遍。
if (!binding && n) binding = s.bindings.find((b) => !b.uuid && (b.name ?? '') === n) ?? null;
```

⇒ uuid 精确命中优先；名字回退只对"当初没拿到 uuid"的记录生效。这挡住了"异 uuid 同名冒用"（R4 的 ①-g 用例），但**挡不住"同 uuid 同名"**（见 E.5）。

`permissions.js:204 resolveLevel` 的顺序也一致：`internal` → **绑定（1.5 步）** → 空 author → 别的 bot → 未启用绑定才看名单 → 否则 guest。

### E.3 绑定码有效期：**上限 5 分钟，实测被强制压住**

```bash
$ grep -n "DEFAULT_CODE_TTL_MS" mindcraft/src/mindcraft/identity_store.js
39:export const DEFAULT_CODE_TTL_MS = 5 * 60_000;
295:        expiresAt: now + Math.min(Math.max(Number(ttlMs) || 0, 1000), DEFAULT_CODE_TTL_MS),
```

```

MAX_PENDING_CODES      = 8
请求 ttlMs=60 分钟 → 实际有效 = 5 分钟（被压到上限）
```

⇒ 注释说"≤5 分钟"，**实测成立**：即使调用方传 60 分钟也被 `Math.min(…, DEFAULT_CODE_TTL_MS)` 压到 5 分钟。待核销码最多存 8 条。

### E.4 过期 / 撤销 → 降级 guest：**是（fail-closed）**

```
binding 字段 = uuid, name, level, boundAt, expiresAt, sessionId, weak
  值 = {"uuid":"3f680b9f-…","name":"HEAVENZEH","level":"owner","boundAt":1000000,"expiresAt":2593000000,"sessionId":"x","weak":true}
未过期 → level = owner
过期后 → level = null , reason = expired , weak = true
```

`level:null` 落到 `resolveLevel` 的 4) 分支 → **guest（`other`）**，并打印"面板取码 + `!claim`"的引导：

```
[permissions] 身份绑定已启用：没绑定的发言者一律按 guest 处理（只聊天）。
[permissions] 取码：打开面板 → 控制台左侧「玩家身份」区的「生成绑定码」按钮；…
过期/未绑定 → level = other
```

**绑定记录的真实字段名**：`uuid` / `name` / `level` / `boundAt` / `expiresAt` / `sessionId` / `weak`。

### E.5 核心问题：同名者能否区分 —— **不能，实测撞库**

离线模式下服务端怎么发 uuid：

```
$ grep -n "^online-mode" server/server.properties server-test/server.properties
server/server.properties:38:online-mode=false
server-test/server.properties:38:online-mode=false

$ grep -n "nameToMcOfflineUUID" -A2 mindcraft/node_modules/minecraft-protocol/src/datatypes/uuid.js
14:function nameToMcOfflineUUID (name) {
15:  return (new UUID(javaUUID('OfflinePlayer:' + name))).toString()
16-}
```

即 `UUID = v3-md5("OfflinePlayer:" + 名字)`，**只由名字决定**。独立复算与项目函数一致：

```
HEAVENZEH    → 3f680b9f-53a9-34c1-900a-6ba8f0262175
HEAVENZEH    → 3f680b9f-53a9-34c1-900a-6ba8f0262175   （同名 ⇒ 同 uuid）
heavenzeh    → 8ff2dd23-b64b-3b91-9338-acba179d6a07   （大小写不同 ⇒ 不同 uuid ⇒ unbound）
独立复算 HEAVENZEH → 3f680b9f-53a9-34c1-900a-6ba8f0262175   ✅ 一致
```

**冒名推演（实测）**：

```
主人 uuid        = 3f680b9f-53a9-34c1-900a-6ba8f0262175
同名冒名者 uuid  = 3f680b9f-53a9-34c1-900a-6ba8f0262175   同uuid? true
冒名者命中结果   = {"level":"owner","weak":true,"reason":"ok"}
```

⇒ 绑定表**存的是 uuid**（`binding.uuid`），而离线服上同名 ⇒ 同 uuid ⇒ 直接命中主人的那条记录，**`resolveBinding` 判为 owner**。

**代码的应对**：`weak: true` 标记 + 二级策略门（`src/agent/commands/index.js:400-420`）：

```js
if (!hit.weak) return settle(hit);
if (policy.effective === 'persistent') return settle(hit);              // online-mode=true
if (policy.effective === 'session') {
    const fresh = sessionFresh({ uuid, name, windowMs: policy.sessionMinutes * 60_000 });
    if (fresh) return settle(hit);
    return settle({ ...hit, level: null, reason: 'offline-weak-session' });
}
return settle({ ...hit, level: null, reason: 'offline-weak' });         // deny
```

生效策略由 `resolveIdentityPolicy({onlineMode, offlineOwnerMode, sessionMinutes})` 合成，实测：

```
未传参（代码默认）            : effective=session, sessionMinutes=720
onlineMode=false + 未指定 mode : session
onlineMode=false + deny        : deny
onlineMode=true                : persistent（uuid 可信，无视 session 窗口）
```

本机实际配置：`settings.js:56` `"offline_owner_mode": "session"` ⇒ **生效 = session / 720 分钟**。

也就是说：**离线 + 弱绑定 ⇒ 仅在刚 `!claim` 后 720 分钟内授 owner，其余时间 guest。** 这**缩小了暴露窗口**，但**窗口期内冒名者仍拿 owner**（实测 confirmed）。

### E.6 结论：**产品层面无法根治**（不是代码能修完的）

| 问题 | 能否代码修复 | 说明 |
|---|---|---|
| 「同名 ⇒ 同 uuid ⇒ 撞 binding」 | ❌ **不能** | uuid 由服务端按名字派生，客户端无法自证"我是那个 uuid 的那个人"。加"会话挑战"也只能证明"此刻能拿到码"，不能证明"之后进来的还是他"。 |
| 暴露窗口有多大 | ✅ 可调 | `offline_owner_mode=deny` ⇒ 一律只聊天；`session` + 把 `offline_session_minutes` 从 720 调小（如 15）⇒ 窗口更窄。两者都是**配置**，不动代码。 |
| 真正的根治 | ➖ 产品决策 | ① `online-mode=true`（正版验证，uuid 由 Mojang 签发）；② 装登录插件（AuthMe 等）。R4 T13 已经这样写，**没有过时**。 |
| 绑定表若改存名字会怎样 | — | **更糟**：改名即失效、且同名照样撞。当前存 uuid + weak 标记是这套约束下的合理选择。 |

> 唯一的"代码可再改进"空间是**体验与话术**（已做得不错：拒绝时说明原因并给根治路径），**不是安全性**。
