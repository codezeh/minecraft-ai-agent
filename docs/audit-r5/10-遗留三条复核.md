## 2. A — `gracefulStop` 是否仍只是静态确证？

### 2.1 实现顺序：成立（行号已核实）

`src/process/init_agent.js`：

| 步骤 | 行号 | 内容 |
|---|---|---|
| 信号注册 | 116 | `for (const sig of ['SIGINT','SIGTERM'])` → `gracefulStop('signal:'+sig)` |
| ④ 单回共享池 | **105** | `await agent?.board?.update?.(id, { state:'ready', lease_owner:null, lease_until:null, assignee:null })` |
| ④b 放预约 | **109** | `await agent?.board?.release?.(id)` |
| ⑤ 断板连接 | **112** | `agent?.board?.socket?.disconnect?.()` |

`105 < 112` 且 `109 < 112` ⇒ **④⑤ 确实在断连之前**，注释与代码一致。

> ⚠️ 定位陷阱（本轮踩过）：文件 **第 76 行**还有一处 `board?.socket?.disconnect?.()`，那是**孤儿监视器 `onOrphan`** 里的另一条路径。按"第一次出现"取行号会抓到 76，从而得出"顺序不成立（disconnect 在 update 之前）"的**假结论**。探针已改成"在 release 之后找 disconnect"。

### 2.2 有没有真进程级触发？—— 没有

探针扫描 `tools/*.mjs` 中提到 `SIGINT/SIGTERM` 的 8 个文件，逐个判"是否真 spawn 子进程 + 读 init_agent + 断言租约"：

```

[A] control_plane_guard_unit.mjs       realSpawn=n fakeChild=Y 读init_agent=Y 断言租约=Y   ← 正则匹配源码文本
[A] control_zombie_live.mjs            realSpawn=Y fakeChild=n 读init_agent=n 断言租约=n
[A] e2e_server_ctl.mjs                 realSpawn=n fakeChild=n 读init_agent=n 断言租约=n
[A] proc_lifecycle_unit.mjs            realSpawn=n fakeChild=Y 读init_agent=Y 断言租约=n   ← 假 child（EventEmitter）
[A] t51_firstnight_realagent.mjs       realSpawn=Y fakeChild=n 读init_agent=n 断言租约=n
[A] t51_triple_round.mjs               realSpawn=Y fakeChild=n 读init_agent=n 断言租约=n

```

`control_plane_guard_unit.mjs` 的 `断言租约=Y` 是**在源码字符串上正则匹配**（`readFileSync(...init_agent.js)` 后 `/board\?\.socket\?\.disconnect/` 一类），不是运行时断言；
`realSpawn=Y` 的四个 live 脚本都不读 `init_agent.js`、也不断言租约。

### 2.3 真机尝试（本轮新做的实测）

探针真的起了 **真 mindserver**（`createMindServer(false, 65123)`）并 **真 spawn** `node src/process/init_agent.js probeA -n probeA -p <port>`：

```
[A] [场景1 无mindserver] exit= {"early":true,"code":1,"sig":null}  reachedStarting= false  graceful 行= false
[A]   └ 关键输出： 2026-11-08T13:19:14.632Z Connection failed: websocket error
[A] [场景2 真mindserver] exit= {"early":true,"code":1,"sig":null}  reachedStarting= false  graceful 行= false
[A]   └ 关键输出： 2026-11-08T13:19:17.065Z probeA connected to MindServer
```

两件事被**实测**确认：

1. **本会话能 spawn**（`spawnSync` 返回 `child-ok`，exit 0）——"环境不能起进程"在这里不成立，所以"没做"不是借口的空白。
2. 但 `init_agent.js` 在两种离线配置下都**在 `Starting agent` 之前就退出**：
   - 没 mindserver → `Connection failed: websocket error`（exit 1）；
   - 有 mindserver → 连上了，但 `Agent 'probeA' not found.`（exit 1，agent 需由 mindserver 侧 `create-agent` 注册）。
   
   信号处理器（`init_agent.js:116`）在 `new Agent()` **之后**才安装，因此这两条路径上它**根本没装上**，`gracefulStop` 一次都没跑。

### 2.4 A 的结论

**仍成立。** 要真机验证"停手时租约被摘掉、顺序正确"，必须具备：

- 一个**已注册**的 agent（mindserver `create-agent`，或 `main.js` 全量启动）；
- agent 能 `agent.start()` 成功 ⇒ **可连的 Minecraft 服**（禁止项）；
- 之后 scheduler 才会领单，`scheduler.currentJobId` 才非空，④⑤ 才有东西可摘。

缺的是 **可连的 MC 服**（+ 已注册 agent）。这不是"再努一把"能绕过的：没有 MC 服，`Agent.start()` 不返回，调度器不会跑，租约不会存在。⇒ 报告里建议的"起真 agent → 领单 → SIGINT → 断言 `lease_until IS NULL`"**本轮离线做不到**，已在 `RUNBOOK N4` 里挂着的同一个缺口。

**建议（给 captain）**：把 A 的验证放进"允许起真 MC 服"的那条 E2E 车道（`docs/audit-r4/T11-隔离服E2E.md`）。探针 `t-r5-def-A.mjs` 已经准备好场景 2，只要 `reachedStarting=true`，加一句 SIGINT + 板库查询即可闭环。

### 3.2 B — 桥接语义：5 类输入 + 结构化截断

`result.js:246 coerceModelResult` = `assertModelResult` 包装（不合法 ⇒ 降级成 `status=error/errorCode=BAD_RESPONSE`）；
真正做归类的是 `result.js:203 toModelResult`：

| 输入形状 | 桥接结果 |
|---|---|
| `'[LLM_ERROR] boom: 503'` | `status=error, failed=true, truncated=false, content=''` |
| `'正文[LLM_TRUNCATED]'` | `status=truncated, failed=false, truncated=true, content='正文'`（标记被剥掉） |
| `'正文'` | `status=ok`，content 原样 |
| `''` | `status=ok, content=''`（与旧语义一致：空串不是失败） |
| `null` | `status=ok, content=''` |
| `new ModelResult({status:truncated})` | 原样保留（只补 elapsedMs/attempts） |
| `finishReason='length'` | `status=truncated`（★ 结构化提级：原生适配器靠字段，不靠标记） |

`STATUS` 全集 = `ok / truncated / error / cancelled / timeout`（`result.js:27`）；`failed` = `error | cancelled | timeout`。

### 3.4 C — opts 不下传（首次实测）

用**真 Prompter**（真构造函数、真 profile 模板），只把模型层换成记录器，记录"prompter 实际传给模型层几个参数"：

```
[C] promptMemSavingResult  : 模型层收到 2 个实参；第4参 opts = undefined
[C] promptShouldRespondToBot : 模型层收到 2 个实参；第4参 opts = undefined
[C] promptVisionResult        : 模型层收到 3 个实参；第4参 opts = undefined
[C] promptCodingResult(对照)  : 模型层收到 4 个实参；第4参 opts = object   ← 同一条通道在 coding 上是通的
```

**abort 之后是否仍跑满**（记录器实现"看得到 signal 就 abort 后立刻放弃"）：

```
[C] 对照组（有 signal）abort 后 status = cancelled (期望 cancelled)
[C] 记忆摘要（无 signal 通道）abort 之后仍然 status = ok (不是 cancelled ⇒ 跑满)
```

⇒ **C 的后果是可实测的**：这三条路径拿不到 `signal` / `deadline` / `operationId`，
`!stop`、面板停止、动作超时都**拦不住**它们；它们只能等适配器自己的 120s 上限。

**行号更正（R4 表述的一处不精确）**：R4 记的是 `:544 / :587 / :627`，实际是：

| 路径 | 行号 | 实参 |
|---|---|---|
| `promptMemSavingResult` | **544** `chat_model.sendRequest([], prompt)` | 2 |
| `promptShouldRespondToBotResult` | **587** `chat_model.sendRequest([], prompt)` | 2 |
| `promptVisionResult` | **610** `vision_model.sendVisionRequest(messages, prompt, imageBuffer)` | 3 |
| （R4 记的 627）`promptGoalSetting` | **627** `chat_model.sendRequest(user_messages, system_message)` | 2 —— **第 4 处**同类调用点，且是 `// deprecated` 路径 |

即：Vision 在 **610** 而不是 627；627 是**另一处**（`promptGoalSetting`，已废弃）也不传 opts 的调用点。

### 3.5 用户可见后果（三条路径各自）

| 路径 | 拿不到什么 | 什么时候会表现出来 |
