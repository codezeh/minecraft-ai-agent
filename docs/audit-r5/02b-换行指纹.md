| # | 结论 | 判定 |
|---|---|---|
| D-17a | **源码指纹对换行敏感**：同一份语义完全相同的源码，CRLF 版 `8a1714aa…` vs LF 版 `82405964…` | **CONFIRMED（实测）** |

1. **产物那 3 项自检（逐文件一致 / 无野文件 / 入口引用）两次都是 PASS** —— 说明产物确实"没问题"；
2. **唯一的变量是源码换行**；

## 8. 判定、前置条件与修复方向

**判定：CONFIRMED（实测），前置条件如下。**

- **触发条件**：两台机器的行尾归一化不同。具体是 `core.autocrlf=true`（Windows 默认安装）产出 CRLF，而 Linux / docker / CI / `autocrlf=false` 产出 LF。
- **同平台同配置不触发**：本机重复跑都是同一结果（确定性已验证）。
- **跨平台必然触发**：源码指纹与构建产物**两者都变**，所以 LF 机器上既构建不出同样字节，也过不了绑定校验。
- **严重度建议 P2（中）**：不会让程序跑不起来，但使"发布可复现"这道门在跨机器上**永久红且不可达成**，并把排查方向错误地指向"重建产物"。

**与 D-07 的界分（重要，别混为一谈）**：

| | D-07 | D-17 |
|---|---|---|
| 现象 | 清单记录 `7a45c9b2…` 与当前源码（**任何换行状态**）都不符 | 同一份产物下，源码换行一变，校验结论就从绿翻红 |
| 根因 | 产物是旧源码构建的（`generatedAt` 比 `web/` 最后提交早 58 秒） | `web/` 无 `.gitattributes` 换行约束，指纹与产物都随行尾变化 |
| 修复动作 | 在仓库根跑一次 `release.ps1` 重建产物 | 给父仓加 `.gitattributes`（如 `web/** text eol=lf` 或 `-text`）并统一构建换行 |
| 是否互相掩盖 | 不掩盖：本实验用"产物副本 + 盖章"把 D-07 隔离掉后，D-17 依然独立复现 | |

**修复方向**（本轮只诊断，不动仓库）：在父仓加 `.gitattributes`，把 `web/**` 钉成 `text eol=lf`（推荐：跨平台一致且与 docker 内 Linux 构建对齐），然后重新生成一次产物并按 LF 指纹入库；或退一步钉 `-text` 保证"检出字节 == 构建字节"。
