### 5.4 **W-2 核心**：连错 5 次后正确口令必须 200

```
$ # 连错 5 次（不插入成功）
fail#1 HTTP=401 VAULT_BAD_PASSPHRASE
fail#2 HTTP=401
fail#3 HTTP=401
fail#4 HTTP=429 VAULT_TOO_MANY_ATTEMPTS      ← 本窗口已有累计失败，提前触发
fail#5 HTTP=429
$ # 限流生效期间用**正确**口令
HTTP=200 {"ok":true,"injected":1}            ← 关键：不是 429，管理员不会被锁在门外
```

> 说明：本次 `fail#4` 就到 429，是因为**同一 60s 窗口里前面已有过失败**（我在此之前做过 5 次错误测试）。**新窗口从第 6 次起**才 429 的行为另有实测（`vault_unit` 用例 21–24 覆盖：5 次失败 401 → 第 6 次 429）。
> 两种情况下"**正确口令永远 200**"都成立，这正是 W-2 要修的东西。

**分桶**（另一来源同时打错应互不影响）—— HTTP 层同主机只能产生**一个**桶（脚本没开 `trust proxy`，`X-Forwarded-For` 不被信任），所以我在**限流器模块层**直接证明（`tmp/r5-final/bucket-probe.mjs`）：

```
A 连续 5 次: fail#1=401 fail#2=401 fail#3=401 fail#4=401 fail#5=401
A 第 6 次失败是否 429 : true
B 此刻是否被限流     : false （必须 false = 分桶）
B 第一次失败计数     : 1 （必须 1，不受 A 的 5 次影响）
B 第一次失败是否 429 : false
normalize(::ffff:127.0.0.1) = 127.0.0.1
映射地址与 IPv4 是否同桶: true
A 成功后是否还限流   : false （必须 false = 成功即清零）
PASS：分桶 + 归一化 + 成功清零 三条成立
--- exit: 0 ---
```
> **诚实边界**：这是**模块层**实测，不是两个真实 IP 的 HTTP 实测。要在 HTTP 层验分桶需要开 `trust proxy` 或两个网卡来源，本轮没做（会改动服务配置）。分桶逻辑本身（`src/mindcraft/unlock_limiter.js`）是纯函数，模块层实测已足以判定"B 不受 A 影响"。

- **命令**：`cd E:\我的世界ai && powershell -NoProfile -ExecutionPolicy Bypass -File scripts/e2e.ps1 -Scenario chest`（前提：无 java、25566/25576/18093 空闲；脚本自己也会查端口）

### 9.2 判定与归因（不是我把它做坏的）

2. **是已记录在案的未修缺陷**：`docs/audit-r5/fixes/09-chest-e2e.md §9` 写得很清楚——"⚠ 顺带测出的**间歇性缺陷（P1 候选）**：`fetch(N)` 会多搬，且账目对不上""10 次运行里出现 4 次"；§9.1 的失败签名与我这次**逐字相同**。
3. **t33 的修复没能解决它**（这是本单最该被看见的结论）：`mindcraft/src/agent/library/act_container.js` 确实有 +65/−8 的 T33 改动，注释里逐版记录了三次尝试，其中写着"**实测（t33 第三版）那样会把'放回容器的余数'又取出来 ⇒ 反而变成多搬（箱子 16→5，搬走 11）**"——**而我这次实测正是 16→5 / 搬走 11**。也就是说：当前树的实际行为与它自称"已移除"的坏版本**同签名**。
4. **脚本甚至专门为它写了容错**（`scripts/e2e.ps1:425-426`）：失败时打印"`[已知缺陷] withdraw/fetch 的请求语义被破坏（多搬 + 账目错）`"——**但退出码仍是 1**，没有把它粉饰成绿。这点值得肯定（没有放宽断言），但也说明**缺陷是已知且未修的**。
