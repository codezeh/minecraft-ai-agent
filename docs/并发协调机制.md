# 技能并发：设计结论 v3（不加锁）

> 状态：**结论稿，替代 v1/v2**。v1 提 4 把锁、v2 收敛到 2 把、**v3 结论是 0 把**。
>
> 起因是三次连续质疑，每次都证明我原来的方案在解决不存在的问题：
> 1. 「打开背包和控制身体不搭嘎吧」→ 砍掉跨资源死锁防护
> 2. 「窗口锁大概率是为了防止她乱跑吧」→ 发现前台本来不会抢窗口
> 3. 查完 `_executeAction` / `modes.update` → **系统本来就有三层协调机制**

---

## 1. 系统已有的三层协调（实测代码，不是推测）

### 第一层：前台动作之间 —— 打断式串行

```js
// action_manager.js  _executeAction
if (this.executing) {
    console.log(`action "${actionLabel}" trying to interrupt current action "${this.currentActionLabel}"`);
}
await this.stop();          // ← 打断前一个，不是排队
```

`_executeResume` 最终也调 `_executeAction`，所以 `followPlayer` 这类 resume 型
动作**同样在这个队列里**，不能和新动作并存。

> 结论：同一时刻只有一个前台动作在跑。**两个技能同时开 GUI 不可能发生。**

### 第二层：后台 modes 之间 —— 一次只跑一个

```js
// modes.js  update()
for (let mode of modes_list) {
    ...
    if (mode.active) break;      // ← 串行
}
```

### 第三层：前台 ↔ 后台 —— 声明式协调

```js
// modes.js  update()
if (mode.on && !mode.paused && !mode.active &&
    (_agent.isIdle() || interruptible)) {   // ← 前台忙时，只有"可打断"的 mode 才跑
    await mode.update(_agent);
}
```

每个 mode 自己声明能打断什么：

| mode | `interrupts` | 前台忙时能否插进来 |
|---|---|---|
| `self_preservation`（掉岩浆/溺水自救） | `['all']` | ✅ 能 |
| `unstuck`（卡住脱困） | `['all']` | ✅ 能 |
| `cowardice`（血少逃跑） | `['all']` | ✅ 能 |
| `self_defense`（挨打还手） | `['all']` | ✅ 能 |
| `hunting` / `item_collecting` / `torch_placing` / `elbow_room` | `['action:followPlayer']` | ❌ 只在跟随玩家时能 |
| `idle_staring` / `cheat` | `[]` | ❌ 不能 |

**所以：她开箱子/熔炉时（动作标签是 `action:newAction` 之类），
`item_collecting` 无权打断 —— 她不会被"边走边捡"推走。**

这才是"窗口锁"真正想防的事，而它**已经被 `interrupts` 声明解决了**。

## 2. 为什么不该加锁

| 想用锁挡的 | 实际已被谁挡 |
|---|---|
| 两个技能同时开 GUI | 第一层（打断式串行） |
| 两个 mode 同时推她 | 第二层（`if (mode.active) break`） |
| 她开窗时被 `item_collecting` 推走 | 第三层（`interrupts: ['action:followPlayer']`） |

**给一个已经有协调机制的系统再套锁，只会引入新问题**：

- 锁会挡住 `self_preservation` —— 她掉岩浆时还在排队等窗口锁，**这是要命的**
- 锁要处理重入/超时/抢占/死锁 —— 全是自找的复杂度

## 3. 真正的空档（唯一需要改的）

四个 `interrupts: ['all']` 的保命 mode **会**打断 GUI 操作。这是**正确行为**
（掉岩浆了还管箱子干嘛），但打断之后：

```
窗口被服务端关闭  →  技能后续 takeOutput / withdraw 拿到 null
                  →  报一个含糊的 'take_failed'
                  →  她不知道是"炼好了没取到"还是"窗口没了"
```

**这是"两个真相"的又一次：失败原因丢失。**

另外实测发现一个静默失效：**开窗后走远（实测 10.4 格）服务端会静默关窗**，
不报错。`tp` 传送不触发该检查（检查走移动包）—— 所以别用传送去测边界。

### 所以只需要：窗口操作前做存活 + 距离检查

```js
export function checkWindow(bot, win, blockPos) {
    if (!win || !bot.currentWindow || bot.currentWindow !== win) {
        return { ok: false, code: 'WINDOW_CLOSED',
                 message: '窗口已经关了（可能是自救行为打断的），需要重新打开' };
    }
    const d = bot.entity.position.distanceTo(blockPos);
    if (d > 4.5) {   // 取交互距离，比实测的 8~10 格保守；各版本/配置阈值不同
        return { ok: false, code: 'WINDOW_OUT_OF_RANGE',
                 message: `离容器 ${d.toFixed(1)} 格，超出交互距离，窗口已失效` };
    }
    return { ok: true };
}
```

调用点放在**原子层**（`loadFurnace` / `takeFromFurnace` / `waitForSmelt` / `storeItem` /
`verifyChest`），而不是复合层 —— 这样所有调用方都受益，不用每个复合技能重复写。

## 4. 纠正一个我自己的错误判断

我一度说「31 处 `modesPause` 大半是多余的」。**查完代码，这个判断是错的。**

它们是一致的模式：**动作进行中临时抑制某个 mode，动作结束后靠 `isIdle()` 自动恢复**。

```js
// modes.js
if (_agent.isIdle()) {
    this.unPauseAll();      // ← 空闲即全部恢复，所以不必手工 unpause
}
```

所以：
- 动作末尾**不需要**手工 `modesUnpause`（自动恢复兜住了）
- `followPlayer` 里那些**动作中途**的 unpause（离玩家远了要恢复捡东西）是**必要的**
- 因此**没有可收敛的冗余**，不该动它们

这条写在这里是为了防止以后有人（包括我）看到 29 处调用就以为"乱"而去合并，
结果把"中途动态恢复"的行为改坏。

## 7. 若将来真要并发，先过这三关

这个结论**不排除**以后有真并发需求，但门槛是：

1. 先有结构化返回值（`{ok, code}`）—— 否则 `PREEMPTED` / `LOCK_TIMEOUT` 表达不了
2. 先明确新 mode 的 `interrupts` 声明（别默认写 `['all']`）
3. 先能复现"两个行为同时动身体"的场景，再谈锁

## 附：一句话总结

> **这个系统的并发不是"缺锁"，而是"协调规则没写下来"。**
> 三层机制（打断式串行 / mode 串行 / interrupts 声明）已经够用，
> 缺的是把它们写成文档，以及 GUI 会话失效时的明确诊断。
