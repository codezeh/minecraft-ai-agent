# 原子层清理规划：把「移动」和「攀爬/落脚」分开

> 起因（用户判断，2026-10-25）：
> 「我感觉是原子技能不够干净导致的污染，移动和攀爬这几个动作不够明确」
>
> 这条判断经代码核实**成立**：`atom_move.js` 310 行、6 个导出函数里，
> `onGround` / `standable` / `findStandSpot` 命中数 **0** ——
> 移动原子完全不关心「我最后停在哪、是不是站着」。

---

## 1. 现状：一个 moveTo 承担了三件事

| `moveTo` 实际在做的 | 调用方以为它在做的 |
|---|---|
| 走到目标附近 | 走到目标附近 |
| （顺便）可能爬梯子/藤蔓上去 | —— |
| （顺便）可能停在半空、树叶上、水面上 | 停在可站位置 |

**后果**（都已实测）：

| 现象 | 根因 |
|---|---|
| `atom_drops` 报 `BLOCKED 现在悬空` | `collectDrops` 里 `moveTo` 后 bot 停在 `y=-50`（地面 -60） |
| 丛林里反复爬树顶再跳下 | `moveTo` 允许爬藤蔓，pathfinder 把它当合法路线 |
| 采集时"走不动但报 ok" | 返回里只有距离，没有落脚状态 |
| 测试用例互相污染 | 上一个用例的 `moveTo` 把 bot 留在意外位置，下一个用例无感知 |

## 2. 契约缺陷（对照《原子动作规格-v2》）

`moveTo` 的 `ok` 返回字段：

```js
{ pos, distFeetToPoint, advanced, partial, costMs, note }
```

**缺三个关键字段**：

| 缺的字段 | 为什么必须有 |
|---|---|
| `onGround` | 上层要判断"能不能接着挖"（`atom_dig` 依赖这个） |
| `standable` | 停在树叶/水面上时 `onGround` 可能为 true 但不可靠 |
| `landedAt` | 实际停在哪（可能和目标的 `pos` 差很远） |

## 3. 设计：两个原子，职责单一

### 3.1 `moveTo` —— 只负责"到达"

**不管**：会不会爬上去、停在什么方块上。
**必须报告**：最终位置 + 是否站稳。

```js
moveTo(bot, target, { tol, timeout, canDig }) -> {
  ok,
  data: {
    pos,               // 目标（原样返回）
    landedAt,          // ★ 新增：实际停的位置
    distFeetToPoint,   // 实际离目标多远
    advanced, partial,
    onGround,          // ★ 新增：bot 自报的落地标志
    standable,         // ★ 新增：按脚下方块判定（不信标志）
    groundBlock,       // ★ 新增：脚下是什么方块
    costMs,
  }
}
```

### 3.2 `climbTo` —— 独立原子，明确"我要往上爬"

现在"爬上去"是 `moveTo` 的**副作用**。改成显式动作：

```js
climbTo(bot, target, { maxClimb, timeout }) -> { ok, data: { pos, climbedTo, kind } }
```

- `kind: 'ladder'` —— 爬梯子（合法）
- `kind: 'vine'` —— **默认禁止**，除非调用方显式允许
- 判据：`y` 是否真的上升 + 到顶后是否站稳

**为什么要拆**：
1. "走过去"和"爬上去"的成功判据完全不同（距离 vs 高度）
2. 爬藤蔓几乎总是错的（已实测：丛林里会反复爬树顶）
3. 混在一起时，失败无法归因

### 3.3 `stepDown` —— 明确"下到地面"

`collectDrops` 现在用「往下逐层找站位 + moveTo」，实际是把"下到地面"藏在移动里。

```js
stepDown(bot, { maxDrop, wantGround }) -> { ok, data: { from, to, dropped } }
```

## 4. 本轮范围（只做契约修复，不重写全部移动）

| 步 | 内容 | 风险 |
|---|---|---|
| 1 | `moveTo` 返回补 `landedAt` / `onGround` / `standable` / `groundBlock` | 低（只加字段） |
| 2 | `makeMovements` 已移除藤蔓攀爬（**已完成**） | 已完成 |
| 3 | 新增 `climbTo` 原子 + 测试 | 中（新模块，需申报） |
| 4 | `collectDrops` 改用 `stepDown` 语义（不再靠 moveTo 找站位） | 中 |
| 5 | 全套验收 + 主服基线不退化 | — |

**不做**：`moveToXZ` / `moveToXZEx` 的合并（下一轮）。

## 5. 验收标准

| # | 判据 | 怎么验 |
|---|---|---|
| 1 | `moveTo` 停稳后 `standable` 为 true | 平地/树叶/水面三种场景 |
| 2 | `moveTo` 停在半空时 `standable` 为 false，且 `landedAt` 如实返回 | 造悬空场景 |
| 3 | `climbTo` 爬梯子成功、爬藤蔓默认拒绝 | 造两种场景 |
| 4 | `atom_drops` 不再报"现在悬空" | 全套测试 |
| 5 | 采集行为不退化 | 主服基线 ≥ 4/5 |

## 6. 判断标准（以后拆原子用）

用户的原话是"不够干净"。量化成三条：

| 检验 | 不合格的样子 |
|---|---|
| **一个原子只该有一个成功判据** | `moveTo` 既看距离又看高度 |
| **失败必须能归因到单一动作** | 报"移动失败"，但其实是爬错了 |
| **副作用必须显式** | "走过去"顺便爬了 3 格 |
