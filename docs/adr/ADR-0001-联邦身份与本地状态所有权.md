# ADR-0001 联邦身份与本地状态所有权

- 状态：**Proposed（rev 2）**（方向已由所有者确认并补录，尚未实施；阶段 0–1 落地后转 Accepted）
- 日期：2026-11-10
- 适用仓：父仓 `E:\我的世界ai` + 子仓 `mindcraft`
- 相关记录：`docs/audit-r6/00-缺陷报告.md`、`docs/audit-r6/architecture-gaps.md`、`docs/audit-r5/`
- 决策人：项目所有者；记录：captain

---

## 1. 为什么需要这份记录

这套系统要从「单人本机陪玩」扩到「多人服务器 + 多分身协作 + 串门互访」。一旦有第二个玩家、第二台机器、第二份存档，三件事就必须现在定死，否则以后每改一次都要迁数据：

1. **谁是「一个人」** —— 身份主键是什么、跨机器怎么互认
2. **状态归谁写** —— 多进程共享状态时谁有写权
3. **存档怎么切** —— 哪些数据跨存档、哪些按存档重置

这三件事都满足 ADR 门槛（难逆转 / 无上下文会费解 / 有真实取舍），因此立此记录。

## 3. 决策

### D1 · 本地真相 + 极小联邦面

每台机器一个 mindserver，玩家各自跑自己的存档。**不做全局统一数据库，不做数据复制。**

跨机器只交换三样，其余一概不过网：

| 内容 | 方向 | 时机 |
|---|---|---|
| 邀请凭证（含 scope 与有效期） | 主机 → 被邀者 | 房主签发一次 |
| 名片（稳定 ID + 当前公钥 + 签名） | 访问者 → 主机 | 首次串门 |
| 关系增量（`relations` 变化） | 双向 | 访问结束时 |

**存档、任务板、库存账本、记忆正文一律不出本机。**

### D2 · mindserver 独占数据库，agent 退化为无状态执行器

只有 mindserver 打开数据库；bot 子进程通过既有 socket 通道读写。**不引入分布式锁**——因为只有一个写者。

这条同时消灭：跨进程写冲突、`openBoard` 破坏性重建误伤、`mergeSharedChest` 抢锁失败后静默降级、`reserve` 的 check-then-write。

### D3 · 存储用 SQLite，不换引擎、不换语言

- 拒绝 PostgreSQL/Redis：单机、个位数到几十个 bot、写入低频，SQLite 的 ACID 就是所需，且零运维
- 拒绝 Go 重写：bot 运行时是 mineflayer（JS 生态），换语言省不掉 Node；共享规则会分裂成两份实现

### D4 · 身份分三层：稳定 ID、可轮换密钥、外部账号

```
people(id, provider, subject, display_name)          -- provider: mojang | offline
       UNIQUE(provider, subject)
avatar(id UUID PK, person_id UNIQUE, name)           -- 一玩家一分身（本地约束）
avatar_key(avatar_id, pubkey, version,
           activated_at, revoked_at)                 -- 可多把，签名链轮换
```

要点：

- **稳定 ID 是随机 UUID，不是公钥哈希**。公钥哈希做 ID 会让「换钥匙」= 换人，已发邀请与人物关系全部失效
- Mojang UUID 只是一个 `people.subject`，不是主键
- 离线模式不拿名字派生 UUID 当身份（2.8：它不含秘密）
- 轮换：新公钥 + **旧私钥签名**的迁移声明 → 追加 `avatar_key` 一行，`avatar.id` 不变
- 恢复：生成密钥时**同时**产一次性恢复码，存在 `.secrets.db` 之外（否则库一丢两样全没）
- **禁止无凭证的「重新生成」**：没有旧签名也没有恢复码，只能是新人（新 `avatar.id`），否则任何人都能声称自己是别人的重生

### D5 · 邀请制为准入，密钥为自动化；IP 只做风控不做身份

- 准入闸门复用**已开着的白名单**（2.10）：认证通过 → 写入 `whitelist.json` → bot 才连 MC → 到期移除
- Minecraft 登录握手**带不了签名**，所以认证必须在连服之前完成（这也是不写 MC 插件的理由）
- **IP / MAC 不作为身份**：
  - MAC **服务器收不到**（链路层地址，过路由器即重写），技术上不成立
  - IP 会**反向破坏**「一玩家一分身」：同 NAT 的家庭成员被误判为同一人；换 VPN 即可伪造新身份
  - IP 只用于：封禁、限流分桶、`events.source_ip` 审计、异常连接告警
- **先做撤销再谈自动化**：`!revoke` 与 `!invite` 必须同期存在

### D6 · 存档维度：两库分层

```
_global/mind.sqlite                          -- 跨存档
    people / avatar / avatar_key / relation / world / event(全局) / known_peers / visit_grants
_worlds/<world_id>/board.sqlite              -- 按存档重置
    team / team_member / board_job / inventory_reservation / inventory_ledger / container_cache
```

- `world_id` 由世界目录 sidecar 承载（删世界 = 新 ID），随备份走
- 目前全仓无 world 概念（2.9），这是新增维度，需要迁移既有 `board.sqlite`
- 记忆作用域按所有者确认：**身份与人物关系跨存档；队伍、任务板、共享库存按存档重置**

### D7 · 队伍共享库存 = 真实箱子为准 + 数量级预占 + 结算 + 对账

现状（2.3–2.6）只有「容器级独占」，没有数量账。决策：

1. **真相是真实箱子**；`container_cache` 只是缓存，**开箱时强刷**，取用失败时标脏
2. **数量级预占**：`inventory_reservation(world_id, item, qty, holder, expires_at)`，在**一个事务**内校验 `已预占 + 请求量 <= 已知库存`
3. **结算**：实际取用写 `inventory_ledger`，预占转消耗
4. **对账（必选项，非优化项）**：低频比对缓存与真实箱子，以真实为准修正账本；无对账则账实必然分叉
5. **合并两套箱子账本**（2.6）是前置条件：不合并，新账本与真实箱子永远对不上
6. 访客 bot 的活动**不写入本机账本**（它属于访客自己的存档）；主机侧只留审计

### D8 · 记忆先做结构化，暂不做语义检索

```
events(id, world_id, avatar_id, kind, payload_json, at, source_ip)   -- 追加写，永不改
relations(from_avatar, to_avatar, affinity, tags_json, updated_at)
```

- `events` 一次覆盖三件事：结构化记忆、按时间/玩家/任务统计、事后复盘
- 追加写天然适配「永远只增不改」
- **暂不引入向量库/FTS5**：当前瓶颈是「没有可检索的结构」，不是「召回不准」。表结构不动即可后加 FTS5

### D9 · 安全边界：离线模式只能防君子

诚实结论，写进记录以免以后误判：

- 认证链能防「没被邀请的人进来」，**防不住**「知道某人名字的人在放行窗口内冒名入侵」（2.8 的残余风险）
- 访客的 bot 是**别人机器上的代码**，白名单管不住它在你世界里做什么
- 因此：**装 WorldGuard 做区域限制**（事前）+ **CoreProtect 日志入 `events`**（事后）+ 白名单（准入），三件套；承认在 `online-mode=false` 下这是「防君子不防恶意客户端」
- 彻底解决只有 `online-mode=true`，与「朋友用非正版」冲突，故并存两种模式并如实标注风险

## 4. 备选方案与否决理由

| 备选 | 否决理由 |
|---|---|
| 全局 PostgreSQL/Redis | 单机 + 几十 bot，写入低频；引入服务端组件换不到任何东西 |
| 换 Go 重写后端 | bot 运行时锁死 JS 生态；共享规则（vault 加密格式、板 schema）会分裂成两份必须手工对齐的实现 |
| 微服务拆分 | 多一跳网络，换不到隔离收益；当前痛点是一个写者都没有，不是耦合 |
| 事件溯源全套 | 成本远高于收益；只取「单表 append-only `events`」这一子集 |
| 现在上向量数据库 | 先有结构化事件与关系，再谈相似度召回 |
| 用 IP/MAC 当身份 | 见 D5：MAC 收不到；IP 会误伤同 NAT 用户且易绕过 |
| 开放联邦（谁都能连） | 主机无法约束访客客户端行为，且离线模式下无法验证身份 |
| 每 bot 一份数据库 | 与协作、队伍共享、跨 bot 统计直接冲突 |

## 5. 后果与代价

**收益**

- 消除整类跨进程写冲突（D2）
- 「一玩家一分身」「队伍共享库存」从「不可判定/不存在」变为可判定、有事务语义（D4/D6/D7）
- 身份可跨机器验证，且换钥匙不丢关系（D4）
- 串门不需要搬运 bot 进程，联邦面保持极小（D1）

**代价**

- 每个 bot 的状态读写变成一次 RPC 往返（该规模下无感）
- 需要迁移既有 `board.sqlite`（加 world/team 维度）——**而当前迁移代码无独占锁**（2.3），必须先修
- 密钥与恢复码带来新的运维责任：私钥丢失 = 分身身份与关系丢失
- 几十 bot 时内存是硬约束（2.15 推断需实测），必须配同时在线上限与空闲休眠
- 两库意味着备份要同时覆盖 `_global` 与 `_worlds`，与世界备份的一致性需要对齐策略

| 阶段 | 内容 | 为什么必须在这个位置 |

## 7. 未决问题

1. 同时在线 bot 上限的具体数值，以及空闲休眠的触发条件与状态落库点
2. 恢复码的存放形态（打印件 / 外部密码管理器 / 两者）与恢复冷却时长

## 9. v2 补录（2026-11-10，需求澄清后）

本节记录五个需求岔口的裁定，以及由此产生的硬约束。**本节优先于 §3 中被它覆盖的表述。**

### 9.1 D10 · 分身必须自持，不支持托管

- 每个玩家必须自己跑 mindserver；不做"代跑分身"。
- 理由：托管意味着私钥、记忆、人物关系全部落在别人机器上，身份归属与数据归属同时失守。
- 后果：**阶段 0 的"从零部署能跑"从体验问题升级为准入前提**——现在按文档 clone 下来跑不起来（#7 无 JDK/server.jar/properties、#8 缺 web/node_modules、#9 备份不含 server.properties）。

### 9.2 D11 · 全网络唯一：唯一性锚在密钥上，不引入中心名册

- 系统强制：**一把密钥 = 一个 avatar**（`avatar_key` 中同一 `pubkey` 只能有一个活跃绑定）。
- 正版玩家额外有 Mojang 锚：`people.subject` = Mojang UUID ⇒ **一账号一分身可强制**。
- 离线玩家：**无法阻止其生成第二把密钥**。当前架构（无中心服务）只能保证"一钥一人"，**保证不了"一真人一分身"**。
- 若必须对离线玩家也强制，唯一途径是引入中心名册；该方案与 D1（无中心、纯联邦）直接冲突，**不采用**，残余风险如实记录。
- 这条是 v2 最重要的诚实边界：不要在未来把"一钥一人"误读为"一真人一分身"。

### 9.3 D12 · 组队需要双方同意；AI 可发起，玩家可否决

```
team_invite(world_id, team_id, from_avatar, to_avatar, status, expires_at)
```
- AI 可以自主发起组队邀请，但同样需要对方（AI 或玩家）accept。
- 玩家可以强制指派**自己的**分身，不能强制别人的分身。
- 拒绝要留痕（`events` 记一条），这是"关系"的输入之一。

### 9.4 D13 · 队内共享 = 只有队伍专属箱子

```
team(world_id, id, name, created_by)
team_member(team_id, avatar_id, role)
team_chest(world_id, team_id, x, y, z)     -- 只有这些坐标的内容进共享账本
```
- **私人物品永不进入队内视图**（D7 的共享账本只覆盖 `team_chest` 列出的容器）。
- 退队：释放该分身未结算的预占；已领用按 `ledger` 结清；**箱子里的实物留在原地不动**（不迁物、不分家）。
- 队伍按存档重置（与 D6 一致）：换世界即新队伍。

### 9.5 D14 · 冲突分级：按好感度阈值分四档

| affinity | 行为 | 开关 |
|---|---|---|
| ≥ 60 | 正常协作、可组队、可交材料 | 默认 |
| 0 – 59 | 可对话，拒绝主动帮忙 | 默认 |
| −50 – −1 | 拒绝组队、拒绝交材料 | 默认 |
| < −50 | 可偷取、可破坏 | **默认关闭**，需房主显式开启 |

- 每档行为由**策略层判定**，不由模型自由发挥（避免提示注入直接触发攻击）。
- 最低档必须同时受两件事约束：房主的开关 + WorldGuard 区域限制（D9）。
- 阈值是初始值，需真机调参；记录在 `events` 里以便回放。

### 9.6 v2 对实施顺序的影响

- 阶段 0：从"体验改进"变为"准入前提"（D10）。不修完 #7/#8/#9，别人根本加入不了。
- 阶段 2：身份层必须同时支持 `mojang` 与 `offline` 两种锚（D11）。
- 阶段 3：新增 `team_invite` / `team_chest` 两张表；退队结算规则（D13）。
- 阶段 3.5：冲突分档（D14），依赖 `relations.affinity` 已稳定产生。
