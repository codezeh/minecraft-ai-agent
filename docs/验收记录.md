## 2026-10-25 凌晨 · 原子二次拆分 → **17/17 全过**

### 起因（用户判断）

> 「那说明拆的还不够原子，你尝试拆一下，这样污染应该好查一些」

判断成立。证据就是那个自相矛盾：
`★ 回收成功` 报 `TIMEOUT 2786ms`，紧接着 `★ 背包真的 +1` 却 PASS。

### 拆分结果

`collectDrops` 原来一个原子干**五件事**（等 / 找 / 走 / 判 / 往下找），拆成：

| 新原子 | 职责 | 行数 | 测试 |
|---|---|---|---|
| `atom_find_drops.js` | 纯查询：找附近掉落物 | ~110 | 含在 16 条里 |
| `atom_wait_item.js` | 只等：背包数量变化 | ~110 | 同上 |
| `atom_drops.js` | 退化为编排 | 205 | 13/13 |

### ★ 拆分时抓到一个藏了很久的真 bug

```js
// 原来两处都这么写（collectDrops + 拆分时新写的一版）
.filter(e => e.type === 'item')
```

**实测 mineflayer 4.39 + MC 1.21.8：掉落物的 `type` 是 `'other'`，`name` 才是 `'item'`。**

后果：**"走过去捡"这条分支从来没执行过**，一直只靠"站在原地等自动吸附"。
修复后 `atom_drops` 的 steps 里第一次出现 `walk-to-drop`，13/13 全过。

### 三个矛盾症状 → 拆分后的可查性

| 症状 | 拆前 | 拆后 |

## 2026-10-25 凌晨 · 新增 L2 复合技能「清除障碍」

### 起因（用户实测反馈）

> 「如果在丛林中，树被藤蔓包裹的情况下，就不会砍被藤蔓包裹的树」

### 根因（两条叠加）

| # | 原因 | 说明 |
|---|---|---|
| 1 | **重构时清藤蔓能力没接上** | `task_collect` 里 `clearBlockers` 的调用在我重写 collect 时被删掉了，`vine_clear.js` 变成无人调用的死代码 |
| 2 | 旧实现本身也不够 | `vine_clear` 只沿「眼睛→目标」采样；而藤蔓是**贴着树干长**的，视线根本不穿过它 → 永远找不到 |

### 产物

| 文件 | 行数 | 内容 |
|---|---|---|
| `skill_clear.js` | ~190 | `inspectObstacles` / `planClearObstacles` / `blockersOnSightLine` / `vineAround` |
| `skill_collect.js` | 修改 | 每格挖掘前插入清除步骤，与挖掘同 `group` |
| `tools/skill_clear.mjs` | 新增 | **11/11 通过** |

### 验收结果

```
skill_clear：11 PASS / 0 FAIL
```

关键断言：

| 断言 | 结果 |
|---|---|
| 识别出被障碍物包围 | ✅ |
| 数出挡路方块 ≥3 | ✅ |
| 规划里有 clear 步骤 | ✅ cleared=4 |
| **先清障碍、后砍树** | ✅ clear@1 < digLog@2 |

规划结果样例：
```
1. moveTo   move   (-7,-60,9)
2. digBlock clear  (-6,-58,9)   ← 先清树叶
3. digBlock dig    (-5,-58,9)   ← 再砍树干
...
```

### 一个有价值的发现

旧实现只认 `vine`；实测**12 处树叶包围只能识别出 1 处**。
改成同时认 `_leaves$` 后全部识别——**树叶包裹和藤蔓包裹是同一类问题**。

### 已知测试债务（不是产品缺陷）

`atom_drops` 的「挖掉 oak_log」用例在顺序跑时偶发失败（`BLOCKED 现在悬空`）：
前一个用例的 `collectDrops` 会真实移动 bot（"往下找站位"），把 bot 留在半空，
后续用例的 `digBlock` 因此报悬空。**是测试用例之间耦合，不是原子缺陷**。
（单独跑 `atom_drops` 时 13/13 通过。）

| # | bug | 影响 | 修法 |
|---|---|---|---|
| 1 | **判据基准错位**（BUG-002） | 捡到 1 个后，后续每次捡拾都立刻判成功 → 再也不真捡。表现为「拿到 4 就涨不上去」 | `collectDrops` 改成每次调用自己快照基准 |

### 另一处效率优化（不是 bug）

原来「每格走一次 + 每格捡一次」，改成**「一棵树走一次 + 挖完统一捡一次」**：

| | 优化前 | 优化后 |
|---|---|---|
| 每棵树步数 | 9 步（3 格 × 3） | 5 步（1 走 + 3 挖 + 1 捡） |
| 走位次数 | 3 | 1 |

配套加了 `step_runner` 的 `skipGroup`：`moveTo` 失败时跳过同组剩余 dig，
避免"走不到 → 连挖 3 次全悬空失败 → 每次白耗 1.5 秒"。

### 剩余问题

第 5 轮 `拿到=0`、480s 超时、`step-failed=141`。发生在 `(-269,69,-352)`（高处）。
本轮已加"往下找站位"的补强，但**还没在这类场景实测验证**。

### 本轮新增两个原子

**`atom_look.js`（150 行）**：统一"看向"。底层用 `bot.lookAt`，补三件事：
目标解析（方块/实体/玩家/坐标）、实体看**头部**而非脚、**后置校验**。

后置校验是必须的：`bot.lookAt` 在目标被挡时会静默不转。实测角度验证：
正东 `yaw=-1.57`、天顶 `pitch=1.57`、脚下 `pitch=-1.57`。

**`atom_safe.js`（160 行）**：安全预检。修掉原 `skills.isSafeHere` 两个**会漏报危险**的缺陷：

| 缺陷 | 后果 | 修法 |
|---|---|---|
| 液体采样只扫 ±4 格 | 5~10 格外的岩浆被判"安全" → **两个真相** | 采样 + 枚举两条路都走 |
| `collectHazards` 以 bot 自身为圆心 | 查远处位置时答案完全错 | 改用目标位置作圆心 |

实测：6 格外的岩浆 `liquids=0`（采样没看到）但 `nearHazards=1`（枚举发现）。

**明确它的边界**：这是【预检】不是【保证】。`safe:true` 只表示"没有已知风险"，
不覆盖脚下塌陷/活塞/水下呼吸。API 带 `note` 明示。

### 一个反复出现的教训

本轮 3 个真 bug 里有两个是同一类：**状态标志不可信，要读世界**。
- `onGround=false` 但脚下明明是实心方块 → 用脚下方块判定
- `bot.lookAt` 返回成功但实际没转 → 读 yaw/pitch 校验

这和 R3-08（站树叶）是同一个道理：客户端的推断状态会骗人，方块和角度不会。

| 项 | 内容 |

## 2026-10-24 · 原子接口对齐（B 步完成）

### B 步顺带扫出的两类新矛盾（这两条最有价值）

| # | 矛盾 | 表现 | 修法 |
|---|---|---|---|
| 10 | **原子间调用传错形状** | `useBlock` 的工作站分支给 `openContainer` 传 Vec3，后者只收描述对象 → 报「目标位置无效」 | 改成 `{kind:'block', pos}` |

### 另外补的命名一致性

| 原子 | 改动 | 理由 |
|---|---|---|

## 技术债清理（2026-10-23）

| 项 | 处理 | 依据 |
|---|---|---|
| 40 个 `.dsh-ops-update-*.lock` 空文件 | **已删** | 全是 0 字节的临时残留 |

| `bots/` 14 个探针账号 | **保留待定** | 账号数据，需要你确认 |
