# 技能返回值契约（规则）

> 这条规则**本来就存在于代码里**（34 个查询类返回对象、38 个动作类返回 boolean），
> 只是没写下来，导致一度被"统一成对象"的改造搅浑。写在这里，避免再漂。

## 规则

> **动作类 → boolean ｜ 数据/查询类 → 对象**

| 类型 | 返回 | 例子 |
|---|---|---|
| **动作类**（做成一件事） | `Promise<boolean>` | `placeBlock`、`digDown`、`goToPosition`、`craftRecipe`、`smeltItem`、`equip` |
| **数据/查询类**（问一个问题） | `Promise<Object>` | `ensureNearbyBlock`、`storeItem`、`verifyChest`、`isSafeHere`、`planRoute`、`furnaceStatus` |

## 判断标准

问一句：**调用方要的是"成没成"，还是"结果是什么"？**

- 只要成没成 → boolean
- 需要拿到数据（坐标、数量、清单、诊断信息）→ 对象
- 需要"失败原因也机器可读" → **先确认真的有调用方要按原因分支**

## 为什么不做"全部对象"

曾经试图把动作类也统一成 `{ ok, code, message, data }`，理由是可以按失败原因分支。
实测发现：

- 全仓按 `.code` 分支的调用方：**0 个**（只有我自己写的 JSDoc 示例）
- `code` 也传不到模型那里 —— `runAsAction` 里
  `const actionFnWithAgent = async () => { await actionFn(...); }` 没有 return，
  技能返回的对象在命令层就被丢掉了

**没有消费方的能力，加上去就是负担**：改造面越大，回归风险越大，收益为零。

## 失败原因怎么让她知道

**靠日志**（`bot.output`）。她是读日志的，不是读返回值的。

所以动作类失败时：

```js
log(bot, `没有木板可以放（背包里有 0 个 oak_planks）。`);
return false;
```

要点：**先 log 再 return false**，别让失败静默。
（历史上有 10 处 `return false` 前面完全没有日志，后来补上了。）

## 例外：动作类需要返回数据时

不要为了"想拿到数量"就把动作类改成对象。两种做法：

1. 加一个**配套的查询函数**（`furnaceStatus` 就是给 `smeltItem` 配的）
2. 让调用方读日志，或者读 `bot.inventory`

## 2026-10-22 修订：新原子改用 ActionResult

背景：要引入执行器（重试 / 失败归类 / 一行播报），它需要按 `code` 分支，而不是去解析中文日志。这正是当年缺的「消费者」。

范围（关键：**不原地改**）：

| 范围 | 返回 |
|---|---|
| 旧 `skills.js` 全部函数 | **不变**（动作 boolean / 查询对象） |
| 新增 `atom_*.js` | 动作 → `{ ok, code, message, data }`；查询 → 原值 / `null` / `[]` |
| 旧命令调用方 | 走 `asBool(r)` 适配，不直接读对象 |

沿用 `{ok, code, message, data}` 四个键名，不第三次改名。完整规则见 `陪玩改造方案.md` §3.2 与 `原子动作规格.md` §0.1–0.7。

⚠️ 对象恒真：`if (await atom())` 永远为真。原子返回值只能在执行器里读 `.ok`。

## 新增技能时

- 先按规则定类型，写在 `@returns` 里
- JSDoc **必须写在函数体内**（`docHelper` 用 `toString()` 取文档，写在签名上方模型看不见）
- 启动时会自检（`utils/skill_doc_check.js`），"被引用却没有体内文档"会告警
