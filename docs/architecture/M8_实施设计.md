## 2. 分层与数据流

```
┌─ mindserver 进程（唯一写库）────────────────────────────┐
│  board_store.js   —— 增删改查 + 状态机 + 租约过期扫描      │
│       ↕ (node:sqlite, bots/_board/board.sqlite)        │
│  board_server.js  —— socket 事件 board:add/claim/…      │
└────────────────────────────────────────────────────────┘
              ↕ socket（带 ack，5 秒超时）
┌─ agent 子进程（每只 bot 一个）──────────────────────────┐
│  board_client.js     —— 事件薄封装，返回 ActionResult    │
│  board_scheduler.js  —— 空闲领单 → runAction → 续租 → 回报│
│  control.js          —— 已有的"停的原因/单去哪"（M2）     │
└────────────────────────────────────────────────────────┘
```

**为什么板必须在 mindserver**（06 §3 原文理由，我确认成立）：每个 agent 是独立子进程，
放 agent 里别的 bot 看不到；放 mindserver 则**只有一个进程写库**，省掉多进程锁。
`terrain3d` 虽然也用 sqlite 但**不共享**（06 §9.3 明确：多进程写同一 SQLite 要处理 WAL+busy 重试，收益不值）。

## 3. B1 详细设计（建议本轮做这个）

### 3.1 `board_store.js`（mindserver，约 350 行）

职责：**唯一写库的地方**。所有状态转移都在这里，不在调用方。

```js
// 表结构（两张表就够 B1）
jobs(
  id TEXT PRIMARY KEY,
  kind TEXT,            -- 'personal' | 'shared'
  title TEXT, skill TEXT, args TEXT,       -- args 存 JSON
  why TEXT, priority INTEGER,
  source TEXT, assignee TEXT,
  state TEXT, attempts INTEGER, maxAttempts INTEGER,
  lease_owner TEXT, lease_until INTEGER,
  progress TEXT, checkpoint TEXT, result TEXT,
  notBefore INTEGER, repeat_ms INTEGER,
  createdAt INTEGER, updatedAt INTEGER
)
claims(id TEXT, key TEXT, owner TEXT, until INTEGER)   -- B3 才真正用，B1 建表不填
```

必须实现的原子操作（06 §6 原文要求）：

```js
claimFor(bot)      // 原子：UPDATE ... WHERE id=? AND state='ready' → changes===1 才算领到
heartbeat(id, bot) // 续租；owner 不符或已过期 → { ok:false, code:'LEASE_LOST' }
finish(id, result) // 按结果决定 done / ready(attempts+1) / blocked / failed
expireLeases(now)  // 扫描过期租约 → state='ready'，**checkpoint 保留**
```

**三条容易写错的规则（06 §6，逐条写测试）：**

| 规则 | 要点 |
|---|---|
| 领单原子 | 靠 `UPDATE ... WHERE state='ready'` 的 `changes` 判断，**不要"先 SELECT 再 UPDATE"**（两个 bot 会同时领到）|
| 重试计数 | `INTERRUPTED` / `PREEMPTED` **不计** attempts；`TIMEOUT` / `STUCK` / `NO_PATH` **计**；`NO_ITEM` / `NO_TOOL` / `NO_RECIPE` → **直接 blocked**（重试没用）|
| 完成判据 | `ok` **且** `progress.count >= want`；只看"没报错"不算完成 |

### 3.2 `board_server.js`（mindserver，约 200 行）

只做三件事：**校验参数 → 调 store → 回 ack**。业务逻辑一律在 store 里。

```js
board:add       → 校验 skill ∈ 该 bot 注册表 & args 按 manifest.params → store.add → { ok, id }
board:list      → { mine?, state? } → { jobs }
board:claim     → { bot } → { job } | { job:null }
board:heartbeat → { id, progress } → { ok } | { ok:false, code:'LEASE_LOST' }
board:checkpoint→ { id, checkpoint } → { ok }
board:finish    → { id, result } → { ok }
board:set-state → { id, state, reason }（cancel/pause/resume）→ { ok }
board:hello     → { bot, skills, roles } → 记下该 bot 能领什么
```

**安全三条（06 §10 原文）**：
1. `skill` 只能填该 bot 报上来的注册名，**不能是任意函数名**
2. `args` 按 `manifest.params` 校验，不合格**直接拒、不进库**
3. 参数在服务端**再校验一遍**（不信任 agent 传来的东西）

### 3.3 `board_client.js`（agent，约 150 行）

薄封装。**必须实现控制层已经在调的那 5 个方法**（这是硬约束，见 §1）：

```js
list(filter)  get(id)  update(id, patch)  add(job)  setAutoClaim(bool)
```

另外 5 个给调度器用：`claim / heartbeat / checkpoint / finish / setState`。
全部返回 `ActionResult`；socket 5 秒无 ack → `TIMEOUT`；断线 → `INTERNAL` 并在 `data.retryable:true` 标记。

### 3.4 `agent.board` 接线（约 20 行）

```js
// agent.js 构造里
this.board = new BoardClient({ proxy: this.mindserverProxy, name: this.name, registry: compositeRegistry });
if (await this.board.hello()) console.log('[任务板] 已连接');
else { this.board = null; console.log('[任务板] 未连接，控制层降级为"没有单要动"'); }
```

**关键：连不上就保持 `null`**，与控制层现有降级完全一致 —— 不维护"有板/无板"两条业务路径（06 §9.2 末句：单 bot 和多机走同一套）。

### 3.5 三条命令（B1 范围）

| 命令 | 语义 |
|---|---|
| `!addJob(skill, args, priority?)` | 加个人单；`args` 是 `key=value` 串；**skill 必须在注册表里** |
| `!jobs()` | 列自己的单 + 可领的多人单：状态/进度/卡在哪 |
| `!cancelJob(id)` | 取消 |

权限（08 §5）：`!addJob` / `!jobs` / `!cancelJob` 属**信任级**（"下的单最高 6 级"由 `maxJobLevel()` 卡）。

## 4. B2 设计要点（抢占，真正动调度权的地方）

主循环（06 §8）：

```
空闲 且 未被玩家暂停:
  1. 有自己的 paused 单 → resume 它
  2. 否则 board:claim（个人单优先，再多人单；按 requires 过滤，按 priority、距离排序）
  3. 逐个 reserve(job.claims) → 冲突则全部 release，退避 5 秒
  4. action_manager.runAction(job.title, () => run(bot, args, ctx), { timeout })
     每 10 秒 heartbeat + progress
  5. board:finish(result), release 预约
```

**抢占（07 §4 / 06 §7）**：
- 玩家 9 级可抢任何单；6–8 级可抢比自己低 ≥2 级的；3–5 级不抢只排队；0–2 级只在完全空闲时
- 抢占 = `action_manager.stop()` → 流程在步骤边界读到 `interrupt_code` → `ctx.save()` → 返回 `INTERRUPTED`
  → 调度器把单记 `paused(reason:'preempted')` → 新单跑完按 checkpoint 续做
- **玩家说"停"时调度器也要暂停自动领单**，直到玩家说"继续"——否则她停一秒又去领下一张

**B2 的三个高危点（我会逐条写测试）：**
1. **抢占方与被抢占方不能同时驱动 bot** —— D18 已修（`killed` 后不再开新动作），B2 必须依赖这条
2. **`INTERRUPTED` 不能算失败** —— 否则玩家一喊停，单子 attempts+1，几次就 blocked
3. **暂停自动领单要有明确开关**，不能靠"当前没单"推断

## 5. B3 / B4 概述

**B3（多人单 + 预约 + 角色）**
- 预约 6 种 key（`block:` / `area:` / `container:` / `station:` / `entity:` / `item:` 视需要）
- **冲突返回 `CLAIM_CONFLICT`，流程按 onFail 换目标**
- 单 bot 时 `reserve` 恒成功（与现有一致，不维护两条路径）
- `requires: { roles, items }` 按 profile 的 `roles` 过滤

**B4（共享数据）**
- 地标、危险点、箱子内容搬进板库，各 bot 读写
- `terrain3d` **明确不共享**（06 §9.3）

## 6. 验收计划（对齐 06 §11/§12）

| 期 | 验收（原文） | 我的执行方式 |
|---|---|---|
| **B1** | 加单 → 重启 bot → 单还在，从断点接着做，不重复计数 | 真机：`!addJob(collect,...)` → 中途 kill agent → 重启 → 断言 `progress.count` 不倒退、不重复 |
| **B2** | 做 3 级单时玩家下 9 级命令 → 先做 9 级 → 回去接着做 3 级，进度不丢 | 真机：`!do collect` 跑起来后 `!goToPlayer`，断言被抢占的单 `paused(preempted)`、之后 resume 且 `progress` 保住 |
| **B3** | 两个 bot 领"采 64 原木"的 4 张子单：不砍同一棵树，合计 ≥ 64 | 真机：起 2 个 bot，断言 `claims` 无重叠、合计 ≥64 |
| **B4** | A 存进箱子的东西，B 不开箱就知道在哪个箱子 | 离线（读库）+ 真机（B 的 `fetch` 不试探直接去对的箱子）|

**离线测试（06 §12，必须接进 `unit_all`）：**
- 状态机**全部转移**（含非法转移要拒绝）
- 租约过期（**假时钟**，不 sleep）
- 两个客户端抢同一张单 **只有一个成功**
- 预约冲突
- 重启后恢复

## 7. 需要你先定的 3 件事

### ① B1 的边界：命令只给 owner 还是也给信任级？

08 §5 说 `!jobs` 属信任级、"下的单最高 6 级"。但 `!addJob` 会用 `skill` + `args` 直接驱动流程 ——
**信任级的人可以让 bot 去做任意流程**（采集/建造/战斗）。

- **选项 A（我倾向）**：`!jobs` / `!cancelJob` 信任级；**`!addJob` 只给 owner**。
  理由：`!addJob` 等价于"派活"，比"聊天/走/跟"重得多；而且它绕过了 `!newAction` 的白名单约束。
- 选项 B：全信任级，靠 `maxJobLevel()` 卡优先级。但"6 级单"仍能让 bot 去打架。

### ② 板库文件放哪、要不要进 git？

06 §3 写 `bots/_board/board.sqlite`。`bots/` 现在在仓库外还是里？这决定要不要加 `.gitignore`。
（我倾向：`bots/` 不入库，`board.sqlite` 也不入；但要有"库损坏自动重建空库"的兜底。）

### ③ B1 要不要现在就接 `!do`？

现在 `!do` 是**直接 `runAction` 跑**（M5 的实现，无板路径）。
B1 建好板之后，`!do` 可以改成"生成一张 priority 8 的个人单"（06 §8 末段说这是 **B3** 的事）。

- **选项 A（我倾向）**：B1 里 `!do` **保持直接执行**，只在 `!addJob` 走板。
  理由：先让两条路各自跑通，B3 再合并。**一次只改一个变量**。
- 选项 B：B1 就把 `!do` 改成走板，所有入口立刻统一。但那样 B1 一上来就同时动"数据结构"和"执行路径"，出问题分不清。

## 8. 风险与依赖

| 风险 | 说明 | 缓解 |
|---|---|---|
| **板存在但调度器不认** | 控制层已按"无板"写好降级，若 `board_client` 漏实现那 5 个方法，会出现两套行为 | 先写 `board_client` 的接口契约测试（假 socket），断言 5 个方法齐全且返回 `ActionResult` |
| **抢占把单搞丢** | 抢占→paused 的转移若漏了 checkpoint | 测试断言"抢占后 checkpoint 非空且 resume 后 progress 不倒退" |
| **租约过期与正在跑冲突** | agent 以为还在跑，服务端已经把单派给别人 | 06 §14 末：`LEASE_LOST` **立刻停手、不写结果**（别人可能已接手）|
| **重启丢单** | 这正是 B1 要证明的 | 验收就是"重启后单还在" |
| **`bots/` 路径与现有 `mapDirOf` 冲突** | 已有唯一真相 `bot_paths`，别新拼一个 | 板库路径也走 `bot_paths`，加一个 `boardDirOf()` |
