## 2. 为什么原子优先是对的

### 2.1 复合是乘法，不是加法

单次成功率 `p`，最多试 `k` 次，至少成功一次的概率是 `1-(1-p)^k`。

| 原子单次成功率 | 1 个方块 | 8 个方块（只试 1 次） | 8 个方块（每块最多 3 次） |
|---|---|---|---|
| 0.7 | 70% | 5.8% | 0.973⁸ ≈ **80%** |
| 0.8 | 80% | 16.8% | 0.992⁸ ≈ **93.7%** |
| 0.9 | 90% | 43% | 0.999⁸ ≈ **99.2%** |

三个直接结论：

1. **一次成功不重试 = 必挂。** 现在 `collectBlocks` 就是每块只试一次，所以 8 块几乎不可能全成。
2. **原子不需要 100%，但必须「失败可干净重试」。** 原子 80% 够用，前提是失败后状态没被污染。
3. **重试的前提是幂等。** 卡在屋檐下、goal 被抢、背包没变却报成功——这些不是「成功率低」，是**状态脏了，重试会放大错误**。

### 2.2 什么会变简单

契约冻结之后，新增能力 = **组合已有原子**，而不是重新调试一遍失败处理。

现在的 `skills.js` 是 54 个导出函数、6027 行，原子和复合混在一层，每个复合函数都自己写一遍 `try/catch`、自己猜原子返回什么。这就是复杂度的**乘法**。

目标结构：

```
原子（12 个，每个都有契约）
   ×
策略（1 份：重试、超时、中断、失败分类）
   ×
组合（N 个，每个只写「顺序 + 目标」）
```

### 2.3 什么不会变简单

复杂度不会消失，只会**集中**到两个地方：

| 复杂度 | 去哪 | 为什么 |
|---|---|---|
| 世界不确定性（藤蔓、建筑、玩家走动、岩浆） | **策略层**：失败分类 + 换目标 + 恢复 | 原子再聪明也管不了「路被封了」 |
| 模型能力（flash 不擅长长工具链） | **路由层**：只做听懂 → 选任务 → 播报 | 把多步决策压进确定性代码 |

所以「后面越来越简单」成立，但有条件：**前面必须把契约和策略做扎实，否则复杂度会反弹回复合层。**

## 3. 什么叫「原子动作」

### 3.1 五条判据（全满足才是原子）

1. **单一副作用**：要么只读，要么只改一处世界状态。
2. **成功可观测**：能用一句话判定（方块变 air、背包 +1、距离 ≤ 2）。
3. **失败可分类**：能落到 §4 的 8 类 code 之一，不出现「false 但不知道为什么」。
4. **能被一个 20 行脚本在真服上测**：不需要 LLM、不需要对话。
5. **可重入**：失败后再调一次，不需要手工清理状态。

判据 5 是新增的，也是最关键的——它直接决定 §2.1 的重试能不能用。

### 3.2 统一返回契约

动作原子统一返回同一个形状（查询不在此列）：

```js
{ ok: boolean, code: string, message: string, data: object }
```

| 键 | 何时必填 | 语义 | 不写什么 |
|---|---|---|---|
| `ok` | 永远 | 世界状态是否**真的**达成（不是“命令发出去了”） | — |
| `code` | 永远 | 失败归类，取自封闭枚举；成功为 `'OK'` | 自由文本 |
| `message` | 失败必填 | 一句人话，可直接播报给玩家 | 枚举名、堆栈、英文异常 |
| `data` | 永远（可为 `{}`） | 机器用：`pos` / `dist` / `block` / `costMs` / `count` | 给玩家看的句子、嵌套 `data.data` |

`code` 枚举：`OK / NO_TARGET / NO_PATH / OUT_OF_REACH / NO_TOOL / NO_ITEM / OCCUPIED / NO_SUPPORT / BLOCKED / TIMEOUT / INTERRUPTED / INTERNAL`

三条硬规则：

1. **顶层只有这四个键**。多出来的信息进 `data`，不另开字段。
2. **不用 `undefined`**（JSON 里会消失）、**不用 `null` 表示失败**；只有查询返回 `null` / `[]`。
3. **`INTERNAL` 才带 `data.error`**（message + 可选 stack）；业务失败不得伪装成异常。

⚠️ **对象恒真**：`if (await digBlock(...))` 永远为真。所以**禁止**在布尔语境里使用原子返回值；只有执行器读 `.ok`。

### 3.3 三条禁令

1. **原子不重试**：只做一次尝试，失败返回 code。重试是策略层的事。
2. **原子不调用 LLM**，也不解析自然语言。
3. **原子嵌套不超过 1 层**：`digBlock` 可以调 `canReach`，但不能调 `collect`。

### 3.4 模块布局

```
src/agent/library/
  atom_contract.js   ActionResult / ok() / fail() / withTimeout / interruptible
  atom_perceive.js   查询族（blockAt / findBlocks / canReach / countItem / playerPos）
  atom_move.js       moveTo / stopMove / lookAt
  atom_dig.js        digBlock
  atom_place.js      placeBlockAt
  atom_items.js      equipItem / dropItem
  atom_social.js     say
src/agent/tasks/
  executor.js        策略层：runTask / retry / deadline / cancel
  task_collect.js    B1
  task_follow.js     B2
  task_platform.js   B3
```

不用子目录：沙箱不允许在 `mindcraft/` 下新建目录（见 §12），所以前缀平铺。迁移期 `skills.js` 原样保留，新代码不 import 它的业务函数（只临时借用 `eyePosition`、`reachDistanceTo`）。

### 3.5 多细才算原子

**原子的粗细按「重试单位」定，不按动作大小定。**

三个测试，全过才是原子：

1. 失败后能原地再试一次吗？（幂等、无残留）
2. 失败原因能用一个词说清吗？（`NO_PATH` / `OUT_OF_REACH` / `NO_TOOL`）
3. 能用 10 行脚本判定成功吗？（单一断言）

两个附加：

4. 日志里一行能看懂吗？（`[atom digBlock] ok 1.1s` 有意义，`[atom collectBlocks] ok` 没有）
5. p99 时长 < 30 秒吗？（超了说明它在做复合的事）

锚点：**动作原子 8–12 个、查询 5–8 个、复合 3–5 个**。动作原子 > 15 说明策略或变体渗进来了；< 6 说明太粗。

三个反模式（现在代码里都有）：

- **原子带重试**：`collectBlock` 内部循环 `i<num`，失败继续——重试层级混了。
- **原子带规划**：`goToPositionPlanned` 用热力图绕路——规划属于复合层。
- **原子带播报**：`log(bot, 'FAILED')` 把内部细节喂给模型。

### 3.6 原子按结果定义，不按手段定义

`digBlock` 的成功判据是「方块消失」，不是「调用了 `bot.dig`」。手段可以换（挖、指令、工具），复合层不受影响。

同理，不要为 `moveTo` 造 `moveFast` / `moveSafe` / `moveNear` 三个变体——那是参数，不是新原子。

## 4. 原子清单与顺序

依赖图（箭头 = 前置）：

```
A0 契约
 └─ A1 感知 ──┬─ A2 移动 ──┬─ A3 挖掘 ──┐
              │            ├─ A4 放置 ──┤
```

| 编号 | 原子 | 内容 | 依赖 | 真服验收（跑 N 次） | 预算 |

| **B2** | 跟随 | `follow(player)`：500ms 追踪 + 追上 + 跟丢上报 | A2 | S1：8/10 | 0.5d |

### 「够用线」怎么定

- 原子：**80% 且可重试**即可进下一步，不追 100%。追 100% 会卡死在 pathfinder 上。
- 复合：**80%（8/10）** 才算这条场景过。
- 达不到 80% 时，先看是哪个原子在拖后腿，回到那一层修，不要在复合层加判断。

## 5. 测试场（这次最该补的基础设施）

### 5.1 为什么必须造场景

现在每次都在你的主世界里测，地形每次都不同：这次是丛林边有藤蔓，下次是屋檐底下。**失败不可复现，成功率就没法算。**

### 5.2 规格：独立的超平坦测试服

不占主世界，另起一个 Paper 实例：

| 项 | 值 |
|---|---|
| 目录 | `server-test/`（与 `server/` 平级，共用同一个 `server.jar`） |
| 端口 | `25566`（主服 25565 不动） |
| RCON | `25576` / `localdev` |
| 世界类型 | `minecraft:flat`，默认地层，地表 y≈-60 |
| 插件 | 无 |
| 内存 | `-Xmx1024M` |
| 规则 | 和平难度、不刷怪、关闭下界、`spawn-protection=0` |

好处：地形绝对干净、每次失败可复现、重建场景只要 `/fill`、测试崩了也不碰你的家和仓库。

场景用 RCON `setblock` / `fill` 在出生点附近造，测完还原。用独立账号 `probe`（现在的 `live_*.mjs` 已经是这么做的），不加载 deepseek 的记忆。每个脚本输出：`{ok, runs, passed, perRun:{code, costMs}}`。

**已实测**：出生点 `y=-60`，脚下 `grass_block`；RCON 通；`probe` / `builder` 可登录；RCON 造方块 → bot 立刻看得到。

### 5.3 场景库

| 场景 | 造法 | 用来测 |
|---|---|---|
| `flat` | 全平石头 | 移动基线 |
| `wall` | 中间一堵 2 格高墙 | 绕行 / 判断该不该挖 |
| `pit` | 3×3 深 4 格坑 | 下去 / 上来 |
| `tree` | 原木柱 + 树叶 + 藤蔓 | 采集（复现今天那棵树） |
| `ledge` | 悬空方块 | 放置的支撑面判定 |
| `water` | 2×2 水源 | 危险判定 |

**注意**：超平坦上跑通 ≠ 在主世界跑通。所以 S1–S3 必须回主世界再跑 5 次，那一步才是真实体验。

## 6. 分阶段排期

> 每阶段的写法、前置检查、失败分支、测试用例，见 [原子动作规格.md](原子动作规格.md) 对应小节。

### B0 契约与降噪（0.5d）

| 改什么 | 位置 |
|---|---|
| 新增 `ActionResult` 与 `fail()` | `src/agent/library/outcome.js`（已有雏形，扩成契约） |
| 删筛选回调里的 `log('FAILED')` | [skills.js:818、824](mindcraft/src/agent/library/skills.js) |
| 输出截断：> 200 行留头 20 + 尾 20 + 统计 | 命令执行返回处 |
| 静默失败审计：`/tp` `/give` `/setblock` 检查返回 | `tasks.js`、`cooking_tasks.js` |

**验收**：砍 8 个木头的完整日志 < 30 行。

### B1 测试服 + 感知（0.5d）

**先把测试服跑起来，再写感知。** 没有确定性场景，感知也只能靠猜。

**验收**：10 个构造场景全对（3 格远 / 5 格远 / 隔墙 / 头顶 / 脚下 / 水 / 岩浆 / 树叶遮挡 / 箱子后 / 未加载区块）。

### B2 移动（1d）

- `moveTo(x,y,z,tol=1)`：一次 `pathfinder.goto`，30s 超时，每 100ms 检查 `interrupt_code`。
- `stopMove()`：清 goal + 清控制键；**1 秒内位置变化 < 0.2 格**。
- `lookAt(pos)`：smoothLook，夹角 < 5°。

**验收**：8 方向 ×（15 格、30 格）= 16 次 ≥ 14；走一半发 stop 能真停；目标不可达时返回 `NO_PATH` 而不是抛异常。

### B3 挖掘（1d）

- `digBlock(pos)`：有工具 → `canReach` → `dig` → 确认变 air → `pickupNearby`。
- 失败分支：`OUT_OF_REACH`（含距离数字）/ `NO_TOOL` / `TIMEOUT`。

**验收**：`flat` 20 次 ≥ 18；`tree`（藤蔓+树叶）10 次 ≥ 7。

### B4 放置（1d）

- `placeBlockAt(pos, item)`：找支撑面 → 判定面朝向 → `canReach` → 放 → `blockAt` 复核。
- 失败分支：`NO_SUPPORT` / `OCCUPIED` / `OUT_OF_REACH`。

**验收**：`flat` 20 次 ≥ 18；`ledge` 5 次全对；贴墙 5 次。

### B5 物品 + 复合动作（1.5d）

- A5：`equipItem` / `countItem`。
- B1 `collect`：每块最多 3 次，失败换最近目标；每 5 秒检查 deadline；结束只报一行。
- B2 `follow`：跟丢 > 30 格追一次，追不上就上报；跟随时暂停抢 goal 的 mode。
- B3 `placePlatform`、B4 `comeTo` / `stay`。

**验收**：S1 8/10、S2 8/10、S3 7/10。

### B6 长会话（0.5d）

- `memory.json` 上限 20 KB（超了按时间淘汰，不靠模型自觉）。
- 上下文裁剪：`max_messages` 生效验证；自 prompt 关闭。
- 断线重连 + 重登后恢复原位。

**验收**：S0 30 分钟，memory 不涨、不掉线、不自己走开。

## 10. 风险

| 风险 | 应对 |

## 14. 增删规矩

### 14.1 加：两条硬判据

1. **两个消费者才配当原子**。只有一个调用方 → 私有函数，放复合里；两个以上 → 原子。
2. **新功能 ≤ 2 个新原子**。超过就停下来看：缺的是一类基础能力（比如“与方块交互”），不是又一个专用原子。

### 14.2 减：先减概念，再减代码

| 层 | 例子 | 为什么先减 |
|---|---|---|
| **概念** | 60 条命令 → 6；4 套记忆 → 1；2 个规划器 → 1 | 概念不删，代码删了还会长回来 |
| **入口** | 删命令，实现留着 | 最后一个调用方消失再删实现 |
| **代码** | 死代码、重复封装 | 收益最小，放最后 |
