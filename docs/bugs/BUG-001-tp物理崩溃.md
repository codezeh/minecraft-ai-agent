# BUG-001：外部瞬移（RCON tp）导致客户端物理崩溃 → 服务端踢人

> 状态：**✅ 已解决（升级 mineflayer 4.33 → 4.39，业务代码零改动）** · 记录 2026-10-24
> 证据脚本：`tools/_dbg_tp_dist.mjs`、`_dbg_noguard.mjs`、`_dbg_tp_physics.mjs`

---

## 0. 最终结论（2026-10-24 验证）

| | 4.33（旧） | 4.39（新） |
|---|---|---|
| tp 20 格 | ❌ 坐标 NaN，永不恢复 | ✅ 正常 |
| tp 60 格 | ❌ 同上 | ✅ 正常 |
| 连续 tp 5 次 | ❌ 第一次就崩 | ✅ 5 次全正常 |
| tp 后走路 | ❌ 0.2 格/秒（物理死） | ✅ 1.9 格/秒（可用） |
| 主服采集被踢 | 前两轮必踢 | ✅ **3 轮 0 次** |

**为什么换服务端没用**：协议虽是标准，但物理两边各算一份，踢人 = 两份对不上。
客户端算出 NaN，换哪个裁判都会踢。

**为什么换版本有用**：PrismarineJS 在这 6 个版本里修了瞬移后的物理状态处理。
`prismarine-physics` 版本没变（1.11.1），修复在 mineflayer 层。

**兼容性**：升级后 `atom_all` 14/14 全过（177 条用例），`preflight` 四层全绿。

## 1. 现象（用户视角）

- 她在主服上"**有点卡卡的**"
- 采集时频繁被踢：`multiplayer.disconnect.invalid_player_movement`
- 被踢集中在**前两轮**，第 3 轮往后正常（因为前两轮用了 `tp` 定位）
- 踢了之后自动重连，看起来像"她自己退出又回来"

## 2. 关键事实（一句话）

**服务端没问题。是 bot 这个客户端自己把物理算崩了，报到服务端的位置不合法，服务端按规则踢人。**

## 3. 证据链（全部实测）

### 3.1 距离阈值实验（`tools/_dbg_tp_dist.mjs`）

| tp 距离 | 结果 |
|---|---|
| 5 格 | ✅ 坐标正常 |
| **20 格** | ❌ **变成 NaN，永不恢复** |
| 60 格 | ❌ 同上 |

**结论**：`tp` 超过约 5~20 格，客户端物理就会算出 NaN。

### 3.2 对照：自己走路完全正常（`tools/_dbg_forward.mjs`）

```
起点 (-137,64,-218) → 走 3 秒 → (-137,64,-205)
位移 12.91 格 = 4.3 格/秒（正常速度）
```

**结论**：只有"被外部瞬移"会崩，自己走永远不崩。

### 3.3 物理崩了之后的表现（`tools/_dbg_tp_physics.mjs`）

```
tp 后 0.4s: y=74.9, vel=-0.16
tp 后 2.4s: y=73.9, vel=-0.45     ← 2 秒只掉了 1 格
tp 后 4.4s: y=71.7, vel=-0.72     ← 4 秒掉 3.2 格（正常自由落体应掉 60+ 格）
```

走 5 秒只移动 **1.2 格**（正常应该 21 格）。

### 3.4 不修会怎样（`tools/_dbg_noguard.mjs`）

```
tp 后 0.4s: (-299.5, 74.8, -399.5)
tp 后 1.0s: NaN ← 从这里开始永远 NaN
```

## 4. 因果链

```
RCON tp（>5 格）
  → mineflayer 物理引擎用「瞬移前的速度 + 瞬移后的位置」推演
  → 算出 NaN
  → 位置永远 NaN（不自愈）
  → 客户端报给服务端的位置不合法/乱跳
  → 服务端判 invalid_player_movement → 踢人
  → agent 自动重连 → 看起来像"她退出又回来"
```

而且物理半死状态（有坐标但走不动）会让位置包**稀疏、跳动**，
这本身也会撞上服务端的移动校验 → 额外增加被踢概率。

## 5. 试过但无效的方案（别再试）

| 方案 | 结果 | 为什么没用 |
|---|---|---|
| `spigot.yml` `moved-wrongly-threshold` 0.0625 → 0.5 | **仍然被踢** | 问题在客户端，不在服务端容差 |
| `spigot.yml` `moved-too-quickly-multiplier` 10 → 100 | **仍然被踢** | 同上 |
| 位置包节流（50ms 合并） | 无关 | 包稀疏是结果不是原因 |
| 故意把坐标设成 NaN | **不踢** | 说明服务端不是对 NaN 敏感，而是对"不合法/突变位置序列"敏感 |

## 6. 一个错误的修法（已废弃，必须记下）

**当初的修法**：`src/sim/position_guard.js` 每 tick 检查，发现 NaN 就用"最后一个 position 包"恢复。

**为什么错**：它只把**坐标**拉回去了，**物理状态还是死的**。
表现为"看着有坐标，但走 5 秒只移动 1.2 格"——比直接报错更难查，
而且半死状态下位置包稀疏，照样被踢。

**现在的修法（已改善但仍有局限）**：监听官方 `forcedMove` 事件，在瞬移那一刻
重建物理状态（速度清零 + 清控制键 + `jumpTicks=0`），并用 `physicsTick` 兜底 NaN。

> 但仍**没有根治**：`physics.js` 的 `timeAccumulator` / `lastSent` 是闭包变量，
> 外部改不到。真正的根治要改 mineflayer 内部或打补丁（方案 B）。

## 7. 当前方案（方案 A：不瞬移）

测试和实际使用**都不依赖 tp 定位**：

| 场景 | 做法 |
|---|---|
| bench 基线 | 走进森林后**连续跑 N 轮**，不每轮 tp |
| 测试脚本 | 每个测试用**独立区域**但**只 tp 一次**（5 格内安全），或干脆走位过去 |
| 运维手动 tp | 会中招；建议用 `spreadplayers` 之前先确认……不，`spreadplayers` 同样会崩 |

**新增规矩**：`tp` 超过 5 格后，必须重新连接 bot（因为物理已死）。
这条要写进运维脚本。
