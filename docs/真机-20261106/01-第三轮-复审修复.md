## 1. P1｜容器槽位更新延迟时被过早判断为零进度

### 复审指出的问题

`settleTransferCounts()` 只要「连续两次读到相同计数且光标为空」就认定转移完成，
**没有要求观察到任何变化**。异步槽位更新尚未到达时，两个旧快照也满足条件。
复审用受控延迟复现：存入操作 180ms 后才更新槽位，而函数约 **66ms** 就返回
`INVENTORY_FULL/stored: 0`；随后容器实际 +3、背包 −3。

### 改法（`src/agent/library/act_container.js`）

判据拆成两段：

1. **完成信号**：本次转移相关的计数相对 `baseline`（`invBefore`/`winBefore`）发生了变化，
   或光标上出现过东西（说明点击已开始）。**没看到任何变化 = 还没有证据**说明转移发生过。
2. **稳定**：①成立之后，才要求「连续两次读数完全相同且光标为空」。

配套：
- `settleTransferCounts` 新增 `baseline` 参数与 `sawChange` 返回值；
- 四个调用点（deposit 异常/正常、withdraw 异常/正常）全部传 baseline；
- 超时且从未看到变化 ⇒ 显式标 `unconfirmed: true` / `settled: false` 并打 warn，
  `verified` 不再谎称 true。**保留既有返回码**（`INVENTORY_FULL`/`INTERNAL`），
  不引入会破坏 flow 契约的新码（这一点下面 §1.2 有说明）。

### 附：中断时的光标残留（复审"其他检查结果"提到）

原来 `catch` 里 `if (/interrupt/i.test(msg)) return fail('INTERRUPTED', {item})` **直接返回**，
没有归还光标上的在途件 ⇒ 关窗时物品掉地上/消失。

现在两处中断分支都先调 `returnCursorToOrigin` 再返回：
- deposit 的在途件 ⇒ 送回**背包**（来路）
- withdraw 的在途件 ⇒ 送回**容器**（来路）

### 1.1 验证（`tools/review2_regression_unit.mjs`）

| 断言 | 结果 |
|---|---|
| 延迟 180ms 更新时，**不会**在更新前返回（耗时 ≥ 170ms） | PASS（实测 ≥170ms） |
| 最终报出真实部分进度 `stored=3`（不是 0） | PASS |
| 返回码仍是 `INVENTORY_FULL`（契约不变） | PASS |
| 这份报告是"已确认"的（`settled=true, unconfirmed=false`） | PASS |
| 与真实账单一致（背包 10→7、箱子 0→3） | PASS |
| 确实没动时仍返回零进度失败 + 显式 `unconfirmed=true`、不谎称 `verified` | PASS |
| 中断仍报 `INTERRUPTED`，且执行了光标归还 | PASS（`putBack=1, cursorReturned=true`） |

### 1.2 一处对复审建议的**偏离**（必须说明）

复审建议「超时返回未确认状态」。我先真的实现了 `TIMEOUT` 新码，但**撞了两条既有契约**：
`flow_p0_unit` 的「store 容器满 → INVENTORY_FULL」和「fetch 背包满 → INVENTORY_FULL」
都断言 `INVENTORY_FULL`；而且 flow 层不认识 `TIMEOUT`，会把它当未知错误扩散
（实测 fetch 场景直接退化成 `NO_ITEM`）。

所以最终采用：**保留返回码 + 显式 `unconfirmed`/`settled` 标记 + warn 日志**。
复审真正要防的「静默把旧快照折成零进度」已经不存在了——因为**修复的核心是"必须等到变化"**，
延迟 180ms 的更新会在 timeout（默认 1200ms）内被等到，根本不会走进零进度分支。
标记只用于"确实等到超时也没变化"的兜底，且不像以前那样静默。

## 2. P1｜模型请求期限没有覆盖响应体读取

### 复审指出的问题

`fetchWithDeadline()` 在 `fetch()` 返回 `Response` 时就执行 `finally` 并清掉超时计时器；
Ollama / Hyperbolic 随后才读 `res.json()`。服务端发完响应头但 body 持续挂起时，
应用级总期限已失效。复审实测：期限 35ms，`fetch` 立即返回，body 150ms 才完成，
整个请求仍等到 150ms。

### 改法（`src/models/_shared.js` + 两个调用方）

新增 `opts.parse` 回调：传了它，期限作用域**延伸到响应体读完**，
`timer` 与外部 abort listener 在 `parse(res)` 完成/失败之后才清。

```js
const res = await fetch(input, { ...init, signal: ctrl.signal });
if (typeof opts.parse === 'function') return await opts.parse(res);   // ★ 读体也在期限内
return res;                                                            // 旧调用方式不变
```

调用方把 `ok` 检查与 `.json()` 一起搬进 `parse`：
- `ollama.js`：`parse: async (res) => { if (!res.ok) throw new Error(...); return res.json(); }`
- `hyperbolic.js`：同上，并保留 429 的 `status` 字段（重试分支要用）

### 验证

| 断言 | 结果 |
|---|---|
| body 延迟 150ms、期限 35ms ⇒ **期限内中止** | PASS（`LLM_TIMEOUT`，实测 40ms） |
| 不传 `parse` 时仍返回 `Response`（旧调用方式不破坏） | PASS |
| `parse` 内的 JSON 语法错误**不被**误判为超时 | PASS（保持 `SyntaxError`） |
| 成功路径返回解析结果且无残留 timer | PASS |
| 外部 `AbortSignal` 在 body 读取中触发 ⇒ 结束且可判别为取消 | PASS（`LLM_TIMEOUT`，50ms） |

## 3. P2｜截断结果需要统一处理，不能把内部标记当作对话内容

### 3A｜适配器覆盖不完整

| 适配器 | 改前 | 改后 |
|---|---|---|
| `openrouter.js` | `finish_reason==='length'` → `throw` → `failedReply`（把写了一半的有效回答丢成错误） | 正常返回内容 + `markTruncated()` |
| `gemini.js` | 只读 `result.text`，**从不看** `finishReason` | `finishReason==='MAX_TOKENS'` ⇒ 打截断标记 |

> Gemini 的 `SAFETY` / `RECITATION` **不**打截断标记——安全拦截 ≠ 输出额度用完，
> 混为一谈会误导上层做"续写"决策。

### 3B｜标记泄漏到玩家可见内容

缺陷：`markTruncated()` 把 `[LLM_TRUNCATED]` 追加到正文末尾，但**全仓没有任何地方**
调用 `isTruncatedReply()`（grep 33 条命中里 0 处调用）。于是标记一路进
`promptConvo()` 返回值 → 聊天历史 → `routeResponse()` → **玩家真的看到这几个字**。

修法：新增 `stripTruncatedMark()`，在 prompter 四个出口统一处理：

| 出口 | 处理 |
|---|---|
| `promptConvo` | 剥离标记（玩家看不到），并置 `last_convo_truncated = true` 保留诊断 |
| `promptCoding` | **截断代码拒绝执行**：返回 `//no response (truncated)` 约定块，原文进日志 —— 半截代码最坏是语法错，更坏是把一句正确指令截成另一条危险指令 |
| `promptMemSaving` | 标记不许写进 `memory.json`（长期记忆不能被内部标记永久污染） |
| `promptShouldRespondToBot` | 标记会让 `=== 'respond'` 恒为 false，先剥离再比较 |

|---|---|

| Gemini `MAX_TOKENS` 被识别 | PASS |
| Gemini `STOP` 不带标记 | PASS |
| Gemini `SAFETY` **不**被误标为截断 | PASS |
| 对话正文已剥离 `[LLM_TRUNCATED]`，玩家看不到 | PASS |
| 剥离后仍保留结构化诊断 | PASS |

## 4. P2｜Docker 镜像依赖未跟踪的 UI 产物

### 复审指出的问题（这条直接命中我上一轮的疏漏）

`Dockerfile` 执行 `COPY web-dist ./web-dist`，但 `mindcraft/web-dist/` **在 Git 中未跟踪**
（`git status` 一直是 `??`）。全新克隆/CI checkout 没有该目录 ⇒ `docker build` 在 COPY 阶段失败。
"当前目录能构建"只证明本地生成产物存在，不证明干净检出可构建。

### 选型说明：为什么不是多阶段构建

复审给了两条路（产物入库 + 门禁查一致 / 多阶段构建）。**多阶段在这里走不通**，依据是门禁源码：

`tools/dockerignore_coverage_unit.mjs:126-128` 把每个 `COPY` 行**除最后一个之外的所有 token**
都当源路径，并 `existsSync(path.join(mindcraft, src))`：
- `COPY --from=ui /build/web/dist ./web-dist` ⇒ 把 `--from=ui` 也当 src ⇒ `existsSync('--from=ui')` = false ⇒ **门禁红**；
- 改用仓库根作构建上下文 ⇒ 所有 `src/...` 在 mindcraft 相对下不存在 ⇒ **门禁全红**。

⇒ 三者（零补丁 `docker build .` + `npm run gate` 绿 + 镜像带 UI）同时成立，UI 产物**必须固化在 `mindcraft/` 内**。
故取「产物入库 + 门禁查一致」。

### 改法

1. `mindcraft/web-dist/` **纳入版本控制**（9 个产物 + README + `MANIFEST.json`）；
2. `tools/sync_web_dist.mjs`：从 `web/dist` 同步并重写 `MANIFEST.json`（逐文件 sha256），支持 `--check`；
3. `tools/web_dist_manifest_unit.mjs`：门禁断言 —— 产物存在、内容与 MANIFEST 逐文件一致、
   无野文件、不是空壳（≥1 个 `assets/*.js`）。防「改了 `web/` 忘重新生成」与「手改产物」两种漂移；
4. **`.gitattributes`**：`web-dist/**` 与 `patches/**` 声明 `-text`。

第 4 点是实测发现的必要项：本机 `core.autocrlf=true`，Git 检出时把产物 LF→CRLF，
`index.html` 从 **398 字节变 411 字节**，9 个产物 sha256 **全变** ⇒ 干净克隆上的
一致性门禁**必然报红**（我第一次克隆就撞到了）。加 `-text` 后字节完全一致。

## 8. 本轮方法论上的两点收获

1. **"改了" ≠ "进了版本库"**：上一轮 t9 的 7 个适配器改动只存在于工作区。干净克隆才发现。
   复审第 4 条提的「干净检出」要求，价值就在这里。
2. **产物入库必须同时锁字节**：`core.autocrlf=true` 会让同一份产物在不同机器上哈希不同，
   一致性门禁直接失效。`.gitattributes` 的 `-text` 是这个方案的**必要组成**，不是可选优化。
