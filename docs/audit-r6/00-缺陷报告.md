## 1. 结论摘要（先看这 10 条）

1. **现在最危险的不是"缺功能"，而是三处会骗人的地方**：面板说"已发出/已停止"（#57）、备份说"能恢复"（#10）、启动脚本说"已启动完成"（#44）。三者叠加，用户会在**最不该放心**的时候放心。
2. **任务板是全系统单库共享，不是"每 bot 一份"**。`openBoard()` 全仓只有 `mindserver.js:965` 一处调用且不传参，`dir = boardDirOf() = botsRoot/_board`（`bot_paths.js:102-104`）。所以**队伍共享板不需要迁移库文件、不需要换数据库**。
3. 但"只有 mindserver 写"是**拓扑约定，代码零强制**；且 `reserve()` 非事务（#5）、`claims` 无 `UNIQUE(key)`（#5）、`mergeSharedChest` 吞掉 `BEGIN IMMEDIATE` 失败还返回 `ok:true`（#4）。这三条不补，任何新账本一接第二个写者就丢账。
4. **已经有人在直接清生产板库**：6 个 `*_live.mjs` 用默认 `openBoard()` + `DELETE FROM jobs/claims`，`catch {}` 吞失败、正常 DELETE 不留 `.corrupt-*`（#1）。这是账本方案的前置阻断项。
5. **箱子有两套账本**：板库 `shared(kind='chest')` 与 `bots/<bot>/memory/chests.json` 并存；`flow_store.js:24-27` 注释写"不再有第二个真相"，但 `!putInChest` / `!viewChest` / `verifyChest` / `findItemInStorage` 仍读写旧文件（#19）。
6. **控制面高危事件没有"面板门"**（#2），**任务板 socket 层零鉴权、可冒充任意 bot**（#3）——"每个 agent 只动自己的单"这条多 bot 协作的核心信任假设，在服务端**不存在**。
7. **从零部署没有供给路径**（#7）；按 README 装依赖会让「停止面板.bat」**直接不可用**（#8）⇒ 用户只能强关窗口 ⇒ 存档未刷盘。
8. **备份链的三个断点**：默认不备份 `server.properties`（#9）⇒ 恢复后没有 RCON ⇒ 优雅关服链断；`restore-drill` 只还原 `world`+`bots` 却给 PASS（#10）；`stop-all` 把"连不上"判成"没在跑"并 exit 0（#11）。合起来就是"以为有备份，其实恢复不出来，而且关服可能是硬关"。
9. **三条硬约束一条都不能判定**：一玩家一分身 = **不可判定**；队伍板 = **板在、队无**；队内材料清单 = **不存在**（§6，逐条给最小可行改造）。
10. **跨存档记忆 / AI 社交 / 多 bot 协作都不是"加功能"，而是"先搬数据"**：`world_id` 与 `people` 表是前置，顺序见 §8。

## 2. Must fix（19 条）

### #1 · live 实测工具直连生产板库并清空任务与预占

- **位置**：`mindcraft/tools/board_b3_live.mjs:128-131`（`const { db } = store.openBoard();` → `try { db.exec("DELETE FROM jobs"); db.exec("DELETE FROM claims"); } catch { }`）。同款：`a2_budget_live.mjs:40`、`first_night_live.mjs:39-41`、`t37_idle_live.mjs:99`、`t51_triple_round.mjs:50`、`m10_do_live.mjs:42`；`grep -l "DELETE FROM jobs\|DELETE FROM claims"` 另命中 `board_openonly_unit.mjs`。
- **触发 → 错误结果**：在任何一台已跑过 bot 的机器上执行一次 `node tools/board_b3_live.mjs`。`openBoard()` 不传参 ⇒ 走 `boardDirOf()` ⇒ 打到 `bots/_board/board.sqlite`（生产库）。三个叠加点：
  1. **无环境隔离**：默认参数就是生产路径，工具作者没打算写生产，但也没人拦；
  2. **`catch { }` 吞掉删除失败**：删不掉也继续跑，日志里看不出"我删了线上数据"；
  3. **正常 DELETE 不产生 `.corrupt-*` 备份**：这是合法 SQL，不是损坏重建路径，删了**不可恢复**。
- **实测线索**（captain 已核实）：生产库 `bots/_board/board.sqlite` 当前 `jobs=0 / claims=0 / shared=1`，目录内**没有任何 `.corrupt-*`**；而 `board_store.js:511-514` 的代码路径"jobs 从不删除"。两条事实的**唯一**自洽解释就是被这类工具清过（或手工清过）——这是相关性证据，不是抓现行（见 §10）。
- **最小修法**：`openBoard(dir)` 去掉默认值——不传 `dir` 直接抛错；`mindserver.js:965` 改成显式 `openBoard(boardDirOf())`。live 工具统一 `openBoard(join(tmpdir(), 'board-live-'+Date.now()))`，并在 `DELETE` 前断言路径不在 `botsRoot` 下。
- **跳过后果**：线上跑到一半的任务、别人正在预占的容器/区域一次性消失，且事后无法从库里看出发生过什么。**更关键的是：不堵住，新账本（#19、§6.3）也会被同一脚本清空**——这就是它必须是 P0 而不是"工具卫生"的原因。
- **源**：architecture-gaps §4.5 + captain 补充（本轮新增条目）。**证据级别**：【实测】+【静态】

### #2 · 破坏性控制面事件没有"面板门"，且多数没有速率限制；agent/panel 身份不可区分

- **位置**：`mindcraft/src/mindcraft/mindserver.js:1647-1659`（`stop-all-agents` / `shutdown`）、`:1603-1606`（`stop-agent`）、`:1353-1372`（`server-status/start/stop/log`）、`:1374`（`create-agent`）、`:1475`（`get-settings`）、`:1562`（`chat-message`）、`:1575`（`set-agent-settings`）。
- **触发 → 错误结果**：任何持握手 token 的连接（**包括每个 agent 子进程**）依次发 `stop-all-agents` → `shutdown`，整套控制面退出（`shutdownOnce('socket')` → `process.exit(0)`）。这些 handler 全部没有 `requirePanel`，除 `create-agent` 外**全部没有 `takeToken`**。
  **根因**：`isPanelConnection()` 的判据是"**没有**发 `auth.token`"（`:1241`）——换一种携带方式（query/header/cookie）就自动变成"面板"；面板只要发 `auth:{token}` 就变成"agent 身份"。**同一个 bearer token 区分不了两类主体，所以 agent/panel 不是鉴权，是语义标签。**
- **最小修法**：给危险事件统一加 `requirePanel(socket)`（`shutdown`/`stop-all-agents`/`server-*`/`create-agent`/`destroy-agent`/`set-agent-settings`/`stop-agent`），并给全部事件补 `takeToken`（`shutdown` 至少 1/60s）。真要区分主体，需要**第二种凭据**（agent 专用 token / 进程级 secret / mTLS）。
- **跳过后果**：一个被提示注入的 bot 就能关掉整台机器上的控制面、批量杀 bot、发 RCON 关服、起新进程。`stop-all-agents`（无限流）+ `start-agent`（6/min）还能组合成"反复杀/拉"。
- **源**：R6-CTRL-01。**证据级别**：【静态】

### #3 · 任务板 socket 层零鉴权：任何连接可冒充任意 bot

- **位置**：`mindcraft/src/agent/library/board_server.js:116`（`io.on('connection')`）、`:118-124`（`board:hello`）、`:216-236`（`board:claim`）、`:274-314`（`board:finish`）、`:317-330`（`board:set-state`）、`:391-437`（`board:shared-*`）、`:440-449`（`board:update`）。
- **触发 → 错误结果**：`grep -n "token\|identity\|isAgent\|auth" board_server.js` → **0 命中**。`board:claim`/`board:finish` 的身份取自 `payload.bot`，服务端**从不校验"这条连接是不是那个 bot"**；`board:add` 的 `assignee` 来自 payload；`board:shared-del` 无 owner 校验。于是任何过了握手门的连接都能：把别人的单收尾成 `done`、取消/暂停别人的单、删掉全队共享的箱子清单、把任意单指派给任意 bot。
- **最小修法**：`board:hello` 时把 `{bot}` 绑到 `socket.data`，此后所有 `board:*` 的身份**只取绑定值**、忽略 payload 里的 `bot/owner`；`board:add`/`set-state`/`update`/`shared-*` 加"只有 assignee 或 lease owner 可改"的归属校验。
- **跳过后果**：多 bot 协作的信任模型不成立；任何一只被注入的 bot 可以破坏其它 bot 的整个任务流，且没有审计线索。
- **源**：R6-CTRL-02。**证据级别**：【静态】

### #4 · `mergeSharedChest()` 把 `BEGIN IMMEDIATE` 失败吞掉，退化成非原子读-改-写并返回成功

- **位置**：`mindcraft/src/agent/library/board_store.js:2084-2109`。
- **触发 → 错误结果**：另一个写者正在写库（`BEGIN IMMEDIATE` 拿不到锁）时：

  ```js
  try { db.exec('BEGIN IMMEDIATE'); inTx = true; } catch { inTx = false; }  // ← 吞掉
  const prev = getShared(...);  ...合并...  putShared(...);
  if (inTx) db.exec('COMMIT');
  return { ok: true, key: k, value };   // ← 仍然报成功
  ```

  `BEGIN IMMEDIATE` 失败**恰好意味着"最需要原子性的时刻"**，此时函数静默做无锁读-改-写，正是 T31 第 16 条要消灭的"后写覆盖先写"，而且返回 `ok:true`，`board_server.js:405-416` 会把它转给 agent ⇒ **丢件且无人知**。注释写的"先拿写锁再读，保证中间不会被插进来"与实现相反。
- **最小修法**：`BEGIN IMMEDIATE` 失败必须**有限次重试 + 退避，或直接返回失败**；绝不允许降级继续。宁可让 agent 重试，也不能声称成功。
- **跳过后果**：箱子清单会在并发时静默丢物品，而调用方认为写入成功；后续所有"按清单取料"的行为都建立在错误数据上。
- **源**：R6-CTRL-05。**证据级别**：【静态】

### #5 · `reserve()` 是 check-then-write：无事务、无 `UNIQUE(key)`

- **位置**：`board_store.js:1285-1327`（`expireClaims` → `SELECT` 冲突 → 逐条 `INSERT`，四步之间**没有 `BEGIN`**）；表定义 `:137-141`（`claims` 主键 `(id,key)`）。
- **触发 → 错误结果**：单进程下靠 Node 单线程"中间不让出"侥幸正确（这正是测试全绿的原因）。一旦有第二个写者（队伍板让 agent 写、或运维开一个 sqlite 客户端、或 #1 那个工具），两个分身同时 `reserve('item:oak_log:5')` → 都查不到冲突 → 都插入 → **双占**，两边都收到 `ok:true`。而 `(id,key)` 主键**允许**同一个 key 属于不同 id，数据库层不阻止。
- **最小修法**：`BEGIN IMMEDIATE` 包住四步并加重试；`claims` 加 `UNIQUE(key)`（或唯一索引 + `INSERT ... ON CONFLICT DO NOTHING` 看 `changes`）；冲突返回 `CLAIM_CONFLICT` 而不是抛。
- **跳过后果**：两支 bot 同时搬同一批材料/开同一个箱子/占同一块地；上层"已预占"的假设全部失效。这是 #1 之后第二块必须补的地基。
- **源**：R6-CTRL-04。**证据级别**：【静态】（SQL 语义推断，未起第二个写者）

### #6 · "坏库自动重建"在多写者下是数据毁灭路径；WAL 设置失败被静默忽略

- **位置**：`board_store.js:283-330`（重建：`close` → `renameSync/rmSync` → 建空库）、`:271`（`PRAGMA journal_mode = WAL` 失败 `catch {}`）。
- **触发 → 错误结果**：A 进程判定损坏（或真损坏）→ 把 `board.sqlite` 改名 → B 进程手里还是**指向被改名 inode** 的句柄，继续写 ⇒ ① B 的写入落进"孤儿文件"，重启后消失；② A 的空库与 B 的库双真相；③ A 删 `-wal`/`-shm` 时 B 的 WAL 内容直接丢。目前"正确"只是因为**没有第二个写者**。WAL 那条：若某文件系统不支持，没人知道现在是 rollback journal 模式，`busy_timeout` 语义随之变化——**不可观测的状态差异**。
- **最小修法**：多写者前先有"唯一写者"机制（lock 文件/写者令牌）；重建改为"标记 + 由唯一写者执行"，或干脆**只报错不重建**；WAL/`busy_timeout` 设置失败要在启动日志里显式打一条（不能只 catch）。
- **跳过后果**：某天一次误判损坏 + 一个并发写者 = 任务与材料账**双库分裂**，两边都自认为成功；事后无法判断哪份是真的。
- **源**：R6-CTRL-06。**证据级别**：【静态】

### #7 · 从零 clone 之后没有"能跑的服务端"，而部署文档到此为止

- **位置**：`README.md`「从零开始（3 条命令）」、`scripts/clone-all.ps1:383-398`、`scripts/start-panel.ps1:181-183`。
- **触发 → 错误结果**：新机器照 README 跑完 3 条命令 → 双击「启动面板.bat」。干净 clone 里**没有**跑起来所需的三件硬前置：
  - `.tools/`（JDK）——`.gitignore:46`，`git ls-files` 0 个文件；
  - `server/server.jar`——`.gitignore:47` 的 `*.jar`；
  - `server/server.properties`——`.gitignore:74`，只跟踪 `.example`；
  - `server/world*`、`server/plugins/`——`.gitignore:58-66`。

  `git ls-files server | wc -l` = **11**（只有文本）。`clone-all` 打印的"下一步"从不提这些 ⇒ `start-panel` 必然停在 `[错误] 找不到 JDK` 或 `[错误] 找不到 server\server.jar`。唯一供给线索是 `server/.paper-url` 里一条 URL，**没有任何脚本读它**。
- **最小修法**：新增 `scripts/provision.ps1`（读 `.paper-url` 下 jar + 校验 sha、解 JDK 到 `.tools/`、从 `server.properties.example` 生成 `server.properties`），并排进 `clone-all` 的"下一步"；`start-panel` 报错指向它。
- **跳过后果**：这套系统**换一台机器就部署不起来**；所有"回归全绿"只在这台已经装好的机器上成立（见 #56）。
- **源**：OPS-R6-01。**证据级别**：【实测】（`git ls-files`/`.gitignore` 事实）

### #8 · 按文档装依赖会漏掉 `web/node_modules`，于是「停止面板.bat」根本无法运行

- **位置**：`README.md` 第 2 步（只有 `cd mindcraft; npm ci`）、`web/scripts/stop-all.mjs:14`（`import { io } from 'socket.io-client'`，解析基准 `web/scripts/`）、`scripts/stop-panel.ps1:19-25`、`scripts/start-panel.ps1:187-190`。
- **触发 → 错误结果**：照 README 装完依赖 → 点「停止面板」。`node stop-all.mjs` 立刻 `ERR_MODULE_NOT_FOUND` → 退出码 1 → `stop-panel.ps1:43-46` 打印"[未完成] stop-all.mjs 以退出码 1 结束"，但建议是"看上面对输出"，**不是**"去 `web/` 装依赖"。同一根因第二处：`start-panel:187-190` 发现 `web/node_modules/vite` 不存在时只 `Write-Warn2 '跳过'`，然后**继续**起服、打印"已启动完成"、打开一个必然 404 的地址。
- **最小修法**：README 补 `cd web; npm ci`；`stop-panel` 调用前预检 `web/node_modules/socket.io-client` 并给出确切修复命令；`start-panel` 把"缺 web 依赖"从 WARN 升级为**拒绝启动**（至少不打印"启动完成"）。
- **跳过后果**：优雅关服链断 ⇒ 用户只能关窗口/杀进程 ⇒ **存档未刷盘**。这不是体验问题，是数据风险；且它和 #11 合起来正是"用户强关窗口"的真实入口。
- **源**：OPS-R6-02。**证据级别**：【实测】（`web/node_modules` 缺失时 `ERR_MODULE_NOT_FOUND` 已复现）

### #9 · 自动备份默认不含 `server.properties`，恢复后"优雅关服"直接失效

## 6. 架构缺口与数据库缺口

> 本节回答用户的五条硬约束。**一句话总览**：三条硬约束里**一条都不能判定**；但好消息是任务板**不需要迁移数据库**（它已经是"单进程写 + WAL + 原子状态转移"的正确形态），要动的是**表结构维度**（world / team）和**库存账本**，以及"把身份从 bot 目录搬到 people 主键"。

| 硬约束 | 现状判定 | 一句话原因 |
|---|---|---|
| ① 一个玩家只允许一个 AI 分身 | ❌ **不可判定** | 身份是"每只 bot 一个 `identity.json`"，没有 people 表、没有 person→avatar 唯一约束；同一玩家可对 N 个 agent 各领一次码，同一个 agent 也可被 N 个玩家同时绑成 owner |
| ② 服务器内置任务板 + 各分身组队 | ⚠️ **板在、队无** | 板是**全系统单库单写者**（可复用，且**不需要迁库**），但数据模型里没有 `team`/`team_member`/`jobs.team_id`；`!addSharedJob` 只在权限表登记、无实现 |
| ③ 进入队伍板时共享队内材料清单 | ❌ **不存在** | 共享库存是"全服一张 `shared(kind='chest')` 缓存"，没有队伍命名空间，也没有数量级预占/领用账本，无法回答"队里还差多少材料" |
| ④ 正版/离线双身份归一 | ❌ **未归一** | 主键是"(bot 目录, uuid/name, level)"，不是人；离线服 uuid = `MD5('OfflinePlayer:'+name)`，**不携带秘密** |
| ⑤ 内存按存档隔离 | ❌ **完全没有** | 全仓 `world_id|worldId|save_id|saveId` 在 `mindcraft/src` 与 `web/src` **0 命中**；地形库/坐标类记忆都在世界无关路径 |

### 6.1 ① 一玩家一分身 —— 现状不可判定

**现状（逐条可查）**：`server.properties:38` `online-mode=false`；bot 取 `bot.players[name].uuid`（服务端下发，`commands/identity.js:24-38`）；离线服上该 uuid = `offlineUuidOf(name) = javaUUID('OfflinePlayer:'+name)`（v3 MD5，`identity_store.js:72-79`）；绑定写 `bots/<agent>/identity.json`（`:173-174`、`:329-351`）；定级 uuid 优先、名字只作回退（`:365-381`）；离线服标 `weak`，owner 只在 `!claim` 后 60 分钟会话窗口内有效（`settings.js:43-58`、`offline_identity_risk.js:158-175`）。

**为什么不够**：
- 绑定表挂在**bot 目录**下，主键是"这只 bot 的绑定数组"，**没有 person 实体**——全局唯一的"人"不存在；
- 面板按 agent 发码（`mindserver.js:1301-1325`）：同一面板持有人可对 N 个 agent 各发一次码、各 `!claim` 一次 ⇒ **同一玩家成为 N 个分身的 owner**，没有任何路径会拒绝；
- 反方向也没约束：`bindFromCode` 只在"同 uuid/同名"时覆盖（`identity_store.js:348`），不同人会被**追加**进同一 `bindings` 数组 ⇒ **同一个分身可以有 N 个 owner**（等级恒 `owner`）；
- 全仓唯一的"跨 bot 身份扫描"是启动时统计绑定总数用于提示（`mindserver.js:1826-1842`），只读、不判定、不拦截。

**最小可行改造**：`people(provider, subject) UNIQUE(provider,subject)` + `avatar(id, person_id)` 上加 **`UNIQUE(person_id)`**（NULL 允许多个 = 未绑定）。面板发码时做"此人已有分身"检查；`bindFromCode` 改成"绑到 person"而不是"追加 uuid"。

**验收**：对同一 `people.id` 连续两次绑定不同 avatar ⇒ 第二次必须被拒，且面板给出"你已有分身 X"；对同一 avatar 绑定第二个 person ⇒ 必须被拒或明确"换绑"语义。

### 6.2 ② 队伍任务板 —— 板在、队无；**不需要迁库**

**先纠正一个前提**：任务板**不是**"每 bot 一份"。证据：`openBoard()` 全仓只有 `mindserver.js:965` 一处调用**且不传参**；`dir = boardDirOf() = botsRoot/_board`（`bot_paths.js:102-104`）；agent 子进程**不打开 sqlite**，只走 socket（`board_client.js` 是薄封装）。`grep -rn "team|队伍|组队" board_*.js mindserver.js` → **0 命中**。

⇒ **队伍共享板不需要迁移库文件、不需要换数据库。** 需要的是"加 team 维度 + 一个原子取料 RPC"。

**为什么不够**：
- `shared` 主键只有 `(kind,key)`，`claims` 只有 `(id,key)` ⇒ 两个队伍都写 `chest:10,64,20` 或 `landmark:home` 会**互相覆盖**；
- 没有队伍表/成员表，等价物只有 `assignee`（单个人）与 `kind='shared'`（所有人；且 `'shared'` 是**拆单壳** `board_store.js:1923,1943`，不是队伍）；
- `board:list` 只有 `mine/claimable/all` 三档，`all` 是**全局**可见（`board_server.js:177-181`）⇒ 队伍板只能靠约定，不能靠代码；
- `claimFor` 没有"队内可见/队外不可见"的过滤（`board_store.js:663-669` 只按 `assignee` 与 `notBefore`）；
- 入口缺失：`!addSharedJob`/`!pauseJob`/`!resumeJob` 只在权限表登记、**零实现**（#42）。

**最小可行改造**：`team(id, world_id, name)` + `team_member(team_id, avatar_id)`，`avatar_id` 上加 `UNIQUE`（一人同时只在一队）；`jobs`/`shared`/`claims` 各加 `team_id`（`shared` 主键改 `(team_id, kind, key)`）；`claimFor` 加队伍过滤；`board:list` 增加默认档 `team`；实现那三条命令。**写者模型保持不变（单写者 mindserver）**。

**验收**：两个分身入同一队后，A 下的单在 B 的 `!jobs` 可见且可领；不入队的分身看不到、领不到；`!addSharedJob` 可用。

### 6.3 ③ 队内共享材料清单（真实箱子为准 + 预占/领用账本）—— 现状不存在

**现状盘点**：

| 最小机制 | 现状 | 证据 | 缺口 |
|---|---|---|---|
| 单写者 | ✅ 有 | `openBoard()` 仅 `mindserver.js:965` | 生产板库可被工具进程直接打开写（#1） |
| 事务 | ⚠️ 部分 | `mergeSharedChest` 用 `BEGIN IMMEDIATE`（`board_store.js:2084-2105`）；`reserve()` **无事务**（`1285-1327`） | 前者会静默降级（#4）、后者跨进程会双插（#5） |
| 预占原子性 | ⚠️ 仅"进程内恰好原子" | `reserve` 是同步函数，node 单线程 | 无 `UNIQUE(key)` |
| 超时回收 | ✅ 有 | `expireClaims`（`:1392-1397`）+ 5s 扫描（`board_server.js:451-460`）；TTL 30s | 无"回收后通知持有者" |
| **数量维度** | ❌ 无 | `claims` 只有 `(id,key,owner,until)`；`item:<name>:n` 的 `n` **只被解析、从不参与比较**（`board_claims.js:82-87`、`122-123`） | 是"互斥锁"不是"额度" |
| **领用结算** | ❌ 只有产出账 | `settleCraftLedger` 只记 **craft 产出** `checkpoint.producedTotal`（`:798-817`） | 没有"领了多少料、从哪个箱子、消耗在哪张单" |
| **对账** | ❌ 完全没有 | 全仓 `reconcile` 只出现在 `board_store.js:1000` 的一句注释，无实现 | 无定期核对、无差异修正、无"缓存不可信"标记 |
| **一个账本** | ❌ 两个 | `flow_store` 写 `shared`；`!putInChest`/`!viewChest`/`verifyChest`/`findItemInStorage` 读写 `memory/chests.json`（#19） | 两套账互不同步 |

**三个并发场景的推演结论**：
1. **同一箱子同时取同一批材料 → 能防住**：开箱前 `reserveNow('container:x,y,z')`（`act_container.js:186-215`），冲突即 `CLAIM_CONFLICT` 并当场换目标（`composite_registry.js:650-670`）。边界：依赖 `bot.__reserveNow` 被注入；无板时只 warn 一次**不阻塞**（`act_container.js:32-42,205-215`）。
2. **不同箱子、同一材料、各自取"最后一批" → 防不住**：规划读的是共享缓存；预占只有 `container:`（按坐标），**现实中没有任何流程产出 `item:` 预占**——`deriveClaims` 只在 `args.materials/cost/material` 显式给出时生成（`board_claims.js:231-254`），而全仓没有流程填这些字段（`strat_obtain` 的 `cost` 是策略代价整数）。结果不是"双花"（真实世界由服务端裁定），而是**白跑 + 反复 blocked/retry + 上层对"还剩多少"判断失真**。
3. **规划期与实际取料之间（幽灵库存）→ 无对账 ⇒ 缓存可长期偏大或偏小**，且没有任何机制会自己纠正。

**最小可行改造（三件套 + 一条铁律）**：
1. `inventory_reservation(world_id, item, qty, job_id, avatar_id, chest_key, expires_at, state)`：只表示"我打算领 N 个"，过期自动释放；
2. `ledger(world_id, ts, avatar_id, job_id, item, delta, chest_key, reason)`：**只追加**，`delta` 负数=取走，`reason ∈ {withdraw, deposit, craft, reconcile, rollback}`——这是唯一可审计的领用结算；
3. `reconcile`：**开箱即对账**（每次 `openContainer` 成功后回写 `container_cache` 并结算该 job 的预占），定时任务只做兜底（清过期预占 + 标记长期未核对）；
4. **铁律**：真实箱子永远赢。可用量 = `最近一次核对到的实际数量 − 未过期预占之和`；缓存必须带 `verified_at`，规划器不得把未核对的缓存当承诺。

**前置**：#19（先合成一个账本）、#1（先禁止工具清库）、#5（先让 `reserve` 事务化 + `UNIQUE(key)`）。**不先做这三条，新账本会同时被"清空"和"双占"两种方式破坏。**

**验收**：队伍页显示"材料 / 需要 / 已预占 / 可用 / 最后核对时间"；两人同时申请最后一组 ⇒ 只有一个 `ok`，另一个收到 `CLAIM_CONFLICT`（而不是白跑后 `NO_ITEM`）。

### 6.4 ④ 正版/离线双身份归一

**现状**：主键是"(bot 目录, uuid/name, level)"，不是人。`uuid` 在离线服上等价于 `name`（确定性派生）⇒ **uuid 不携带任何秘密**。三种情形：

| 情形 | 结果 |
|---|---|
| 冒名者把客户端名改成主人名 | 服务端发**同一个 uuid** ⇒ `resolveBinding` 精确命中 ⇒ 会话窗口内直接拿 owner |
| 主人改名 | 新 uuid ⇒ 查不到绑定 ⇒ 掉回 guest（`legacy_profile_names=false` 时名字不再兜底） |
| 冒名者用别的名字 | 无绑定 ⇒ guest（正确） |

现有设计对"改名冒用"的**唯一**抑制是时间窗口（`weak` + session），不是身份证明。代码注释是诚实的（`identity_store.js:17-20,51-71`；`config/network.json` 的 `_剩余风险`）。

**最小可行改造**：`people(id, provider ∈ {mojang, offline}, subject, display_name, first_seen, last_seen) UNIQUE(provider, subject)`。正版 `subject=uuid`；离线 `subject` 用**自建随机 id**（首次入服生成并落库），**不再用名字派生**；另设 `offline_binding(server_id, name, bound_at, approved_by)` 作为"名字→id"的**弱映射**，只用于提示、不用于授权。授权仍必须经过面板码：`!claim` 绑"当前连接"到 `people.id`，而不是"名字=某人"。

**必须写进文档的诚实结论**：
> 自建 server-side id 只能提供"稳定的句柄"，**不能提供"不可冒名"**。离线服没有共享秘密，服务端只能看到客户端自报的名字；任何"第一次见到这个名字就认定为某人"的规则都可以被"先到者冒充"击穿。要根治只有三条部署选择：①`online-mode=true`；②装离线可用的登录插件（AuthMe 等，密码=秘密）；③书面接受风险。代码层能做的是"把风险收敛到窗口内 + 让它在面板上可见"（现状已做到这一步）。

### 6.5 ⑤ 内存按存档隔离 —— `bots/<name>/` **不能**承载两层切分

**现状错位（这是决策 B 最危险的一处）**：

| 现有路径 | 语义 | 应属哪层 | 判定 |
|---|---|---|---|
| `bots/<bot>/memory.json` | 对话摘要 + 自我目标 + 地点 bank | 跨存档 | ⚠️ 内容对，但按 bot 分目录 ⇒ 换分身就断；**20KB 硬上限**（`history.js:333`）会把长期画像压没 |
| `memory/sites.json`、`storage.json`、`hazards.json`、`tasks.json` | 坐标/危险/长任务进度 | **存档层** | ❌ 现在是全局路径，世界重置后仍被沿用 |
| `memory/chests.json` | 箱子坐标与内容 | **存档层** | ❌ 同上，且是"第二份真相"（#19） |
| `map/terrain3d.db` | 地形扫描 | **存档层** | ❌ 同上——**最危险**：切换存档后旧世界地形仍被当作本世界地形使用（无 world_id、无 seed 校验） |
| `histories/*.json` | 对话归档 | 跨存档 | ⚠️ 语义对，但无 world 标记，无法区分"哪段发生在哪个世界" |
| `identity.json` / `identity-codes.json` | 玩家↔bot 绑定 / 待核销码 | **全局层** | ⚠️ 位置错：挂在 bot 目录、无 people 主键 |
| `bots/_board/board.sqlite` | 任务/预约/共享 | **存档层**（队伍/板/库存按存档重置） | ❌ 现在是全局单库，无 world 维度 |

⇒ **现结构不只是"缺 world 字段"，而是把两层错误地混在同一棵目录里**：世界相关的几何数据放在全局路径，而全局的人/关系数据放在按分身命名的目录里。继续在这棵树上打补丁，会得到"每个文件各自判断自己属哪层"的散乱实现。

**world_id 从哪来**（必须可稳定复现、可随备份走）：读 `level-name` 只能作 fallback（改名即变）；读 `level.dat` 的种子/时间不可靠（会随游玩变化）；**推荐**在世界目录内放 sidecar `.mindcraft-world-id`（首次使用时生成 UUID）——"删世界 = 删 sidecar = 新 id"正是"按存档重置"，恢复备份会带回同一个 id。`world`/`world_nether`/`world_the_end` 三个维度目录共享同一 id（绑主世界）。

**目标路径（只两个库，不引入服务、不引入第三层）**：

```
mindcraft/bots/                      # 只放运行时产物，不再承载身份/世界数据
  _global/mind.sqlite                # 全局层：people / avatar / relation / world 注册表 / 跨存档记忆
  _worlds/<world_id>/board.sqlite    # 存档层：team / team_member / board_job / reservation / ledger / 世界记忆
  avatars/<avatar_id>/memory.json    # 该分身的人格摘要（跨存档）
  avatars/<avatar_id>/histories/     # 对话归档（带 world_id 列）
```

迁移：首次启动若 `_global` 不存在而 `_board` 存在 → 把 `jobs/claims/shared` 整体搬进 `_worlds/<当前 world_id>/board.sqlite`，`_board` 改名归档（不删）。`MC_BOTS_ROOT` 覆盖语义不变——这是现成的测试隔离点（`bot_paths.js:59-63`），也是 #1 的修法基础。

**残留风险与硬规则**：部分恢复（只解 world 不解 bots）会让账本与真实箱子对不上 ⇒ 恢复脚本必须**整包恢复或拒绝**；启动时比对 `world_id` 与板库 `world_id`，不一致 fail-closed（拒绝接单，提示对账）；世界重置但库不动 ⇒ 旧 `_worlds/<old>/` 归档只读，新板从空开始；**热备份不做承诺**，冷备是唯一安全路径。

## 7. 前置阻断项（一条因果链）

> 用户当前的实际处境，用一句话说：**"以为有备份，其实恢复不出来，而且关服可能是硬关。"** 这三件事不是三个独立缺陷，是一条链。

```
① 你以为有备份
     #9  备份默认排除 server.properties（含 RCON 口令/online-mode/white-list）
     #46 备份不记录 6 个插件 jar 的名字/版本（恢复者靠记忆）
     #48 唯一的 RCON 暴露缓解是一条"换机即失效、无人自检"的防火墙规则
   ↓
② 其实恢复不出来（或恢复出来是另一台服）
     #10 restore-drill 只还原 world + bots（switch 只有两分支）
         ⇒ 不验 CoreProtect 库、不验插件加载、不验备份里的 server.properties
         ⇒ 但 report.json 给 verdict=PASS
     #47 失败时最有用的 Java 堆栈（boot.out）被清理删掉，报告还指向不存在的路径
   ↓
③ 所以你关服只能硬关
     #9 恢复后没有 RCON ⇒ stop-all 的 server-stop 返回 rcon_disabled
         ⇒ stop-policy.mjs:38-41 判 fail ⇒ stop-panel exit 4
     #11 stop-all 固定 1.5s 把"连不上"判成"没在跑"并 exit 0
         ⇒ 面板说"已停止"，其实可能还在跑
     #8  缺 web/node_modules ⇒ 「停止面板.bat」直接 ERR_MODULE_NOT_FOUND
   ↓
④ 硬关 = 存档未刷盘（用户看到的现象）
   ↓
⑤ 而且就算恢复成功，账本也是假的
     #1  6 个 live 工具直连生产板库 DELETE jobs/claims（catch 吞失败、无 .corrupt-* 备份）
     #19 两个箱子账本并存（shared vs memory/chests.json）
     #4/#5 reserve 非事务 + mergeSharedChest 静默降级 ⇒ 材料账可双占/丢件
```

**必须先做完的四件事（顺序不能换）：**

1. **#1 堵住"清生产库"** —— 不然下一步做什么都会被清空；这是**所有账本工作的前置**（也是本报告把它列 #1 的原因）。
2. **#8 + #11 + #9** —— 让"关服"这件事真的发生（能停、能确认、恢复后还能优雅停）。这三条合起来才解决"硬关窗口"。
3. **#10 + #46 + #47** —— 让"能恢复"这句话变成可证伪的（拆 verdict 两级、插件入 manifest、保住 boot 日志）。
4. **#19 + #4 + #5** —— 让"材料账"只有一个真相、且并发下不丢。

**为什么这条链要单独列**：这五条分散在四个审计域（ops/control/arch/agent）、原始严重度各异，但**用户的体验是一条**。按域修会得到"每条都修了、还是硬关"的结果。

## 8. 演进前置条件（按依赖顺序）

> 目标三件事：**跨存档记忆**、**AI 社交**、**多 bot 协作**。它们不是三个功能，是三层数据模型。下面是"必须先做完什么"的依赖顺序——每一步都标了"不做会怎样"。

### 第 0 层 · 地基（不做完，后面全是沙上建塔）

| 顺序 | 事项 | 为什么必须在最前 | 不做会怎样 |
|---|---|---|---|
| 0.1 | **#1 隔离工具与生产库** | 任何新表/新账本都会被 live 工具清空 | 账本方案上线当天被清一次，团队失去信任 |
| 0.2 | **#5 + #4 事务化 + `UNIQUE(key)`** | 新账本的"预占"必须原子；这是唯一可复用的正确范式（`claimFor` 的 `UPDATE…changes`） | 双占/丢件，且 `ok:true` 让人无从发现 |
| 0.3 | **#3 板 socket 绑定身份** | 多 bot 协作的信任模型建立在这条上 | 一只被注入的 bot 能改所有单，协作没有意义 |
| 0.4 | **#2 高危事件补面板门** | 协作意味着更多 agent 进程、更大 token 暴露面 | 一只 bot 能关整机 |
| 0.5 | **#6 唯一写者机制** | 0.1–0.4 都假设"只有一个写者" | 坏库重建/多写者双库分裂 |

### 第 1 层 · 空间维度（跨存档记忆的前置）

| 顺序 | 事项 | 依赖 | 不做会怎样 |
|---|---|---|---|

### 三个目标的"最小可交付"

| 目标 | 必须完成的最小集合 | 预计最先撞上的墙 |
|---|---|---|
| **跨存档记忆** | 0.5 → 1.1 → 1.2 → 1.3 | 1.2 的数据迁移（`_board` 改名归档不能删） |
