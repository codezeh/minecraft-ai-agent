## 二、第12条原问题（为什么这不是"日志难看"）

审查报告的实测：`tmp-t59-agent.log` 293 行里 **0 条**带时间、`run-live.log` 85 行里 **0 条**。后果：

1. 任何事故**定位不到秒**，只能靠上下文猜。
2. **LLM 调用 / 技能执行的耗时物理上算不出来** —— 没有起点时间戳，减法无从做起。
3. 连「两次 goal 冲突之间隔了多久」这种最基本的问题都答不了。

## 三、实现

### 3.1 `src/infra/log_prefix.js`

`installLogPrefix()` 把 `console.log / error / warn` 各包一层，输出 `YYYY-MM-DDTHH:MM:SS.sssZ ` 前缀。

四条硬要求，每条都对应一个真实会咬人的坑：

| 要求 | 做法 | 不这么做的后果 |
| --- | --- | --- |
| **保留 printf 语义** | 用 `util.format(...args)`，不用字符串拼接 | `console.log('%s 走了 %d 格', n, k)` 会变成字面量；`console.log({a:1})` 的对象展开会丢 |
| **幂等** | ① 包装函数带 `Symbol.for('mindcraft.log_prefix.wrapped')` 标记，已标记即跳过；② 兜底再查「这行是不是已经带 ISO 前缀」 | 重复调用 → `ts ts ts msg`，日志直接被污染 |
| **不改返回值** | `return orig.apply(this, [line])` | 上层若有依赖返回值的代码会被悄悄改行为 |
| **不吞异常** | 全程无 `try/catch` | 包装层吞掉错误 = 又一个"看起来没报错" |
| **单调可排序** | `Date.toISOString()`，定长 24 字符 `…Z` | 本地时区/变长格式会让字典序 ≠ 时间序，跨进程没法直接 sort |

只包 `log / error / warn` 三个，**不擅自扩大**到 `debug / info`（不在第12条范围内）。

### 3.2 接线：`src/process/init_agent.js` 顶部

```js
import { installLogPrefix } from '../infra/log_prefix.js';

// 必须在任何输出之前调用 —— 下面那条 Usage 提示也要带时间戳。
installLogPrefix();

const args = process.argv.slice(2);
```

一个诚实的边界：ESM 的 `import` 会提前求值，所以**本文件之前被 import 的模块在求值期打的日志抓不到**。
但本文件之后的全部（argv 解析、Agent 构造、后续运行期）都覆盖到了 —— 而运行期正是第12条要解决的
（"LLM/技能耗时算不出来"发生在运行期，不在 import 期）。

### 3.4 验收命令（逐字执行）

```
$ node -e "require('./src/infra/log_prefix.js').installLogPrefix(); console.log('probe-log'); console.error('probe-err')"
2026-11-05T10:26:45.236Z probe-log
2026-11-05T10:26:45.238Z probe-err
```

> 顺带确认了一个容易踩的点：本仓库 `package.json` 是 `"type": "module"`，
> 而验收命令用的是 `require()`。Node 24 支持同步 `require(ESM)`，所以这条路是通的
> （模块无 top-level await）。**如果以后有人在 log_prefix.js 里加 top-level await，这条验收命令会失效。**

## 四、单元测试 `tools/log_prefix_unit.mjs`（15 条）

为什么值得单独写：日志前缀这种东西**"打一行看到有前缀"最容易自欺** —— 然后漏掉幂等、漏掉 printf 语义、
漏掉 stderr。这些都是"装上之后才慢慢咬人"的类型。

| 组 | 覆盖 |
| --- | --- |
| 子进程真链路 | stdout 带前缀 / stderr 带前缀 / 前缀后紧接原消息 / 单调可排序 / 定长 24 字符 Z 结尾 |
| 幂等 | 连续 install 3 次后仍**只有 1 个**前缀；`isLogPrefixInstalled()` = true |
| printf 语义 | `%s %d` → `bot 走了 7 格`；对象 → `{ a: 1, b: 'x' }`；多参数 → `a b 3` |
| 边界 | `console.log()` 空参数 → 只出时间戳，不出现 `undefined` |
| 契约 | 返回值仍是 `undefined`；原函数抛错时**异常能冒出来**（没被吞）；`console.info/debug` 未被改动 |

设计取材：子进程那条是刻意用 `require(...)` 的 —— 跑的就是验收命令本身那条真链路。

> 两个自己踩到并修掉的小坑，记下来免得下一个人再踩：
> 1. 测试自身在 test 2 装上前缀后，后续 `PASS` 行变成 `2026-…Z   PASS …`，
>    而 `unit_all` 按行首 `^\s*PASS` 数用例 → **后面的用例全被漏计**。
>    修法：模块顶部保存安装前的 `console.log` 用来输出结果（`const emit = console.log`）。
> 2. 有一条 `check()` 写在了 `capture()` 回调里，输出被劫持进缓冲 → 那条 PASS 既看不到也不计数（14≠15）。

## 五、captain 的 4 项裁决（T03 后追加，已落地）

### 裁决 5（要求立刻做）：`Compartment` 不再挂在 no-undef

`eslint.config.js` 的 `languageOptions.globals` 显式声明：

```js
globals: {
  ...globals.node,
  Compartment: "readonly",   // 由 ses lockdown 在运行时提供，只读
},
```

带注释说明它是 SES 运行时注入的全局、不是本项目符号。
**效果（实测）**：`no-undef` **14 → 13**，剩下的 13 条**全是真缺陷**（逐条列在 T03-门禁.md §2.2）。
这样 T90 的 `no-undef = 0` 指标才有意义（否则永远有一条假阳性归不了零）。

### 裁决 4：lint 拆成「硬门 + 棘轮」

```json
"lint":       "eslint src main.js",        ← 硬门：目标 no-undef=0 / no-floating-promise=0
"lint:tools": "node tools/lint_ratchet.mjs", ← 棘轮：不许超过基线，不要求清零
"lint:all":   "npm run lint && npm run lint:tools"
```

- **硬门**现状：`✖ 304 problems`，**红着是设计如此** —— 等 T20/T21/T31/T32 修完才归零。
- **棘轮**：`tools/lint_ratchet.mjs` 跑 eslint → 按 **ruleId 分类计数 + 总数** 与 `tools/lint_tools_baseline.json` 比。
  - **一处分歧要说明**：裁决里写的 `584` 是 `src + tools + main.js` 的**合计**；**`tools/` 单独是 278**
    （硬门 304 − src 部分…）。棘轮按 `tools/` 单独计数才有意义，所以基线记 **278**。
  - 基线（217 文件 / 278 条）：`no-empty 129`、`require-await 128`、`no-floating-promise 8`、`no-undef 5`、`no-constant-binary-expression 2`、`no-irregular-whitespace 2`、其余各 1（`no-constant-condition`/`semi`/`no-dupe-keys`/`no-useless-escape`）。
  - **只查总数会被"修好一个又新写两个"骗过**，所以分类也逐项比（抓"总数没变但某类暴涨"）。
  - **棘轮真的会咬人（实测）**：往 `tools/log_prefix_unit.mjs` 尾部塞一个 `var x = 1 }` 缺分号 →
    ```
    ✗ tools/ 的 lint 问题超过基线（棘轮只许降不许升）
       · 总数 278 → 279（+1）
       · semi 1 → 2（+1）
    ```
    恢复后立即 `✓ 278 ≤ 278`。不是装饰品。
  - `--update` 用于**确实改善后**收紧上限（输出里会提示"可以收紧基线了"）。

## 六、t4 的三件附件

### 附件 1：`test_nav_opt` 不再硬编码用户名路径

```js
// 改前
const TMP = 'C:/Users/zeh/AppData/Local/Temp/navopt-test-' + Date.now();
// 改后
const TMP = process.env.NAVOPT_TMP || join(tmpdir(), `navopt-test-${Date.now()}`);
```
理由：把某个人的目录结构写进仓库，换机器/换用户名就跑不了。需要固定位置时用 `NAVOPT_TMP` 覆盖。

### 附件 2：3 个真机脚本「缺数据 = SKIP，不是 ERR」

`bots/` 在 `.gitignore` 里，干净克隆上必然没有。原来：

| 脚本 | 改前行为 | 改后行为 |
| --- | --- | --- |
| `test_memory_cap` | `readFileSync` 直接抛 ENOENT | `existsSync` 先查 → `SKIP` + exit 0 |
| `test_nav_opt` | 空库/缺目录 → 各种失败 | `existsSync(REAL)` → `SKIP` + exit 0 |
| `test_path3d` | 目录缺失时 `stats3d()` 抛 ENOENT；空库时 `exit(2)`（被当成"测试红了"） | 先 `existsSync(MAP)`，再判断空库 → 都是 `SKIP` + exit 0 |

`tools/unit_all.mjs` 同步支持这个约定：**行首 `SKIP` + exit 0 = 该脚本自报缺环境** →
计入跳过（**不计失败**），并且**点名打印理由**（否则就变成"静默没跑"，那是第18条那族坑）。

**实测（把 `bots/deepseek` 改名模拟干净克隆）**：

```
$ for t in test_memory_cap test_nav_opt test_path3d; do node tools/$t.mjs; done
  SKIP  test_memory_cap：缺少真机数据 ./bots/deepseek/memory.json（bots/ 不在版本库里；先跑一次真机再跑本测试）
  SKIP  test_nav_opt：缺少真机地形库 ./bots/deepseek/map（…）
  SKIP  test_path3d：缺少真机地形库 ./bots/deepseek/map（…）
（三个 exit=0，无 ERR）

$ node tools/unit_all.mjs --real memory_cap nav_opt path3d
  ⏭ test_memory_cap  (缺环境，脚本自报跳过)
  ⏭ test_nav_opt  (缺环境，脚本自报跳过)
  ⏭ test_path3d  (缺环境，脚本自报跳过)
  1/1 个脚本通过，3 个跳过            ← 0 失败
```

**恢复真机数据后**，同样三条 `--real` 下全部真通过：`✅ test_memory_cap (7) / ✅ test_nav_opt (18) / ✅ test_path3d (16)`。

> 计数口径也顺手改对了：摘要里「N/M 个脚本通过」的 M **不再包含跳过的**，
> 否则跳过会被算进分母，看起来像"通过率下降"。

### 附件 3：`SKIP_GATE=1` 保留

不变，仍可用。原因与 T03 §4.3 一致：硬拦中间态提交会把并发三路逼成习惯性 `--no-verify`。
