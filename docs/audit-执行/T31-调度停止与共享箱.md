## 1. 第 6 条 三处断链（逐条：病根 → 改法）

### ① `_runJob` 没走 `actions.runAction`（根因）
`board_scheduler.js` 原来 `result = await runner(this.agent, job.skill, argsToString(job.args), job);`
—— 直接调流程，`actions.executing` **全程 false**。

改成 `control.runJobAction(agentView, job, …)`。它是全仓**零调用方**的现成实现，负责四件事：
label=`job:<skill>`（`resolveJob` 靠它认出"被打断的是哪张单"）、把 `actions.currentJobId` 指向这张单、
按 deadline 换算 timeout、**经由 `actions.runAction` 驱动**（→ `executing` 真置位）。

★ **一个必须绕开的陷阱**（否则修出一个更严重的 bug）：`runJobAction` 内部是
`runAction(label, async () => { await fn(); })` —— **它把 `fn` 的返回值扔了**，只回传
ActionManager 的 `{success, message, interrupted, timedout}`。而 `finish()` 要的是 `{ok, code, message, data}`。
→ 用闭包把内层结果捞出来；否则 `result.ok` 恒 `undefined` → **每张单都被判失败重试**。

★ `agentView` 必须补 `actions`：调度器把 ActionManager 存在自己的 `this.actions` 上，
而 `runJobAction` 读 `agent.actions`。这是本文件记录的第**三**次"两处各叫一个名字"（前两次：board、interrupted）。
离线用例先把它暴露成 7 条 `run-failed`：`Cannot read properties of undefined (reading 'runAction')`。

### ② `action_manager.stop()` 的 `if (!this.executing) return;`
即使 ① 修好，仍有一个窗口：流程处在两个动作之间的等待里时 `executing` 是 false（或流程还没轮到第一个动作），
一次 `requestInterrupt()` 都不发 —— 面板上单变 paused 了，**身体接着干活**。
现在：只要有**在飞的任务单**（`currentJobId` 非空）就补发一次中断。
★ 刻意**不进**下面那个 10 秒等待循环、**不触发** zombie 重启：那套是给"真有动作在跑却停不下来"(D18) 用的，
套在这里会把"调度器在等模型/等 IO"误判成僵尸 → 白重启一次进程。

### ③ `setAutoClaim` 关错了对象 + `pausedReason` 只读不写
- `control.applyStop` 原来只调 `board.setAutoClaim?.(false)` —— 那只是**客户端镜像**字段，
  服务端不看、**调度器也不看**；真正管领单的是 `scheduler._autoClaim`（`board_scheduler:441`），
  而它的开关 `scheduler.setAutoClaim()`（`:385`）**零调用方**。
  → 现在两条都关（`agent.scheduler.setAutoClaim(false)`）。
- `pausedReason` **全仓一处读（`:540`）、零处写** → `_resumeOwnPaused` 里
  `j.pausedReason !== 'player'` **恒真** → 下一拍（约 3 秒）调度器就把这张单自己 resume 回 ready，
  玩家按停只生效一拍。
  → `planStop` 的 PLAYER 分支写 `checkpoint: { …(job.checkpoint ?? {}), pausedReason: 'player' }`
  （**合并写**，不覆盖已有断点）；scheduler 侧改成两处都读（`pausedReasonOf()`）。

### ④ 收尾：`finish` 不许把玩家按停的 paused 覆盖掉
`applyStop` 已写入权威状态（paused + result.INTERRUPTED + checkpoint.pausedReason），
而 `finish(INTERRUPTED)` 按 store 规则②会把状态**推回 ready**。
→ `_runJob` 的 finally 里先 `_jobPausedByPlayer(job.id)`（**读服务端权威状态**，不看本地镜像），
命中就跳过 finish 并发 `skip-finish-paused` 事件 —— 与 `_preemptedJobId` 同一道理：
**who 写下的状态更权威**。

## 2. ★ 第 6 条的失败反证（改之前会怎样）

用例 `tools/board_stop_unit.mjs` 的 ⑤ 用**变异体**跑同一场景：
把两处接线**一起**变异回原样（A: 直调 `runner`；B: `if (!this.executing) return;`），
因为它们是同一条链上的两个环（① 让 `executing` 为假，② 才因此提前 return）；只变异一个另一个会兜住。

```
PASS ★ ⑤ 失败反证：改之前 `executing` 全程 false、按停之后身体**还在干活**（步数继续涨）
     executing=false 步数 3 → 9
```

对照（改之后，同一个场景）：

```
PASS ★ ① 长单跑着按 !stop → 单 paused + pausedReason=player + 自动领单关 + 身体停下
     state=paused pausedReason=player autoClaim=false 步数 1/1/1
PASS ② 收尾守卫：玩家按停的单跳过 finish
PASS ★ ③ 自动领单打开后，玩家按停的单**仍不被自动 resume**
PASS ★ ④ applyStop(player) 关掉 scheduler._autoClaim → 下一拍真不领单（reason=auto-claim-off）
```

> 读法：**改之前按停之后步数从 3 涨到 9（她一直在挖），改之后停在 1/1/1（当场停手）。**
> 这就是"手没停"这个玩家可感知症状的量化证据。

★ 本文件的"身体"是假的、"库里"是真的：真 `board_store`（SQLite）+ 真 `ActionManager`
+ 真 `BoardScheduler` + 真 `control.planStop/applyStop`。

## 3. 第 16 条：共享箱并发写入丢件

**病根**（`flow_store.rememberChest`）：`sharedGet` → 本地叠加 → `sharedPut`，跨**两次 socket 往返**：

```
A 读 {oak_log:5} ─┐                ┌→ A 写 {oak_log:5, stone:3}
B 读 {oak_log:5} ─┴─(同一时刻)─────┴→ B 写 {oak_log:5}        ← A 那次被**整份覆盖**
```

丢件且**两边都返回 ok**。现场表现：箱子里的东西"越存越少"。

**修法**：`board_store.mergeSharedChest(db, key, delta, owner, {now, pos})` ——
`BEGIN IMMEDIATE` 内 `SELECT → 合并 → UPDATE`，把读-改-写收进**唯一写库进程**（mindserver，06 §3）的一个事务；
`board:shared-merge` 事件 + `client.sharedMerge(key, delta, pos)`；`flow_store` **只发增量**，
老的"读+整份写"两条调用已删除（不留第二条实现）。

合并语义与原来一致：`delta` 是增量，合计 ≤ 0 就删条目（不留 0 条垃圾），`pos` 保留、`owner/at` 取最后一次。

### ★ 失败反证（改之前会怎样）

```
PASS ★ ⑤ 失败反证：老做法（读-改-写）同一交错下 **A 的 oak_log 被整份覆盖** → 丢件
     老做法结果={"stone":3}（oak_log 没了，这正是本条要消灭的 bug）
PASS ⑤-b 同一交错的对照：合并版两条都在 items={"oak_log":5,"stone":3}
```

## 4. 补充A：`finish` 的 fail-closed 窗口（T30 留下的洞）

T30 的规则是"不传 bot 就不做归属校验"——那条 Must 级防护**对漏传者等于不存在**。
现在只收紧危险窗口：`bot` 未传 **且** 该行 `lease_owner` 非空 **且** 租约**还没过期** → `LEASE_STALE` + 一行 warn。
其余情形（无租约 / 租约已过期 / 正常传了 bot）**行为完全不变**。

```
PASS ★ ⑤ 不传 bot + 别人的**活**租约 → LEASE_STALE 且一字不写（fail closed）
PASS ⑤-b 边界：租约**已过期** + 不传 bot → 照常放行（不误杀残局收尾）
PASS ⑤-c 边界：**无租约**的单 + 不传 bot → 照常放行（老签名/离线工具不受影响）
```

warn 实际输出（跑测试时可见）：
`[board] finish 未传 bot，而单 j_… 的租约仍属于 A（until=4030000）→ 拒绝写入（LEASE_STALE，fail closed）`

### ★ 这条把 3 个既有用例的断言**翻转**了，说明如下
`board_store_finish_unit` 的 ④-c 原名"不传 bot（老调用方）→ 不做归属校验，照常写入" ——
那正是 fail-open 行为。已改为"不传 bot + 活租约 → 拒绝"，并在注释里写明是**由放行翻转为拒绝**。
另外 `board_store_unit`(6 条) / `board_b3_unit`(7 条) 里"领了单再 finish"的调用补上了 `bot`
（生产 `board_server:252` 一直传 `payload.bot`）—— 这是把测试改成**生产形态**，不是给判据开口子。

## 5. 补充B：`expireLeases` 回滚 `assignee`

`claimFor` 领单时会把 `assignee` 写成领单的人，而 `expireLeases` 原来只清 lease →
过期回 ready 的单**仍"指派给"那个死掉的 bot**；`claimFor` 的候选条件是
`assignee IS NULL OR assignee = 我` ⇒ **别的 bot 永远抢不到**（多 bot 永久死锁，且不报错）。

现在 `assignee` 与租约**同一处、同一条 UPDATE** 一起释放（退回共享池）。

```
PASS ★ ⑧ A 领单 → 租约过期 → **B 能领到**（assignee 随租约一起释放）
     afterClaim.assignee=A → afterExpire.assignee=null B领到=true
PASS ⑧-b 判据在源码里（expireLeases 的 UPDATE 含 assignee=NULL）
```

★ **代价记账**：这会让"原本只给 A 的个人单"在 A 崩后被 B 领走。另一条路是永久僵尸单，
账算下来这样更划算，且与 06 §6「租约过期即回收」一致。**请复核这个取舍。**
