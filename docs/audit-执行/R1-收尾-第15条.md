## 1. 一句话结论

同一张合成单「做出东西 → 中断 → 重试」的重复扣料，从 **"每重试一次真扣一次料"** 变为 **"账够了就不再重跑、一次都不多扣"**：
`finish()` 现在给每张 `craft` 单记 `checkpoint.producedTotal`（按增量累加、同一次尝试重复 finish 不重复记账），
`claimFor` 前的收敛清扫按**这张账**把已做够的单直接收敛成 `done`。

实测反证（§5）：**改前 2 次运行 / 扣 6 个原木，改后 1 次运行 / 扣 3 个原木**。

## 3. 改了什么（189 insertions / 13 deletions，两个文件）

### 3.1 `board_store.js`

1. **新增 `craftProducedOf(result)`（`:711`）** —— 从流程结果里取"本次尝试到目前为止产出了几件"，口径 **宁可少记、绝不虚记**：
   `data.producedTotal` → `data.produced` → （**仅当 `ok===true`**）`progress.count` → 0。
   *不采信 `data.count`，也不在失败分支采信 `progress.count`*：`flow_craft` 的失败分支写的是
   `base = { count: r.data?.got ?? got }`，而 `got` 是**合成次数**（perCraft=1 的配方下"要 3 次只做出 1 件"是常态）→ 拿次数当件数会**虚记** → 单子被判达标提前 done（该做的活没做）。
2. **新增 `settleCraftLedger(job, result)`（`:745`）** —— 增量结算：
   `delta = 本次产 − 上次已计`；`producedTotal(新) = producedTotal(旧) + delta`。
   "上次已计"用 `checkpoint.producedAttempt` + `checkpoint.countedSeq` 记账，**同一个 `attemptSeq` 内重复 finish 时 delta=0**。
3. **`finish()`（`:814` 起）**：
   - `const ledger = isCraftJob ? settleCraftLedger(...) : null`；
   - **新增完成判据** `ledgerSatisfied = producedTotal >= want` → `next = done`（`:819`）。这是"第二次扣料不会发生"的落点：账够了就**不再回队列**；
   - 落盘：`checkpoint = { ...旧, producedTotal, producedAttempt, countedSeq }`（`:936-941`）；`result.craftLedger = { producedTotal, delta, attemptSeq }` 供只读对账；
   - `progress.count` 对 craft 改成"**本单累计产出**"（`Math.max`，只许涨）—— 原来它是"背包里该物品总数"，正是复审 §3.2 说的"看不出扣了几次"。
4. **`convergeIfSatisfied()`（`:534` 起）**：craft 不再整条关掉，改成 **看产出账**：有 `producedTotal` 且 `>= want` → 收敛成 done；**没有该字段的老 row 仍然不收敛**（t120 的行为原样保留，不猜）。这样被打断回 `ready` 的单在**下一次 claim 的清扫**里就被收敛，而不是再跑一遍流程。
5. **`claimFor()`（`:641`）**：领单即"新的一次尝试"，在同一条原子 `UPDATE ... WHERE state='ready'` 里把 `checkpoint.attemptSeq` +1。
   为什么必须要有它：`attempts` **区分不开**"同一次尝试被重复 finish"和"下一次尝试"（它只在 finish 计数的那一刻 +1，两次 finish 之间不动）。没有这个序号，增量对账要么翻倍、要么永远不累加。

### 3.2 `act_craft.js`

改造点是**所有 craft 之后的退出路径都要如实报产出**（原来有两条路径把产出扔了）：

- `bot.craft` 抛错（`:359`）：先算 `countItem` 差值；`INTERRUPTED` / `INTERNAL` 都带 `produced` / `producedTotal` / `invAfter`。
  `bot.craft(recipe, limit)` 内部按次数循环，**被中断时可能已经合出若干件（材料已经真扣了）**，原来这两条 `fail` 只带 `{item}` → 账记 0 → 重试再从零做一遍。
- 合成后等待背包同步的轮询里被中断（`:387`）：同上一路。这一支最容易被漏：`bot.craft` 已 resolve、产物可能已进背包，紧接着收到中断。
- 成功返回（`:446`）新增 `producedTotal`，并在注释里写明口径边界：**跨尝试的累计不在动作层做**（`act_craft` 拿不到 jobId），由 `board_store` 记账。

## 4. 边界（如实说明：它解决了什么、没解决什么）

### 4.1 覆盖：**走到了 finish 的那一类**（A 类）
`INTERRUPTED` / `TIMEOUT` / 部分产出后失败 / 后续步骤失败 / 被抢占后收尾 —— 每次尝试结束时把**这次的真实产出**记进账；
账 `>= want` 时单子直接 `done`，或在下一次 `claimFor` 的清扫里被收敛 → **不会再有第二次运行，也就不会有第二次扣料**。
这一类正是复审描述的"连续崩 2 次、材料被真扣 2 次"的原发场景（真机里 `flow_craft` 中断/失败后返回中断码，单子回 ready 被重领）。

### 4.2 未覆盖：**进程被 SIGKILL / 崩溃，根本没走到 finish**（B 类，残余）
`checkpoint` **是持久化的**（SQLite 列），但**只在 `finish`（或显式塞断点）时写**。进程被杀时这次尝试没有落库时机 →
这次产出记不进库 → 重试仍会重做一份。**残余上界不变：≤ `maxAttempts-1` 次**（`maxAttempts=3`，即最多 2 次）。
`tools/craft_retry_ledger_ab.mjs` 的 **B 场景**把这条钉成了可复现记录（新旧版都跑 2 次），防止以后有人把它当"已修好"。

**要彻底消掉 B 类，最小路径（不在本单边界内，建议 captain 排期）**：
按 `docs/audit/08-deep-executor-flows.md` **E6** 修 `composite_registry.js:109`
（`run: (bot,args,ctx) => runCraft(bot, args.item, args.count)` → 传 `{ctx}`），让 `flow_craft` 在**每轮 `craftOnce` 之后**把累计产出写 `ctx.checkpoint('craft')`（`board:save-checkpoint` 已经是现成的持久通道）。
那时动作层就能知道"这张单已经做出几个"，重试可以只补差额（顺带消掉 4.3 的过度生产）。

### 4.3 部分产出的过度生产仍然存在（只影响浪费量，不影响账）
账 2/3 时重试仍会从头做 3 个（`flow_craft` 不知道账），最终可能多做 1 个。
但**账不会重复记**（增量口径），且材料变成了物品而不是凭空消失 —— 损失量从"无界/每次重试×N"降到"每次重试 ≤1 份自身需求"。

### 4.4 `board_server.js` 为什么没改
`board:finish` 已经是 `finish(db, id, payload.result)` 原样转发（`board_server.js:259-268`），`result.data` 一路不落地丢字段（t105 已修）。
本次改动全部落在 store 内部与动作层，**socket 层不需要动** —— 少改一个文件就少一处风险。
