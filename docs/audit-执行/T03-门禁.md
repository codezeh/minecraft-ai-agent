## 二、第11条 ①：eslint 两行

`eslint.config.js`：

```js
globals: globals.browser,   →   globals: globals.node,
ecmaVersion: 2021,          →   ecmaVersion: "latest",
```

为什么这两行就值这么多：

- **`ecmaVersion: 2021` 造成的不是"少查几条规则"，而是"整个文件没被检查"。** 20 条 `Parsing error`
  意味着那 20 个文件（全部在 `src/models/`）解析失败 → eslint 根本没看它们的语义。所以它们里面的
  `semi` / `require-await` / `no-undef` 全部**不可见**。这是第26条同族的问题：
  **"没有报错"和"没有检查"在输出里长得一模一样。**
- **`globals.browser`** 让 Node 代码里的 `process` / `__dirname` / `Buffer` 被判成未定义。
  57 条 `no-undef` 里 51 条是这种误报，真问题被埋了。

### 2.1 改动前后的真实计数（自己跑出来的，不是抄报告）

| 规则 | 改动前 | 改动后 | 说明 |
| --- | ---: | ---: | --- |
| **Parsing error** | **20** | **0** | 19 条 `Unexpected token =` + 1 条 `Cannot use keyword 'await'` |
| **no-undef** | **57** | **14** | 43 条是 `globals.browser` 的误报，已消失 |
| **no-floating-promise** | **39** | **39** | 数量不变 —— 但含义变了：现在 39 条**全部可见**（见下） |
| semi | 107 | 136 | **+29，因为新解析的 20 个文件终于被检查了** |
| require-await | 78 | 97 | **+19，同上** |
| no-extra-boolean-cast | 0 | 1 | 同上（新暴露） |
| 其它（no-empty 8 / irregular-whitespace 4 / …） | 8+4+2+1+1+1+1 | 同左 | 不变 |
| **合计** | **319** | **305** | |

> 合计只降 14，但**结构完全变了**：20 条"看不见"变成 0；no-undef 从 57 条噪音变成 14 条真问题；
> 同时 49 条**真问题**（semi/require-await）从"解析失败所以看不见"变成"看得见"。
> **总数下降不是目标，"看得见"才是。** 拿总数比前后会得出错误结论。

### 2.2 剩下 14 条 no-undef 全部是真问题（逐条核过）

| 位置 | 未定义符号 | 判断 |
| --- | --- | --- |
| `src/agent/action_manager.js:149` | `assert` | 真 · 缺 import |
| `src/agent/library/skills.js:5750` | `ok` | 真 · 缺 import |
| `src/agent/modes.js:118,126` | `placed` | 真 · 变量名错/漏声明 |
| `src/agent/modes.js:133` | `walked` | 真 · 同上 |
| `src/agent/npc/item_goal.js:163,164` | `res` | 真 · 报告 §3.3 点名过的 ReferenceError |
| `src/models/novita.js:47` | `sendRequest` | 真 · **报告第30条**（novita 分支漏写） |
| `src/models/vllm.js:67,69,74` | `path` | 真 · 缺 import |

即 **13 条真问题 + 1 条配置缺口**（`Compartment`）。任务预期写的是"no-undef 57→6 真问题"，
**实测是 14 条（13 真 + 1 SES 全局）**，比预期多 8 条 —— 差异来自 `src/models/` 那 20 个文件现在真被检查了，
而报告当时的 319 是基于"它们解析失败"的状态数出来的。**以本表为准。**

这 14 条**不归 T03 修**：按任务要求「你只负责让它们可见」。`novita`/`vllm` 归 T20（security），
`modes`/`skills`/`item_goal` 归 T21/T32。`Compartment` 是否补 globals 声明由 T20 定（改 lockdown 时一起看）。

### 2.3 关于 no-floating-promise「39 条全可见」

`39 → 39` 数字没变，看起来像"什么都没做"。实际上：改动前有 20 个文件解析失败，
那 20 个文件里的 floating promise **一条都报不出来**。改动后它们被解析了，
所以现在这 39 条是**跨全部 162 个源文件**的完整集合。变的是**覆盖率**，不是数量。

覆盖 `src tools main.js` 后，`tools/` 下 214 个探针/基准脚本的大量历史问题一并可见。

## 四、第11条 ③：真触发点 = git hooks（不是 CI yaml）

**选择：`git config core.hooksPath .githooks` + `.githooks/pre-commit`（已随本次提交入库）。**

理由（说明为什么不选 `.github/workflows/ci.yml`）：

1. **触发点要挂在真正会发生的动作上。** 这个仓库确实有远端（`mine` → `github.com:codezeh/minecraft-ai-agent`），
   CI 并非不可能；但**日常动作是本地 `git commit`**，不是 push。CI 只在 push 后才跑，
   而本次整改是「改完 → 立刻验证」的闭环，等 push 才反馈等于没有反馈。
2. **不需要网络/账号/远端。** 钩子在断网、未 push、甚至没有远端的机器上都照跑。
3. **成本可承受**：preflight ≈ **3.1s**、正则自检 ≈ **0.1s**，每次提交约 3.2s。
4. CI 与钩子不互斥 —— 若以后要接 GitHub Actions，`.githooks/pre-commit` 里命令可原样搬过去。
   （本任务按"二选一"只落地钩子，不新增 `.github/`。）

### 4.1 装法

```bash
cd mindcraft && npm run gate:install     # = git config core.hooksPath .githooks
```

### 4.2 触发验证方式（都实测过）

**A. 证明 git 真的会调用 `core.hooksPath` 里的钩子，且失败会拦住提交**（用一个必定 exit 1 的钩子）：

```
$ git -c core.hooksPath=<临时目录> commit -m "probe"
  [test-hook] 我被触发了                    ← 钩子被执行
$ git rev-list --count HEAD
219                                        ← 提交数没变 = 提交被拦住
```

**B. 证明真钩子在真实提交上触发并放行**（本次提交的原始输出）：

```
$ git commit -F <message>
  [gate] 提交前门禁（SKIP_GATE=1 可跳过）
  ✓ 门禁通过（preflight + 审计正则自检）
    （完整测试请跑：npm test —— preflight + unit_all）
[main c0c98e3] chore(gate): 第11条 三门接线 + 第18条 UNITS 自动发现（T03）
```

### 4.3 为什么留 `SKIP_GATE=1`

三个并行修复任务必然出现"改到一半"的提交（例如刚删掉一个函数、还没改完调用方）。
强行拦截会把中间态提交逼成「习惯性 `--no-verify`」——**绕过变成肌肉记忆，比没有门禁更糟**。
所以留一个**必须显式打出来、且会打印警告**的口子，而不是让人偷偷绕过：

```
$ SKIP_GATE=1 git commit -m "..."
  ⚠ SKIP_GATE=1 —— 本次提交**跳过了门禁**。
    最终提交前请补跑：npm run gate
```

**给队友的话：中间态提交请用 `SKIP_GATE=1`，最终提交前务必跑一次 `npm test`。**

## 五、第18条：手写白名单 → 自动发现

### 5.1 原来错在哪

`tools/unit_all.mjs` 是一张**手写 65 项白名单**。新增离线测试忘了登记 → 那个测试**永远不跑**，
而且**没有任何输出提示它没跑**。"没登记"和"没失败"长得一模一样 —— 又是一次第26条同族问题。
报告实测：`tools/` 下有 13 个纯离线 `test_*.mjs` 从来没进过门禁。

### 5.2 现在的结构

```js
const EXCLUDE = new Map([
    ['test_mca_import', '引用已删除的 chunk_map.js …'],
    ['test_tile_map',   '同上 …'],
    ['test_reconnect',  '需要在线 bot（exit 2）…'],
    ['test_s0_afk',     '同上 …'],
]);
const EXTRA_OFFLINE = ['test_escape', 'test_tunnel', 'test_climb', 'test_codes',
                       'test_collect_targets', 'test_context_trim', 'test_goto_wiring', 'test_terrain3d'];
const NEEDS_REAL_DATA = new Set(['verify_y_semantics', 'test_memory_cap', 'test_nav_opt', 'test_path3d']);
const UNITS = 自动发现(tools/*_unit.mjs) ∪ EXTRA_OFFLINE ∪ NEEDS_REAL_DATA，再减去 EXCLUDE;
```

**发现规则只认 `*_unit.mjs`**，所以新写的单测零登记成本。命名模式覆盖不到的老脚本放 `EXTRA_OFFLINE`。

### 5.3 三道自检（防"静默不跑"复发）

1. 名单里有名字、但**文件不存在** → 当场 `exit 1`（否则 ENOENT 会被误读成"测试红了"）。
2. **一个脚本都没发现** → `exit 1`（发现规则坏了 ≠ 没有测试）。
3. `NEEDS_REAL_DATA` 里的名字**不在名单中** → `exit 1`。

> 第 3 条是补的一个**我自己刚挖的坑**：第一版只把 3 个真机脚本写进 `NEEDS_REAL_DATA`，
> 却没并进 `UNITS` → 它们的表现是「既不跑、也不报跳过」，**正是第18条要消灭的那种静默**。
> 跑第一遍时输出里既没有 `⏭` 也没有它们，才发现。已修 + 加断言，见 §六对账表。

### 5.4 两个配套的最小改动（为什么必须动它们）

| 文件 | 改动 | 为什么必须动 |
| --- | --- | --- |
| `tools/preflight_regex_unit.mjs` | 断言输出 `✓/✗` → 行首 `PASS/FAIL` | 它匹配 `*_unit.mjs` 会被自动发现，但 `unit_all` 按 `^\s*PASS` 数用例，不改就会以 `NO_CASES_RAN` 判红。守仓库既有约定。 |
| `tools/test_codes.mjs` | 去掉宽口径 `code: 'XXX'` 扫描，只扫 `fail('XXX')` | 它是"错误码未注册"的**第二个实现**，且用的是 T02 已裁决为错的口径 → 对 DIED 报红。它的文件头自己写的职责就是「`fail()` 直接 throw」。若不改，纳入后 unit_all 必然红（4 PASS / 1 FAIL）。 |

**关于 `test_codes` 这处改动需要被复核**：这不是"为了让测试变绿而改测试"，而是
① 报告 §S20 已判该口径错；② T02 已在 preflight §3 做了同样的收窄；
③ 改动方向与该文件自身声明的职责一致（只管 `fail()` 实参）。
但它确实降低了一个检查的覆盖面（不再拦 `{ok:false, code:'TYPO'}` 字面量），
**这层覆盖由 preflight §3 的第二条正则承担**（T02 已实现并加了护栏）。若复核认为应保留双份，
把 `test_codes` 移入 `EXCLUDE` 并写明理由即可，一行的事。
