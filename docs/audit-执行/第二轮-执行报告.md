## 5. 【必开节一】报告结论纠错（4 条）

### 纠错 1：第 1 条第三层的定性错了 —— 不是"锁上了也没用"，是"锁从来没锁上"

**报告原文的定性**：「SES 边界挡不住宿主 realm ⇒ 即使 lockdown 生效也逃得掉」，
意即"这层防护在原理上就没用"。

**实测真相**：`src/agent/library/lockdown.js` 里 `export function lockdown()` **遮蔽了 SES 的全局
`lockdown()`**，函数体内那句 `lockdown({...})` 解析回**它自己**；而它自己第一次调用时先把
`lockeddown = true` 置位，于是第二层的 `if (lockeddown) return` 立刻返回 ——
**SES 的 lockdown 一次都没执行过。**

决定性证据（本轮实测，探针 3.5）：
```
调用前  Object.isFrozen(Object.prototype) = false
仓库 lockdown() 之后 = true                    ← 修复后真的冻上了
直接调全局 lockdown → Already locked down       ← 证明这次真的调到了 SES 那一个
```
双模式 A/B（探针 3.4）：同一表达式
```
off  → skills.log.constructor('return process.version')() = "v24.16.0"      ← 本机 RCE
real → THROW TypeError: Function.prototype.constructor is not a valid constructor
```
**结论更正**：报告第三层应改为「**锁从来没锁上（自引用遮蔽 bug）**」，而不是「锁上了也没用」。
这个区别很重要：前者是**可修的代码 bug**（已修），后者会被读成"原理上无解、别白费力气"。

**同时必须写清三条边界**（否则下一个人会把它当"完整沙箱"）：

1. **只覆盖已测向量，不是形式化证明。** 本轮堵的是 6 类（`constructor` 链 / `process` / `require` /
   `fs` / async 函数 / 数组方法）。SES 的对抗面远大于这 6 类，需要一轮**专项对抗复核**才算数。
2. **`evalTaming` 仍是 `unsafeEval`** —— 这是硬依赖，见纠错 2。
3. **同用户进程仍能读 token。** 握手 token 走环境变量 / cookie，同用户的其它进程照样读得到。
   这是**权限模型问题，认证层解决不了**。

### 纠错 2：第 1 条 ④「evalTaming 改回 safeEval」实测不可行

报告建议把 `evalTaming: 'unsafeEval'` 改回 `safeEval` 以彻底关掉 eval。
**实测不行**：protodef 的 `compiler.js:262` 用 `eval(code)()` 生成的编译器依赖**模块局部变量 `native`**，
`safeEval` 的求值环境看不到那个闭包 → `TypeError: Cannot read properties of undefined (reading 'i8')`
→ 协议编不出来 → **bot 连不上服务器**。

**本轮据此按「真关 lockdown」执行**，保留 `unsafeEval`。
**必须写这条**：不写，下轮就会有人照报告字面把 `safeEval` 装回去，然后 bot 静默连不上。
在真 lockdown 下 `unsafeEval` **不再是逃逸通道**（因为 `Function.prototype.constructor` 已被堵死）。

### 纠错 3：第 31 条不是 16 处而是 17 处；且漏了一个真崩溃点

- **17 处**不是 16：`replicate.js` 用 **tab 缩进**，报告那条正则只认空格，扫漏了。
  连同同族共**标记化 24 处**；修完后 `grep` 兜底串 = 0。
- **报告没点出的真缺陷**：`gemini.sendRequest()` **压根没有 try/catch（裸抛）**。
  看着"更诚实"，但 `prompter` 的 `promptCoding` / `promptMemSaving` / `promptShouldRespondToBot`
  **都没有 try/catch** ⇒ gemini 一抛就是 coder / history / conversation **三个调用方真崩**。
  本轮把适配器契约统一成一句：**`sendRequest()` 永不抛** —— 成功给内容、失败给 `FAILED_REPLY` 标记。
- **故意不动**：`'Vision is only supported by certain models.'`（7 个适配器）是**能力说明**，
  不是伪装成模型的故障台词 —— 玩家看到它是有用信息。

### 纠错 4：第 27 条预期「棘轮缩到 5」不成立，实测 12

报告说"剔掉 9 条死条目后棘轮自动缩到 5"。**实测是 12**，因为还有 **7 处被掩盖的真实新增**
（详见 §6 偏离③与 §7 未修项①）。也就是说：报告只发现了"死条目占名额"，
没发现"新违规正在占用腾出来的名额"。

## 7. 【必开节三】验证手段自身不可信（本轮四次 + 两个亲历教训）

这一节是本轮最有价值的部分：**四次"看起来验了"其实是"没验"**。

### 7.1 正则永不匹配（第26条 0x08）
`preflight.mjs:183` 两个正则各带一个 **0x08 退格字节**前缀 → 要求"字面退格"才匹配 → 永不命中 →
`used2` 恒空 → 恒打印「✓ 错误码审计通过」。**这道门从上线起没检过任何东西。**
**防法**：① 打 ✓ 前断言 `used2.size > 0`（0 命中 = 扫描器坏了）；② 自检脚本必须**从生产源码抽真身**
（不抄副本）且**能对修复前版本变红** —— `preflight_regex_unit.mjs` 对 HEAD 版本 3 项全红，对修复后 33/33。

### 7.2 命令不存在（`-f compact`）
ESLint 9 已把 `-f compact` 移出核心 → 命令直接失败 → 输出为空 → `grep -c` 数出 **0**，
看起来像"零问题"。**防法**：验证命令要先断言自己真跑出了东西 ——本报告 §1.2 里
`files scanned: 167` 那一行就是为此加的；且一律用 `--format json` 自己聚合，不用会漂的 formatter。

### 7.3 夹具形状造假（`atom_classify` 的 `{pos:{}}`）
单测夹具喂了真实代码根本不会收到的形状（`{pos: {}}`），于是测试测的是"夹具能跑"，
而不是"生产路径对"。**防法**：夹具只调**真实写入函数**并断言**端到端性质**
（写进去 → 从另一条路径读出来是什么）。

### 7.4 身份比对只在总数超标时才跑（第27条 audit_rules）
```js
if (violations.length > base.count) { /* 才比对身份 */ }
```
死条目把 `base.count` 撑到 14，实际违规 12 → **12 < 14，身份比对根本不执行** →
死条目腾出的 9 个名额被 7 处真实新增悄悄占掉一个月。**两个错误互相掩护**：
死条目制造缓冲，门槛让缓冲不被检查。
**防法**：① 每条登记项 `existsSync(file)` 断言；② **身份比对无条件执行**（不再依赖总数）。

### 7.5 亲历教训一：复核 NATURAL_BLOCKS 时**两次都抓错了位置**（captain 自陈）
第一次命中的是**注释里的**同名文本，第二次正则写错。**第三次才拿到真身。**
说明「看起来验了」与「真验了」只差**一次对输出的审视**——抓到之后要问"我抓到的这段，是代码还是注释？"

### 7.6 亲历教训二：验收样例本身不合格会骗过验收（本轮 T05 亲历）
我第一次验收 §3 剥注释时，注入的假码写成 `'T05_PROBE'` —— **带数字**，
而捕获组是 `([A-Z_]+)` **不允许数字**。于是"注释里的假码"和"真代码里的假码"**两个方向都没报错**，
差点把"修复失效"误判成"已修好"。换成纯大写 `FAKE_REAL_CODE` 后两方向都正确。
**这个坑在验收方，比在被测方更隐蔽**：被测方错了会红，验收方错了只会给你一个安心的假绿。

### 7.7 两条工程纪律（本轮踩出来的）

- **证据脚本必须落在 `tools/` 并纳入版本控制。** T32 报第 32 条时引用的 `tmp/t32/heartbeat_demo.mjs`
  因 `tmp/` 被 gitignore 而**消失、无法复跑**（所幸结论已落进 `tools/heartbeat_loop_unit.mjs` 7/7 含失败反证）。
  **一个不能复跑的证据不是证据。**
- **负向验证副本不得放 `src/`。** skills 的 `_t14_neg_*.js` 曾被 preflight 当"新源文件"扫出 **9 处红**
  （5 处裸常量 + 条数上涨 + 2 条新模块未申报），而双方代码都没错。应放 `tmp/` 且**用完即删**。

### 7.8 总结这条母题
本轮**五次**撞上同一个形状：**"检查没跑"和"检查通过"长得一模一样**。
- 0x08 正则永不匹配 → 0 命中打 ✓
- 门禁无触发点 → 等于没配
- `-f compact` 命令挂掉 → grep 数出 0
- 死条目 + 总数门槛 → 身份比对不执行
- 探针盯作废文档 → 永远"不变"

**通用防法只有一句**：任何"通过"都要能自证"我确实检查了 N 个东西"，且 N>0 本身要能被伪造检测
（即断言"扫到的数量 > 0"）。
