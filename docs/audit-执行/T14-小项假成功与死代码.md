## 一、逐条：改前 → 改后 + 证据

### S37 `collectHazardsCached` 死代码
- **改前**：全树只有定义处 1 命中（`grep -rc` = 1）。`isSafeHere` 直接调 `wmCollectHazards` ⇒ 缓存永不填、`resetHazardCache()` 空转、每次重枚举（半径 64 约 183ms）。
- **改后**：`isSafeHere` 改走 `collectHazardsCached(bot,{radius:8})`。判据看 **blobs 里落在 8 格内的块**（不是 `fresh`）——命中缓存时 `fresh=0`，按 fresh 数会把"记得的岩浆"报成安全。
- **证据**（数 `bot.findBlocks` 调用次数，连续两次 `isSafeHere`）：

```
修复后： findBlocks 调用 1 次   → PASS 第二次命中缓存
修复前： findBlocks 调用 2 次   → FAIL（每次重枚举）
```
另测 `resetHazardCache()` 真的生效：`两次 isSafeHere 枚举 1 次；resetHazardCache() 之后再跑一次 → 共 2 次` → PASS。

### S38 四个 `goTo*` / `moveAwayFromEntity` 恒 `return true`
- **改前**：忽略被调函数的返回值，永远报成功，失败点被推到下一步。
- **改后**：`goToNearestBlock` / `goToNearestEntity` → `return await goToPosition(...)`；`moveAwayFromEntity` → 返回 `gotoWithTimeout` 的布尔（失败时打 `FAILED`）；`goToPosition` / `goToPlayer` 的 cheat-`tp` 分支也检查 `command()` 的 `ok`（原来白名单拦下也报"传送了"）。
- **证据**（goto 桩永远 reject）：

```
修复后： goToNearestEntity 返回 false / moveAwayFromEntity 返回 false / goToNearestBlock 返回 false
修复前： 三者全部 返回 true        ← 走不到也报成功
```

### S39 `tillAndSow` 在 cheat + `seedType=null` 抛 TypeError
- **改前**：`seedType.endsWith(...)` 无条件执行 ⇒ 按 JSDoc 默认用法（"Defaults to none, which will only till the ground"）调用必抛 `TypeError: Cannot read properties of null (reading 'endsWith')`。
- **改后**：`null` 只耕地不播种（与 JSDoc 承诺一致），并显式记录"nothing planted"。
- **证据**：

```
修复后： tillAndSow(bot,0,63,0) 不抛，返回 true
修复前： 抛了 TypeError: Cannot read properties of null (reading 'endsWith')
```

### S40 `storeItem` / `stashUnneeded` 意图即成功
- **改前**：`storedTotal += put`（`put` 是**打算**放多少）；`stashUnneeded` 更是**先** `stashed.push` 再 `deposit`，失败也记账，且恒 `{ok:true}`。
- **改后**：两者都按**背包前后差值**记账（`countInventoryItem` 前后对比），没真挪走就不算；`stashUnneeded` 的 `ok` = `stashed.length > 0`；`storeItem` 失败分支也带 `stored: 0`（数字总是可读）。
- **证据**（`deposit()` 静默不挪任何东西）：

```
修复后： {"ok":false,"stored":0,"remaining":10,"reason":"nothing_moved"}
修复前： {"ok":true,"stored":10,"remaining":0}    ← 一件都没挪走却报存了 10 个
```

### S41 `digDown` 读不到方块报成功
- **改前**：`bot.blockAt(...).position` 无空值保护（区块未加载直接 `TypeError`）；且 `!targetBlock || !belowBlock` 时统一报"reached the end of the world"并 `return true`。
- **改后**：入口先判空并如实失败；循环内区分**真的到世界底部（y < -64，按原语义返回 true）**与**仅区块未加载（如实反回 false）**。
- **证据**（`blockAt` 全返回 null）：

```
修复后： 返回 false（不抛 TypeError）
修复前： 抛 TypeError: Cannot read properties of null (reading 'position')
```

### S42 `buildStorageRoom` 判据过弱 + `fillRoomWithChests` 硬编码 `+4`
- **改前**：`ok = floorN > 0 && wallN > 0 && ceilN > 0` —— 1 块地板 + 1 块墙 + 1 块顶就算"房间建好"；探针位置写死 `x0+4, z0+4`（绑死 `innerSize=7`）。
- **改后**：按期望值判定 —— 地板/天花板 `OUT×OUT`、墙 `(4·OUT−4)×innerHeight − 4`（扣 2×2 门洞），容差 10%，返回值新增 `expected` 便于对账；探针改为 `probeMid = Math.floor(OUT/2)`。
- **证据**（夹具：每层只放行第一块 ⇒ 恰好 1 地板 + 1 墙 + 1 顶）：

```
修复后： ok=false  floor=1/81  walls=3/92  ceiling=1/81   （带 expected）
修复前： ok=true   floor=1     walls=3     ceiling=1       ← 「三块零件」= 房间建好
```

## 四、给下游 / 行为变化须知

1. **S38/S41 从"恒 true"变"如实失败"**：`goToNearestBlock` / `goToNearestEntity` /
   `moveAwayFromEntity` / `digDown` 现在会返回 `false`。依赖"它们永远成功"的上层
   会把失败当失败处理 —— 这正是修这条的目的，但**下游若原本靠返回值恒真来推进**，需要改成按返回值分支。
2. **`digDown` 的两种 false 含义**：区块未加载（可重试）vs 挖不动（`FAILED` 已写明原因）；
   **到世界底部仍返回 true**（保留原语义，不制造新失败）。
3. **`storeItem` 的失败分支新增 `stored: 0`**、`reason` 细分为 `nothing_moved` / `chests_full`；
   上游若按 `reason === 'chests_full'` 分支，需要兼容 `nothing_moved`。
4. **`stashUnneeded` 的 `ok` 现在是 `stashed.length > 0`**：以前恒 true，`prepareForBuilding`
   等调用方若把 `ok` 当作"开箱成功"，语义收紧了。
5. **`buildStorageRoom` 更严格**：`.expect` 判据带 10% 容差；若某次建造把"已经是目标方块"记为
   `exists` 不计入 `placed`，90% 容差可吸收，但**极端缺料会返回 ok:false**（以前会 ok:true）。
6. **`readLitematic` 会抛新错**：`MAX_SCAN_VOXELS = 2_000_000` 上限；region 数据与包围盒不符；
   全程无非空气方块。`describeSchematic` 等调用方需要接住（它们本来就在 try/catch 里读文件错误）。
7. **`isSafeHere` 现在会写 `store.hazards`**（借用 collectHazardsCached 的记忆），
   即"安全检查"会顺带更新危险记忆 —— 这是 S37 带来的附带收益，也让 `!forgetHazards` 真正生效。
