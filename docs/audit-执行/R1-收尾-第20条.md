## 2. 同源证明：引用的都是原子侧的函数/常量，没有第二个数字

### 2.1 `isSafeHere` → `query_safe.hostilesNear`（本次在 query_safe 里抽出来的唯一实现）

`query_safe.js` 新增导出 `hostilesNear(bot, pos, { radius=12, nameLimit=3 })`，`isSafe` 自己的敌对生物段也改成调它：

```js
// query_safe.js（isSafe 内）
const hostileHit = hostilesNear(bot, pos, { radius: hostileRadius });
const hostiles = hostileHit.count;
```

```js
// skills.js（isSafeHere 内，替换掉 world.getNearestEntityWhere(...) → hostiles = 1）
let hostiles = 0;
const hostileHit = hostilesNear(bot, pos, { radius: 12 });
hostiles = hostileHit.count;
```

于是"认哪些名字（`HOSTILE` 集合）、半径多大（12）、怎么数（全数）"只有**一处**。分叉的根不是重复代码，而是旧实现拿 `getNearestEntityWhere` 只有一只就 `hostiles = 1`。

### 2.2 `canReach` → `query_perceive.reachDistanceTo` + `rules.runtime.digReach()`

```js
export function canReach(bot, pos, max = digReach()) {
    if (!pos) return false;
    return atomReachDistanceTo(bot, pos) <= max;
}
```

- 距离：`query_perceive.reachDistanceTo`（原子层的眼到方块中心，本次连 `reachDistanceTo`/`eyePosition` 也改成委托它 / `atom_read.eyePosition`）。
- 阈值：`rules.runtime.digReach()` → `game_rules.json.derived.dig_reach_usable = 5.1`，挂在已验证规则 **R3-01** 上（"Paper 服务端实测 6.10 格仍成功，取保守 5.1"）。**这是 5.1 的唯一出处**，`skills.js` 不再自带数字。

为什么用"只看距离"这条原子判据、不加视线检查：调用方是挖前预检（`collectBlock` 挑 `mustCollectManually` 的方块）。`act_dig.js` 里有实测记录——目标原木前挡一层树叶时 `world.raycast` 命中树叶，但 `bot.dig` 照样挖掉；加视线检查会把整片丛林树误判成"够不着"。所以 `query_perceive.canReach`（距离+视线，给右键交互用）不适合这里，这里对齐的是 `act_dig.digBlock` 的那条判据。

### 2.3 `waitUntil` → `atom_wait.waitUntil`

```js
const r = await atomWaitUntil(predicate, { timeoutMs, intervalMs, bot });
```

判据、轮询间隔、中断语义、谓词抛错的分类全部由原子层决定；`skills.js` 只负责把返回值翻译回本文件的历史形状。

## 3. `waitUntil` 的调用方普查（先查清，再动）

`grep -rn "waitUntil" src tools` 的结果里，**本文件内部调用只有两处**（报告 13.3 提到的 `wait:300` 是旧快照，`skills.wait` 现在是纯 sleep 循环，不用 `waitUntil`）：

| 调用方 | 改前谓词 | 改后谓词 | 为什么 |
|---|---|---|---|
| `waitForSmelt` | `() => !!furnace.outputItem()` | `() => !!furnace.outputItem() \|\| undefined` | 没出产物时返回 `undefined`（继续等），出了返回 `true`（完成） |
| `giveToPlayer` | `() => given` | `() => given \|\| undefined` | 没收到时 `undefined`（继续等），收到 `true`（完成）；`if (got && got.ok)` 未改（第22条） |

外部语义依赖只有一处：`tools/skills_property_guard_unit.mjs` 用 `waitUntil(bot, () => false, {timeoutMs:30})` 验证第22条"超时也返回真值对象"。`false` 在新语义下**立刻完成**，所以把该用例的谓词改成 `() => undefined`（"永远等不到"的正确写法），**断言本身一字未改**（仍是"超时 ⇒ 对象真值 + `ok:false`"）。这是修复语义而不是放宽测试：旧写法在新语义下测的已经不是"超时"了。

### 契约（写清，避免下一个人再猜）

```
skills.waitUntil(bot, predicate, { timeoutMs=5000, intervalMs=250, label })
  谓词返回 undefined / null            → 还没好，继续等
  谓词返回其它任何值（含 false/0/''）   → 完成，立即返回，value = 那个返回值
返回 { ok, waitedMs, reason, label, value }
  reason ∈ met | timeout | interrupted | error（谓词抛错）
```

与原子层的唯一差异是**形状**（原子返回 `ActionResult`），不是判据。两处行为细节的诚实交代：

1. 旧实现有"超时边界再查一次"（`reason:'met_late'`）。原子层没有这一步，本次统一掉 —— 在 `timeoutMs` 那一刻刚好满足的条件会报 `timeout`。全仓只有这一处产出过 `met_late`，无消费方。
2. 旧实现 `timeoutMs` 传 `NaN` 会静默转成"立刻超时"，现在由原子层报 `INTERNAL`（非法参数不再被当成"等过了"）。

## 4. 为什么 `isSafeHere` **不**整体转发给 `query_safe.isSafe`

先说结论：**敌对生物判据已经同源（§2.1），但整函数没有合并，这是有意的**。

`isSafeHere` 的地形危险走 `collectHazardsCached`：TTL 3s 缓存 + `store` 里 `hazards` 记忆的合并（`world_model.mergeHazardBlobs`），于是"上次扫到、这次没扫到"的危险仍在，`!forgetHazards` → `resetHazardCache()` 才有意义。这正是 **S37** 修过的东西（`tools/skills_fakesuccess_unit.mjs` 用"两次 `isSafeHere` 只调 1 次 `findBlocks`"盯着它）。

而 `query_safe.isSafe` 是**故意**不用这份枚举的（它自己的注释写明 `heatmap.collectHazards` 有两个不适合当安全判据的问题：丢了方块名、`findBlocks` 圆心固定在 bot 身上）。它用目标点做圆心重新 `findBlocks`。

所以整体转发会同时造成两件事：

1. `collectHazardsCached` / `resetHazardCache` 重新变成死代码 —— 把 S37 的修复原地回退，并且 `!forgetHazards` 再次空转；
2. 丢掉"历史危险记忆"这一层覆盖：原子层只看当前 `findBlocks` 半径 8 的枚举。

实测确认了这一点：改造后 `S37 连续两次 isSafeHere 只枚举一次` 仍然 **PASS**（`findBlocks 调用 1 次`）。若整体转发，该用例会变成 2 次（已推演，未施工）。

因此"同源"落在**判据**上：敌对生物 → 同一个 `hostilesNear`；危险/液体两条本来就与原子层同规则（先查记忆 → 采样 ±4 步长 2 → 半径 8 枚举），不是分叉。这也与第 13.2 节"不要为了合并而合并"的取向一致。

# 附：第33条 —— `goToGoal` 可中断性补测试（t4，同一轮 R1 收尾）

> 任务：t4（T4）· 依据：`docs/audit/17-review-r1-verdict.md` §9 第 4 项「第 33 条修好了但**零测试**」
> 终审原话：`grep goToGoal tools/*_unit.mjs` = **0** ——「这条一旦回退没人看得见」。

## A1. 这条为什么不是"补个测试"那么简单

第 33 条的缺陷是：`goToGoal` 只有两支 —— `pathfinder.goto()` 自己 + **180 秒硬超时**，全程没人看 `bot.interrupt_code`。所以玩家按 `!stop` 之后，她**最长还要走 3 分钟**才动一下。

修复（提交 `00bcf2e`，T21）加的是第三支：一个每 200ms 查一次 `interrupt_code` 的 `setInterval`，命中就 `pathfinder.stop()` 并 reject 一个 `code='INTERRUPTED'` 的错。

要害在于**这个缺陷极易被"绿"骗过去**：断言"最终返回了"会同时接受两种世界 ——
- 真的停下来（~200ms，`INTERRUPTED`）；
- **靠 180s 超时兜底才返回**（3 分钟，`Error: exceeded 180s hard limit`）。

后者正是缺陷本身。所以本测试的判据必须钉死三件事：**多快**返回、**什么码**、**谁叫停的**。

## A2. 用例与判据（`tools/goToGoal_interrupt_unit.mjs`，7 个用例）

桩 bot 风格与现有 `tools/*_unit.mjs` 一致（不联网、不启动服务器）。`import` 走 `SKILLS_MODULE` 环境变量（沿用 `skills_fakesuccess_unit.mjs` 的约定），这样同一份测试能对"改前代码副本"跑一遍做反向验证。

| # | 用例 | 判据（为什么这么写） |
|---|---|---|
| 1 | 没中断时正常返回 `true` | 守卫不许把正常走路掐了；同时断言**没有**"goto 还在跑时被 stop" |
| 2 | 置 `interrupt_code`（30ms 后，模拟走一半按 !stop）⇒ `code='INTERRUPTED'` | 码不对就说明是超时支或别的东西在兜底 |
| 3 | 用时 << 180s，且错误里没有 `hard limit` | 直接排除"靠超时伪装成中断" |
| 4 | `pathfinder.stop()` 是在 **goto 还没 settle** 时被调的 | 关键的去混淆：`withNav` 收尾**也会** `stop()`，按调用次数数会误判；按"调用时 goto 是否仍在进行"才分得清 |
| 5 | `useDoor`：`isMoving()` 恒 true | 没有 `&& !bot.interrupt_code` 就是**死循环**，用看门狗把"卡死"如实报成失败 |
| 6 | `goToBed`：`isSleeping` 恒 true | 同上（这条对应"按 !stop 之后照样睡到天亮"） |
| 7 | 结构断言：三处守卫 + `GOTO_HARD_LIMIT_MS = 180000` 都在源码里 | 防止"守卫被删但用例恰好还能过" |

关于看门狗：这两个 `while` 循环回退后**永远不会退出**，没有看门狗的话门禁会挂 180s 甚至跑不完。所以用例用 `withWatchdog`，卡死时输出的是"看门狗 5s 到了还没返回（goto 从未 settle ⇒ 没有中断支）"——**卡死就说卡死，不假装成断言值不对**。

## A3. 当前绿（逐字输出）
