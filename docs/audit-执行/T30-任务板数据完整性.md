## 1. 第 3 条：`openBoard` 把"任何异常"都当坏库（会删好库）

**病根**：`tryOpen()` 抛什么都进 rebuild 分支 → 原文件 `rename`/`rm` → 建空库。
最刺眼的一种组合：**另一个进程持 `BEGIN EXCLUSIVE`** → 这边拿到 `SQLITE_BUSY(5)`
→ 被当成"文件坏了" → **好库被改名，工单全丢**，日志还写"库损坏已重建空库"。

**改法**：`isCorruptError(e)` 只认 `errcode ∈ {11 SQLITE_CORRUPT, 26 SQLITE_NOTADB}`
或 message 含 `file is not a database` / `malformed`；**其余一律原样 throw**。
另把 `mindserver.js` 的失败日志改成说得清事实的一句：
`[任务板] 板起不来（库文件原样保留，未改名/未删除），按"没有板"继续：…`

### ★ 关键证据（验收要求的那条：另一进程 `BEGIN EXCLUSIVE` 持锁 10 秒）

命令（临时目录 `tmp/t30/`，锁脚本 + 探针脚本）：

```
node -e "…openBoard('tmp/t30/boardlock'); addJob(两张)…"          # 预置 2 张工单
node tmp/t30/lock_hold.mjs "…\tmp/t30\boardlock\board.sqlite" &    # 另一个进程：BEGIN EXCLUSIVE，10 秒
node tmp/t30/lock_probe.mjs "…\tmp/t30\boardlock"                  # 锁期间开板
```

输出（原样）：

```
预置工单数 = 2
--- 起锁进程（另一个进程持 EXCLUSIVE 10 秒）---
[locker] 已持 EXCLUSIVE 锁，10 秒后释放
--- 主进程在锁期间开板 ---
[任务板] 板起不来（库文件原样保留，未改名/未删除），按"没有板"继续：database is locked
--- 裁决 ---
抛错 = database is locked  (errcode=5)
库文件仍在 = true  字节 45056 → 45056（未改名/未删除 ⇒ 不变）
.corrupt- 备份数 = 0（必须是 0）
PROBE_EXIT=0
[locker] 释放锁并退出
```

锁释放后再开板：`rebuilt = false，工单数 = 2，工单标题 = 真实工单,第二张`
→ **可恢复的问题不再变成"数据丢失"**。
（探针脚本里先断言了 `mindserver.js` 确实含那句日志文案，不是我另编一句。）

同样的场景在**单测里也有一个确定性版本**（同进程第二个连接持锁，等 `busy_timeout` 5.5 秒）：
`board_open_migrate_unit` ⑤ —— `等了 5562ms 报「database is locked」 备份=0 行数=1`。

## 2. 第 24 条：加一列不再等于"坏库重建"

`CREATE TABLE IF NOT EXISTS` **不给已存在的表补列** → 以前只有"删库重建"一条路。
新增 `PRAGMA user_version` + `migrateBoardSchema()`：读 `PRAGMA table_info` → `ALTER TABLE ADD COLUMN` → 写回版本。

★ 列清单**从 `SCHEMA` 建表语句里抽**（`jobColumnDefs()`），不另写第二份 —— 两份清单必然漂移，
这正是本仓反复出现的"两个地方都以为自己在管同一件事"。

★ **踩到并修掉的顺序坑**：`SCHEMA` 里除建表还有
`CREATE INDEX … ON jobs(state, priority, createdAt)` —— 老库缺 `priority` 时索引语句先炸
（`no such column: priority`），"补列"永远等不到机会。
现在顺序是 **① 补列 → ② 建表（IF NOT EXISTS）→ ③ 建索引**。

证据（`board_open_migrate_unit` ②）：

```
PASS ★ ② 老库缺列 → 自动补列、rebuilt=false、两张老单原样还在 补列=17 列数=26 行数=2 备份=0
PASS ③ 幂等：第二次打开不再补列，user_version=2，行数不变 added=[] uv=2
PASS ③-b 迁移后的库可正常下单（dependsOn 列可用）
```

造库方式：手工建一张只有 9 列的"老版本" `jobs` 表 + 灌 2 行，然后 `openBoard()`。
**没有一处靠"删库重建"让测试变绿** —— 两条老单（`老单甲/ready`、`老单乙/done`）迁移后原样还在。

## 3. 第 25 条：记忆文件损坏 → 先留证，再降级

`memory_store.readStore` 的 catch 原来只 warn 一句就返回默认值、**不备份**；
而 `updateStore` 的"读→改→整份重写"会把原文件**永久覆盖**。
现在：读不出来 → 先把原文件改名 `<ns>.json.corrupt-<时间戳>` → 告警（点名备份路径）→ 返回默认值。
做法与 `board_store` 的 `.corrupt-` 对齐。

证据（`memory_store_corrupt_unit`，6/6）：坏 JSON → 备份内容**一字不差**；
留证后再写，新数据独立成文、备份仍在；好文件不产生备份；文件不存在不留空备份；
端到端 `updateStore` 在损坏后仍"先留证再落盘"。
空文件走 `raw.trim()` 早返回、**不备份**（没有可抢救内容）—— 这条按实记录，是有意的边界，不是漏测。

## 4. 第 4 条：`finish()` 不看人 —— 旧持有者能改写别人的单

`WHERE id=?` → `WHERE id=? AND (lease_owner IS NULL OR lease_owner = ?)`；
`changes === 0` → `{ok:false, code:'LEASE_STALE'}`，**一个字段都不写**。
`board_server.js` 传 `payload.bot`，`board_client.js` 的 `finish()` 带上 `bot: this.name`。

判据落在 `UPDATE` 的 `changes` 上（不是只靠前面那次 `getJob` 的读快照）—— 两次调用之间可能被接手，
那正是"先 SELECT 再 UPDATE"老坑的 finish 版本。

证据（`board_store_finish_unit` ④，19/19）：

```
PASS ★ ④ 单子已转给 B 后，A 的 finish 必须失败且一个字都不改 code=LEASE_STALE state=claimed attempts=0 lease_owner=B
PASS ④-b 正向对照：租约持有者本人的 finish 照常生效
PASS ④-c 不传 bot（老调用方）→ 不做归属校验，照常写入
PASS ④-d 无租约（过期后无人接手）→ 允许收尾（LEASE_STALE 只管"别人持有"）
```

### 两处需要你复核的语义选择
1. **`opts.bot` 不传 → 不做归属校验（保持旧行为）**。理由：`finish()` 目前只有 `board_server` 一个调用方，
   但它同时被 8 个测试和离线工具按老签名调用；硬要求 bot 会让"没有身份"的调用方全部被拒。
   代价是"忘了传 bot = 少了这道闸"，所以 server/client 两侧都显式传并加了注释。
2. **`lease_owner IS NULL` 时允许写入**（④-d）—— 这正是报告给的字面判据。
   语义上说得通：`heartbeat` 要求"必须持有"（要停手），而 `finish` 是**收尾**，
   不该因为"刚过期 1 秒、还没人接手"就把真实结果丢掉。**如果你要的是严格"必须持有"，
   这条要改成 `AND lease_owner = ?` 且 ④-d 翻成期望失败 —— 请裁决。**
3. 测试里"转手给 B"是用 `updateJob({lease:{owner:'B'}})` 模拟的，因为
   `claimFor()` 会同时写 `assignee`，所以"另一个 bot 再领一次"这条路走不通 ——
   **那是另一条独立缺陷（`expireLeases` 不回滚 assignee，导致单只能原主再领）**，
   不属本条范围，我没动它，记在这里供第二批安排。

## 5. 第 5 条：依赖死了的单永久卡 ready、父单永久 running（现场 166 分钟）

新增 `depDead(db, job)`：任一依赖 ∈ `failed/blocked/cancelled` 即真。
新增 `markDepDeadBlocked()`（落 `blocked` + `result.code='DEP_DEAD'`，并把 `deps` 写进 result）
与兜底扫描 `sweepDeadDepJobs()`（挂 `scanTimer`）。
另外在 `reopenOrphanBlocked` / `reopenBlockedWithSatisfiedDeps` 里**先判死再谈重开**，
在 `convergeOrphanParents` 里**先把"依赖已死"的子单落 blocked 再 rollup 父单**。

`tools/board_store_converge_unit.mjs` 的 XFAIL ②-6 已转成**硬断言**（12/12）：

```
PASS ★ ②-6 依赖已死 → 兜底扫落 blocked + result.code=DEP_DEAD（留痕，不再静默）
PASS ②-6-b 幂等：再扫一次不重复写（已记账的不再动）
PASS ②-6-c 正向对照：依赖 running（还活着）→ 不判死，后继仍 ready 且无痕
```

★ **`dependsOn` 指向库里不存在的 id 不算死**（`depDead` 只看真实存在且是终态三态的行）。
理由：那多半是跨库/尚未落库的中间态，判死会把本来能恢复的单提前废掉；宁可等，不要误杀。
现有用例 ②-1（前置不存在 → 仍 ready）保持绿，即这条选择的证明。

## 6. 第 15 条：租约过期不记 attempt → 崩溃无限重试

`expireLeases` 的 UPDATE 现在带 `attempts = attempts + 1`；
`attempts >= maxAttempts` → `failed` + `result.code='LEASE_EXPIRED'`；
没耗尽 → 回 `ready` 且**不动 result/checkpoint**（保留上次结果给下一个接手的）。

证据（`board_lease_expire_unit`，7/7）：

```
PASS ★ ① 租约过期一次 → attempts 0→1、回 ready、租约清空
PASS ★ ② 连崩到 maxAttempts(3) → failed + result.code=LEASE_EXPIRED（不再无限重试） trail=ready/1 → ready/2 → failed/3
PASS ③ 未耗尽 → result/checkpoint 原样保留（只加 attempt，不洗数据）
PASS ④ 幂等：已经回收过的单再扫不会再加 attempt
PASS ⑤ 租约未过期 → 不动（attempts 仍 0）
PASS ⑥ 边界 maxAttempts=1 → 第一次过期即 failed（不会多跑一轮）
PASS ⑦ 结果码字面值与线上一致（具名常量没改对外字符串）
```

② 的 trail 就是"无限重试"被关掉的直接证据：**第 3 次崩就收敛，没有第 4 次**。

## 7. 第 17 条：幽灵父单（拆单中途崩溃 → 永久 running 且无子单）

新增 `blockOrphanParents(db, opts)`，挂 `board_server` 的 `scanTimer`：
命中 → `blocked` + `result.code='ORPHAN_PARENT'`（面板上"显形"，而不是永远"正在跑"）。

### ★★ 两处**必要的收窄**（相对报告字面写法，**请复核**）

报告写的是「`running`/`ready` 且无子单且 `createdAt < now-120000`」。照字面实现会是灾难：

1. **「`ready` 且无子单」正是队列里每一张还没人领的普通单** —— 上线 2 分钟后**整个待办队列会被一口气全部 block**。
   → 收窄为**只认 `skill` 为空**的单。壳单（`splitByCount`/`splitByArea` 建的父单，`skill:null`）
   在库里**根本无法自己执行**，没有子单就等于永远不会前进 —— 这才是"幽灵"的准确刻画，
   也正是"拆单两步之间崩了"的确切形态。
2. **只认租约已过期/无租约**。租约还活着 = 有人正在跑它，这时候判"幽灵"等于杀掉正在干活的单。

证据（`board_orphan_parent_unit` 23/23，含两条**误伤防线**）：

```
PASS ⑪ 幽灵父单（壳单无子单+无人持有）→ blocked + result.code=ORPHAN_PARENT
PASS ⑫ 壳单**有子单** → 不碰（正常等子单的父单，归 convergeOrphanParents）
PASS ⑬ ★误伤防线：ready+有 skill 的老待办单 → 不动（照字面实现会把整条队列废掉）
PASS ⑭ ★误伤防线：壳单但租约活着（有人正在跑）→ 不动
PASS ⑮ 未过 2 分钟阈值 → 不动（在建子单的窗口）
PASS ⑯ 幂等：第二轮不再重复写
PASS ⑰ board_server 仍在调用 blockOrphanParents（第17条兜底没被摘掉）
PASS ⑰-b 反向验证：内存里摘掉该调用 → 守卫报红（⑰ 会红）
```

**如果你的本意就是"连 ready 也扫"**，那需要另一个判据（比如给壳单打 `kind:'shell'` 标记），
请裁决 —— 我不会在没有区分指标的情况下按字面开这个开关。

## 8. 第 14 条：`LIMIT 200` 把新单挤出调度器视野

`listJobs` 加 `openOnly`（`state NOT IN ('done','failed','cancelled')` **放进 SQL**）；
`board_server` 的 `scope='claimable'` 一律 `openOnly:true`；`board_client.refresh` 对
`scope==='claimable'` 一律带 `openOnly:true`（`board_scheduler` 那两处 `refresh({scope:'claimable'})` 因此自动生效）。

证据（`board_openonly_unit`，6/6）——**先复现病根，再证明修好**：

```
PASS ★ ① 复现病根：不带 openOnly 时窗口被 200 张 done 占满，新单看不见 返回=200 新单可见=false
PASS ★ ② 带 openOnly → 新单进得了视野，且结果集里没有任何终态单 返回=1 新单可见=true
PASS ③ openOnly 判据：done/failed/cancelled 排除，ready/blocked/paused/pending 保留
PASS ④ openOnly 与 states 叠加生效（都在 SQL 里）
PASS ⑤ 接线：client 的 refresh(claimable) 必带 openOnly，server 侧也把它并进 listJobs
PASS ⑤-b 反向验证：内存里摘掉 payload.openOnly → 守卫报红
```

③ 特意保留 `blocked/paused/pending`：残局回收正要看 `blocked`，把它们一起排掉就是另一个 bug。
