# T4 · 取消与截止贯穿（operationId + deadline + AbortSignal）

> 出处：审计 `docs/audit-r4/A5-model-result-cancel.md` §5「方案 B」。
> 一句话：**一次动作 = 一次 operation**，它带唯一 `operationId`、一个 `deadline`、一个 `AbortSignal`；
> 这三样从动作槽一路传到 fetch/SDK，取消与超期都能真的中断请求，而**迟到的结果一律不得落地**。

---

## 1. 关键设计

### 1.1 唯一创建点

`src/agent/action_manager.js` → `ActionManager._newOperation(timeout)`，**全仓只此一处**：

```js
{ id: `${name}:${++this._opSeq}`,           // 操作身份（单调递增）
  deadline: timeout > 0 ? Date.now() + timeout*60_000 : null,
  ac: new AbortController() }               // 唯一取消源
```

创建时机：在 `_executeAction` 里**认领动作槽之后、`executing = true` 之前**（这一段没有 `await`，
所以"一个动作只有一个 op"是可断言的）。`agent.currentOperation` 同步挂一份，供 prompter 消费。

不变量：
- `agent.js` 不造 op、不造 `AbortController`（单测 ⑥ 静态钉住）。
- **停止不造新 op**：`stop()` 走 `_abortCurrentOperation()` —— abort **同一个** op 并把它退休，
  槽位置空。所以 `!stop` / 面板停止 / 超时 / 被取代 取消的是同一个 operationId（单测 ④）。
- 动作正常收尾走 `_retireOperation()`：清槽位但**不 abort**（这次是成功结束），
  与此同时旧 opId 再也匹配不上 `currentOperation`。

### 1.2 四跳下传（全部是"加一个可选参数"）

| 跳 | 位置 | 传的是什么 |
|---|---|---|
| 1 | `action_manager._executeAction` → `agent.currentOperation` | `{id, deadline, ac}` |
| 2 | `agent.handleMessage` → `promptConvoResult(history, opts)` | `{signal: op.ac.signal, deadline: op.deadline, operationId: op.id}` |
| 3 | `prompter._callOptions()` → `sendRequest(turns, sys, stop_seq, callOpts)` | `{signal, timeoutMs, operationId}` |
| 4 | 适配器 → `fetchWithDeadline(..., { signal })` / SDK `{signal, timeout}` | 同一个 `AbortSignal` 实例 |

**`_callOptions` 是唯一的折算点**：`timeoutMs = min(LLM_MAX_CALL_MS, deadline - now)`（下限 1000ms）。
这就是把"两套时钟"并成一套 —— 动作还剩 8 秒时，模型调用只有 8 秒，而不是 120 秒。
`LLM_MAX_CALL_MS = 120000` 与 `callDeadlineSignal()` 都是 **t1 已建的**，这里只复用，没有新建超时机制。

### 1.3 迟到结果：三重不得

判据 `isOperationCurrent(opId)`（`action_manager`，与板侧 `attemptSeq` 代次判据同构）：

```
① currentOperation.id === opId     （旧动作的 id 永远对不上）
② op.ac.signal.aborted !== true    （stop() 之后即使槽位还没清，也已经不算数）
```

- **prompter 侧**：请求返回后若 `signal.aborted`，把结果标成 `status=cancelled`、
  `content=''`、后挂 `operationId`（`ModelResult` 不认未知构造字段，故构造后赋值）。
- **agent 侧**：`status === CANCELLED` → `break`（不写 history、不进聊天）；
  且在**写 history / 打"她说了什么"日志之前**再查一次 `isOperationCurrent(op.id)`。
- **租约侧**：`agent.finishOperation(op, jobId)` 是唯一的"完成这张单"入口，
  op 已过期则直接丢弃并返回 `false`（否则旧操作会在单子 paused/released 之后又 finish 掉，
  别人永远拿不到 —— A5 §5.3 末）。板侧停止语义复用 board-core 已实现的
  `_leaseDropped` / `LEASE_LOST`，本任务不另造 code。

### 1.4 与 `!stop`（t3）的关系

两者互补、不重复：

| 场景 | 判据 | 谁负责 |
|---|---|---|
| 纯对话回合（没有动作在跑） | `cancelEpoch` 快照（t3） | t3 |
| 动作里（有 operation） | `operationId` + `signal.aborted`（t4） | t4 |

t3 的 `checkInterrupt` 已纳入 `interrupt_code`；t4 的 opId 判据处理的是
"操作已换人/已退休"这种**跨动作**的迟到，比"标志位"更耐久。

## 5. 残留风险

- `_abortCurrentOperation` 在 `stop()` 一开始就 abort：如果某次 `stop('brief')` 只是"换个动作"
  而当前 op 的模型请求还没回来，那次请求会被中断 —— 这是**有意的**（停止就是取消），
  但意味着"反射 mode 抢占"也会打断在飞的模型调用。若将来发现误伤，可把 brief 档排除
  （一行：`if (r !== STOP_REASONS.BRIEF) this._abortCurrentOperation(r)`）。
- op 的 `deadline` 只是**数据**，没有任何人主动在 deadline 到点时 abort ——
  真正的到期中断靠 ① `_callOptions` 反算的 `timeoutMs`（适配器/fetch 执行）与
  ② 动作总超时 `_startTimeout → stop(TIMEOUT)`（abort）。这两条都在，但都不是"定时 abort 这个 op"。
