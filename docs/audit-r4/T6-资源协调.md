## 1) deriveClaims 补四类

原来只推导 `block:`（collect/mine/dig + 坐标）与 `container:`（store/fetch + pos）。
现在按 07 的四张表补齐，全部**只从单里已有字段推**：

| 类 | 触发 | 依据字段 |
|---|---|---|
| `station:` | smelt/smeltItem → `furnace`；craft/craftRecipe → `crafting_table` | `args.furnace/station/bench` 或通用坐标 |
| `area:` | 建造/整片挖掘 | `args.area{x,y,z,r}` 或 `args.center + args.radius` |
| `entity:` | attack/trade/fight | `args.entity/entityId/uuid`，或 `args.target` 是**字符串** |
| `item:` | 材料额度 | `args.materials` / `args.material+count` / `args.cost` |

**推不出来就不推**：熔炉没坐标、只有产物名（`args.item`）、没有目标 —— 一律返回空。
猜坐标比不预约更糟：预约了一个跟真实目标对不上的 key，等于给了"已经协调好了"的假安心。
真实目标由第 2 条的执行期补占位解决。

## 2) 执行期二次预约（`reserveNow`）

- `composite_registry.makeCtx` 提供 **`ctx.reserveNow(key)`** 单一实现；
  同一份函数还挂到 `bot.__reserveNow`（沿用本仓既有的 `bot.__navJobId` / `bot.board` 约定），
  给**拿不到 ctx 的动作层**用。
- 动作层接线：`act_container.openContainer` 开窗时按真实方块补 `container:x,y,z`；
  `act_craft.furnaceLoad` 开炉时补 `station:furnace@x,y,z`。
  **冲突（CLAIM_CONFLICT）当场返回**，不静默继续 —— 上层据此换目标（与 `OCCUPIED` 同处置）。
- 补占到的 key 记在 `ctx` 的 `runtimeClaims` 上，`ctx.releaseRuntimeClaims()` 一次放干净；
  调度器 `_runJob` 的 finally **会调**它 —— 否则这些 key 只能等 30 秒 TTL，期间别人拿不到。
- ★ **分层**：`act_*` **不 import 任何 board 模块**（第一版违反了这条，已按队长要求改成注入）：
  只从 `opts.reserveNow ?? bot.__reserveNow` 取回调，取不到就 warn 一次并跳过（单机照常工作）。

## 3) 租约归属校验（renewClaims / release / finish）

| 函数 | 原来 | 现在 |
|---|---|---|
| `renewClaims` | `UPDATE claims SET until=? WHERE id=?` —— **任何知道 jobId 的 bot 都能替别人续** | 校验 state（只 claimed/running）+ owner（`lease_owner`）；UPDATE 只命中 `owner IS NULL OR owner=?`；返回 `{ok,code,renewed}`，失败 `LEASE_STALE` |
| `release` | 只按 `claims.owner` 过滤，**不看这张单归谁** | 单的租约在别人手上且未过期 → `LEASE_STALE`，**一条预约都不删** |
| `finish` | 只有租约归属，**不看状态** | 加状态白名单（ready/claimed/running/paused）；`pending/blocked/终态` → `LEASE_STALE` 且**一个字段都不写**（`{anyState:true}` 可显式放宽） |

`changes===0` → `LEASE_STALE`（不写任何字段）是三条共同的收口；`renewClaims` 从"返回数字"
改成形状化结果，因为数字 0 分不清"没预约"与"不归我"。

★ 兼容：`claims` 表可以有**还没有任务单行**的预约（离线工具/夹具直接 `reserve(db,'jobA',…)`），
查不到单行时退回旧行为（只按 owner 过滤），不让纯预约层用例全红。

## 4) noBoard 不再 fail-open

`composite_registry.reserve/release/reserveNow` 无板时原来是 `ok:true, noBoard:true`
—— 调用方以为占位成功，其实 `claims` 表 0 行（真机事故：85 张单 done、claims 0 行）。
现在：**`ok:false, code:'NO_BOARD', data.noBoard:true` + 一行 warn（进程内一次）**。
无单时 `reserveNow` 返回 `NO_JOB`（没有 `claims.id` 可归属，不能假装占上）。

## 5) 队长加派：`applyStop` 的 `patch.lease`

**结论：这条已经在 store 侧修好了，我选"把 `lease` 对象映射到 `lease_owner/lease_until`"。**
`board_store.updateJob` 在处理 PATCHABLE 白名单**之前**就单独接了 `k === 'lease'`
（HEAD 已存在），所以 `planStop(PLAYER)` 的 `patch.lease=null` 会真的清租约。
实测：`state=paused, lease={owner:null, until:null}`。
我没有改 `control.js`，而是**加了一条守卫用例 ③-f 把它锁死**，防止以后有人"顺手"把这段映射删掉。

## 边界

- `reserveNow` 只在"有 jobId"时才有归属；直接命令调用（`!do xxx`）没有预约归属，
  返回 `NO_JOB` 并 warn —— 这类调用天然无法跨 bot 协调（没有单可挂），不是本条能解决的。
- `flows` 里 `openContainer`/`furnaceLoad` 的调用点没有显式传 `opts.reserveNow`，
  靠的是 `bot.__reserveNow`（makeCtx 挂的）。若某个 flow 走的是"没有 makeCtx"的路径，
  动作层会 warn 一次并跳过占位 —— 行为与改之前一致（不阻断），只是日志里能看见。
