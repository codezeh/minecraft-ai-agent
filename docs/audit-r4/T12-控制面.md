# T12 控制面缺陷批（S1#3/#4/#5、S2#9/#10/#12、S3#20）

改动只落在三处：`mindcraft/src/mindcraft/mindserver.js`、`mindcraft/src/mindcraft/mindcraft.js`、
`mindcraft/src/process/agent_process.js`。新增离线用例：`mindcraft/tools/control_plane_guard_unit.mjs`（65 条）。

## 1) S1#3 双开（面板双击 = 同一个 bot 两个进程）

原缺陷：`forceRestart()` 用 `process.killed` 判断"还没停"；`killed === true` 只表示**信号发过了**，
进程可能还在 ⇒ 走 else 分支直接 spawn。且并发两次调用各自 `once('exit')`，一次退出触发两次 spawn。

修法（三层，缺一不可）：
- `AgentProcess.start()`：`running && process` 时**拒绝**并返回 `false`。`running` 只在子进程真退出
  （`_onChildExit`）或 spawn 失败（`'error'`）时才落回 false。
- `AgentProcess.forceRestart()` 改 async：`_restarting` 并发闸（第二次返回 `in-progress`）；
  旧进程一律 `stopAndWait()`；**未确认退出就绝不 spawn**（返回 `{started:false, exited:false}`）。
- 子进程"代号" `_gen`：`exit`/`error` 带代号回来，对不上就丢弃（旧进程迟到的 exit 不许把新进程状态打成没在跑）。
- `mindcraft.createAgent()`：同名 agent 的进程仍活着时拒绝再建（"删失败后重建"也是双开）。
- `mindserver`：`start-agent` 加来源限流 6 次/60s，并 `await` 结果，失败时回 `start-agent-failed`。

## 2) S1#4 孤儿（忽略 SIGINT 的进程仍持租约领单，而控制面再也管不到）

原缺陷：`destroyAgent` fire-and-forget `stop()` 后立刻 `delete agent_processes[name]`。

修法：`destroyAgent` 改 async，走 `stopAndWait()`（SIGINT → grace → SIGKILL → 再等）；
`!r.exited` 时**保留注册表条目**并返回 `{ok:false, reason}`。`mindserver` 的 `destroy-agent`
`await` 它，失败就**不删** `agent_connections`，回 `destroy-agent-failed`（面板可见），注册项保留可重试。
`createAgent` 失败路径同样 `await destroyAgent`。

## 3) S1#5 类型校验 + 顶层兜底（畸形事件打挂整个控制面）

- 新增 `validateSettingsShape(settings)`（导出，纯函数）：settings 必须是对象、`profile` 必须是对象、
  `profile.name` 必须是非空字符串；否则**入口即拒**并给出可读原因 —— 原来 `key in settings` 对
  `null`/字符串/数组直接抛 TypeError，而处理器是 async ⇒ 未处理拒绝 ⇒ Node 22 默认退出进程。
- `create-agent` 的 ack 全部走 `ack()` 包装：客户端不带 ack 时裸 `callback(...)` 抛 TypeError
  （同一条崩溃路径）。`await mindcraft.createAgent` 也包了 try/catch。
- 新增 `installCrashGuards()`（`createMindServer` 首行调用，按进程幂等）：
  `unhandledRejection` / `uncaughtException` 打完整栈并**继续运行**；
  `MINDSERVER_EXIT_ON_UNCAUGHT=1` 可恢复"崩了就退"的严格语义。诚实边界：这是网，不是修根因。

## 4) S2#9 身份校验 + 通道唯一占用

新增 `isAgentIdentity(socket)`（agent 进程带 `auth.token`；面板只有 cookie）与
`claimAgentChannel(conn, socket, {...})`（纯裁决）：
- 非 agent 身份 ⇒ `identity-required`（面板不能把自己绑成 agent 通道）；
- 同一 socket 重复声明 ⇒ `rebind`（幂等，`connect-agent-process` 之后紧跟 `login-agent` 走这条）；
- 换连接 ⇒ 允许接管（agent 重启/瞬断重连是常态，硬拒会把 bot 锁在门外），但
  **30s 内最多 3 次**，超了 `channel-busy` —— "两个同名进程互相踢"不再无声循环；
- 旧连接已断开 ⇒ `takeover-stale`，不计入限速。
接管时给被顶掉的连接 `agent-channel-taken-over` 并断开，日志点名新旧 socket。
`disconnect` 只在"自己仍是持有者"时清绑定（旧连接迟到的事件不许抹掉新主人）。
`bot-output`/`agent-event` 复用同一判据（原来是三份重复的内联实现）。

## 5) S2#10 `listen-to-agents` 幂等

- `addListener`：已在集合里 ⇒ 直接返回 false（原来重复 push ⇒ 同一 socket 收两份 `state-update`）。
- `registerMapRelay`：`WeakSet` 保证每个 socket 只注册一次（`socket.on` 是追加语义，重复注册会让
  一次 request-map 变成 N 次 `agent.socket.emit`）。
- `removeListener`：`indexOf === -1` 时直接返回 false（原来 `splice(-1,1)` 会删掉**最后一个**监听者）；
  集合归零才 `stopStatePolling()` —— 轮询真的会停。
- handler 先做幂等检查再限流（重复订阅不消耗令牌）。导出 `isStatePolling()` 供断言。

## 6) S3#20 `get-profiles` 绝对路径

`dir: profilesDir` → `dir: path.basename(profilesDir)`（F-WEB-204 同类第 4 处；`path` 字段早已是 basename）。
面板仍显示一个 harmless 的目录名提示。

## 7) 顺手（同文件 S2#12）

spawn `'error'` 时把 `running` 落回 false：原来永远停在 true ⇒ start/stop/forceRestart 都以为还在跑，
而 `exit` 也不会来 ⇒ 永久卡死。`stop()` 也不再在 `process` 为空时抛 TypeError，改为如实返回结果。

# 追加：停手契约（先摘租约、再退出）——t5 交回的遗留线索

## 缺陷

`BoardScheduler.stop()`（`_releaseOnStop()` 主动放租约+预约）与 `BoardClient.stop()`（心跳不再续租）
**实现完整但零生产调用方**。于是进程退出 / 面板 stop / destroy-agent / 关服四条路上，租约都挂到
30 秒自然过期为止，别的 bot 这段时间拿不到单。

## 关键约束：scheduler / boardClient 只活在**子进程**

父进程（mindserver/mindcraft）里没有调度器 —— 所以"先摘租约"只能由**子进程在死之前**做完；
父进程能保证的是**顺序**：先 SIGINT、等 `graceMs`、才 SIGKILL。

## 接在哪（`src/process/init_agent.js`，子进程，4 处汇成一条 `gracefulStop()`）

1. `SIGINT`（面板 stop / destroy-agent / 关服 / forceRestart 都发它）
2. `SIGTERM`
3. `agent.cleanKill()` 包装（被踢 / 断线超时 / 缺玩家 —— 它直接 `process.exit`，绕过信号）
4. 原有"孤儿自杀"路径保持不变（父进程被 SIGKILL 时的唯一兜底）

`gracefulStop()` 的顺序**写死在同一个函数里**，因此不可能被调用方搞反：

① `board.setAutoClaim(false)` → ② `scheduler.stop('preempt')` → ③ `boardClient.stop('preempt')`
→ ④ `board.update(id, {state:'ready', lease_owner:null, lease_until:null, assignee:null})`（单回共享池）
→ ⑤ `board.release(id)`（放预约）→ ⑥ `board.socket.disconnect()` → ⑦ `process.exit(0)`

## 为什么是 `update(...)` 而不是 `releaseLease()`

`expireLeases()` 只回收 `lease_until IS NOT NULL` 的单。只清租约（`releaseLease`）会把 lease 清成
NULL 而状态还留在 `claimed` ⇒ **再也回收不到**（比等 30 秒过期更糟：永久僵尸单）。
而 `claimFor` 的候选条件是 `assignee IS NULL OR assignee = 我`，不清 `assignee` 别人同样抢不到这张单。
所以一次性写 `state:'ready' + lease_* + assignee = null`（四个字段都在 store 的 `PATCHABLE` 白名单里，
`claimed/running → ready` 也在 `TRANSITIONS` 里）。**没有改 board_store / control**（这点由 board-core 的 t6 负责）。

## 顺序是怎么保证的（两层，都可断言）

- 子进程侧：`gracefulStop()` 内部 ①~⑦ 顺序执行，④⑤ `await` 到底才走到 ⑦；
  测试 F3 断言 `update < release < disconnect < exit` 的源码位次。
- 父进程侧：`stopChildAndWait()` 里 `kill('SIGINT')` 在 `kill('SIGKILL')` 之前，中间等 `graceMs`（5s）；
  子进程正常 50ms 就退，**SIGKILL 根本用不上** ⇒ 正常路径上"摘"一定发生在"杀"之前。
- 诚实残余：子进程**卡死**（既不响应信号也不退）时，父进程 5s 后 SIGKILL，租约无人能摘，
  只能等 30 秒过期。此时 destroy-agent 会**保留注册项并回 `destroy-agent-failed`**（不假装成功）。
