# T13 玩家身份：一次性绑定码（第四轮审计 ①，方案 C）

## 缺陷

`permissions.js` 的等级只由**游戏名字符串**与 profile 名单比对；离线服务器
（`online-mode=false`）不校验名字 ⇒ **改个客户端名就是 owner**。控制面的 token 认证
完全不传导到游戏内权限；`agent/` 下 `.uuid` 零命中。

## 链路

```
面板（已过 token 门） --identity-issue-code--> mindserver 造码，写 bots/<agent>/identity-codes.json
        ↑                                              │
        │ 5 分钟内把码给人                              ↓
   玩家在游戏里发  !claim ABCD-EFGH  --> agent 子进程核销（单次） --> 写 bots/<agent>/identity.json
        ↑                                                              │
        └──────────── 之后 resolveLevel 按绑定表定级（uuid 优先）──────┘
```

## 三条硬约束（`identity_store.js` 里实现，不在调用方自觉）

1. **短时**：`code_ttl_ms` 上限硬夹到 **5 分钟**（传 1 小时也只给 5 分钟）。
2. **单次**：核销即从表里删除（"已用过"不留记录，第二次直接失败）。
3. **绑面板会话**：码上记 `socket.id`；该 socket 断开 ⇒ 它签发的**未核销码全部作废**。
   另外"同一个面板会话只留最新一个码"（连点两次生成 ⇒ 旧码立刻失效）。

## 定级（`resolveLevel`）

顺序：`internal` → **绑定表** → 空 author → 别的 bot → （`legacy_profile_names` ? 按名字 : **guest**）

- 绑定表命中 ⇒ 用记录里的等级（`boundAt` / `expiresAt` 都校验，过期即**不命中**）。
- **uuid 优先**；名字回退**只认"当初就没拿到 uuid 的绑定"**。
  → 主人绑了 uuid+name，冒名者改名叫 `Zeh`（uuid 不同）**拿不到 owner**（这是本条的核心理由）。
- 绑定启用且未开 legacy ⇒ 名字不再产生任何权限，一律 guest（`LEVEL.OTHER`）。

## !claim（`commands/identity.js`）

`!claim` 在 `OPEN_COMMANDS` 里：`canRunCommand` 对它**不看等级**（否则"还没身份的人"
没法拿到身份，先有鸡还是先有蛋）。失败不改任何状态，且三种原因**可区分**：
没有码 / 无效或已用过 / 写盘失败。

## 面板入口（t24 补齐，这条链路原本是断的）

**位置**：控制台 → 左侧栏 → `StatusCard` 下方 → **「玩家身份」** 区块 → **「生成绑定码」** 按钮。

> ★ 为什么单独写一节：t13/t20 把服务端做完了，但 `web/src` 里对 identity/绑定/claim 的引用是 **0** ——
> `identity-issue-code` 全仓**零调用方**，面板上也没有按钮。结果玩家永远拿不到码 ⇒ `!claim` 永远失败
> ⇒ owner 永远不可达（叠加 t20 的 `offline_owner_mode=deny` 默认 = 彻底锁死）。
> 单测当时全绿是因为它**自己造码**（直接 `addCode`），掩盖了这条断链。t24 把它接上并加了端到端证据。

点「生成绑定码」之后，面板显示码 + **剩余秒数**，并给出三条提示（缺一条都会让人误判这套机制）：

1. 在游戏里输入 `!claim <码>`（大小写、连字符都无所谓）；
2. **5 分钟**内有效、**只能用一次**；这个面板连接一断，未用的码立刻作废；
3. **离线服提醒**：码只能证明「此刻你能拿到这个面板」，**不能**证明游戏里那个同名的人是本人
   （离线服 uuid 由名字派生，同名即可冒充）；要真正防冒名，请开正版验证或装登录插件（如 AuthMe）。

同一区块还显示**已绑定的人**（等级 / 是否弱绑定 / 是否过期），每行有「解绑」按钮（立刻生效，无需重启）。
`identity-status` / `identity-unbind` 也因此有了真实调用方。

### 服务端的准入

三个身份事件（`identity-issue-code` / `identity-status` / `identity-unbind`）**只允许面板连接**：
带 `auth.token` 的 agent 通道会被拒（`panel_only`）—— 否则 agent 进程能给自己造一个升 owner 的码。

### 端到端证据（`node tools/identity_e2e_probe.mjs`，12/12）

真 mindserver + 真 socket.io 客户端（不是单测自己造码）：

```
PASS ① 面板 emit identity-issue-code ⇒ 拿到码 {"ok":true,"code":"JEFE-HPYA","expiresAt":…,"ttlMs":300000}
PASS ①-b 回执带 expiresAt，且 TTL ≤ 5 分钟
PASS ①-c 码真的落在 bots/<agent>/identity-codes.json 上
PASS ①-d 码绑定到当前面板会话（socket.id）
PASS ①-e !claim 用真码成功
PASS ①-f ★ 端到端闭环：面板发的码 ⇒ 游戏内 !claim ⇒ 等级 owner
PASS ①-g 同名但 uuid 不同的冒名者仍 guest
PASS ⑤ 同一个码第二次使用失败
PASS ② 不带 token ⇒ 握手被拒（AUTH_REQUIRED）
PASS ③ agent 身份连接 ⇒ 被拒 panel_only
PASS ④ 过期码 !claim 失败
12/12 个端到端断言通过
```

## 升级影响（重要）

身份绑定**默认开启**（`identity_binding.enabled: true`）。这意味着：

- **升级后老用户的第一条命令会被拒**，直到他拿码绑定。这是**有意的 fail-closed**，不是故障。
- 提示在两处，都可照做：
  1. **玩家被拒时**：`permissionDeniedReply` 在绑定模式下追加
     「要拿权限：在面板上点「生成绑定码」，然后在游戏里发 `!claim <那个码>`。」
  2. **mindserver 启动时**（仅当"一台都没绑定过"）：打印三段说明 —— 名字不再生效、
     怎么取码、以及怎么退回老行为。
- 过渡操作：
  1. 面板选中 agent → 点「生成绑定码」→ 5 分钟内把码告诉玩家；
  2. 玩家游戏里 `!claim ABCD-EFGH` → 回「绑定成功：你现在的等级是 owner」；
  3. 想撤销：面板「解绑」（写 `identity.json`），**立刻生效**，无需重启。
- 逃生门：profile 里
  `"permissions": { "owner": "Zeh", "identity": { "legacy_profile_names": true } }`
  ⇒ 退回"按名字给权限"。**开它等于放弃防冒名**（离线服务器上改客户端名即可冒充），
  只建议在"临时救急/单人自己玩"时用。
- 完全关掉这套机制：`identity_binding.enabled: false`（= 审计前的行为）。

## ★★★ 离线模式的根本限制（t20 补充，务必先读）

**t13 单独不能解决冒名。** 本仓 `server.properties` 是 `online-mode=false`，而离线模式下
服务端发给玩家的 uuid 是**由名字 MD5 派生**的
（`node_modules/minecraft-protocol/src/datatypes/uuid.js`: `javaUUID('OfflinePlayer:' + name)`）：

```
HEAVENZEH    -> 3f680b9f-53a9-34c1-900a-6ba8f0262175
Impostor     -> 18cca982-c228-3975-9cb1-45bcfa87adc5
HEAVENZEH(2) -> 3f680b9f-53a9-34c1-900a-6ba8f0262175   ← 同名必然同 uuid
```

于是 t13 的链路在离线服上被绕过：

1. 主人 `!claim <码>` → 绑定 `{uuid: 3f680b9f…, name:'HEAVENZEH', level:'owner'}`；
2. 冒名者把客户端名改成 `HEAVENZEH`（或 `HEAVENZEH(2)`，取决于服务端去重）→ 服务端发**同一个 uuid**；
3. `resolveBinding` 按 uuid **精确命中** → 直接 owner。

注意：这不是"名字回退"那条路（那条只认无 uuid 的绑定），所以 t13 里那条防护**在这里不起作用**。

### t20 的处置（识别 + 降级 + 说清楚，不是"修好了"）

| 环节 | 行为 |
|---|---|
| 识别 | `isOfflineDerivedUuid(uuid, name)` 按 `OfflinePlayer:<name>` 重算并比较（忽略大小写/格式）；命中的绑定 `weak: true` |
| 降级 | `identity_binding.offline_owner_mode`：**`deny`（默认）** ⇒ weak 绑定在离线服上**永不授 owner**；`session` ⇒ 仅在刚 `!claim` 后的 `offline_session_minutes`（默认 60）内授 owner（内存态、不落盘、重启即失效） |
| 说清楚 | ① `!claim` 的弱绑定回执**不报"绑定成功"**，而是明说"服务端 uuid 由名字派生、同名者拿到同一 uuid、它不能证明你是你"；② 被拒话术给"离线服无法证明你是你 + 两条根治路径"，**不假装成功**；③ mindserver 启动时若 `online-mode=false` 且绑定启用，打印一次警告（含当前策略与两条根治路径） |

### 离线模式下 owner 的最终可达性（结论）

- `offline_owner_mode = 'deny'`（默认）：**离线服上 owner 不可达**。任何玩家（含真主人）都只到
  guest/chat 这一档；要拿 owner 必须开正版验证或装登录插件。
- `offline_owner_mode = 'session'`：**owner 可达但限时** —— 只有"刚用面板发的码 `!claim` 过"的
  `N` 分钟内有效，其余时间回到 guest。它把冒名窗口从"永久"压到"最多 N 分钟且需要先拿到码"，
  但**仍然不是身份证明**（冒名者可以在那 N 分钟里顶着同名进来）。
- 结论一句话：**离线服 + 无登录插件时，"按身份授权"只能防君子**。真正的修复是部署决策：
  `online-mode=true`（正版验证）或登录插件（AuthMe 等）。代码不会替用户改 `server.properties`。

## 诚实边界

绑定码与绑定表都是**明文落盘**（`bots/<agent>/identity*.json`）。能读这个文件的人可以先自己核销
（= 冒充主人）。本机制解决的是**"游戏里改个名就冒充"这个方向上的一半**（正版 uuid 时有效），
不是**本机提权** —— 后者与 token 门同级（见 OPS-003 / F-RT-001）。
名字在"没拿到 uuid"的绑定里仍是不稳定身份，回执里会明确警告（且这类绑定一律按 weak 处理）。

## 验收

`node tools/identity_binding_unit.mjs` → 46/46，其中 B 段就是任务点名的四条：
冒名者无码→guest、持码→owner、码过期→guest、解绑→guest（外加"同名不同 uuid 仍 guest"）。
t20 追加 4 条反向用例（E 段）：① 同名同 uuid（离线派生）⇒ weak；② weak + deny ⇒ guest；
③ weak + session + 刚核销 ⇒ owner（过窗口回 guest）；④ 正版 uuid ⇒ 强绑定、照常 owner。
另含"冒名者用主人的名字 + 离线 uuid 在 deny 下仍 guest"（队长的复现路径）与
"弱绑定不许报绑定成功"。

`permissions_unit`（77）与 `bot001_identity_unit`（79）已按新契约更新：
名字映射类用例显式走 `legacy_profile_names: true`（它们钉的就是那条回退路），
新契约四条 + 反向冒名用例写在 10b 段。
