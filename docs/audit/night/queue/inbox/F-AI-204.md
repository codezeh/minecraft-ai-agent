evidence: |
  **面板创建的 agent，模型可见工具面从 8 条膨胀到 70 条（设计意图的 8.75 倍）。**
  这条是 F-GATE-001（`companion_mode` 未在 settings_spec 声明）的**安全后果**，我用真实导入实测了数字。

  ## 一、机制：companion_mode 决定"模型能看见几条命令"
  `src/agent/commands/index.js:11-33`：
  ```js
  export const COMPANION_COMMANDS = [
      '!collectBlocks','!followPlayer','!goToPlayer','!placeHere',
      '!buildPlatform','!map','!stay','!stop',
  ];                                    // ← 注意：数组里有 8 条
  export function isVisibleToModel(commandName) {
      if (!settings.companion_mode) return true;      // ← 键缺失 = 全放行
      return COMPANION_COMMANDS.includes(commandName);
  }
  ```
  `getCommandDocs()`（`:367-374`）用它决定写进系统提示的命令清单。
  而 `commands/index.js:4 import settings from '../settings.js'` 拿的是
  **`src/agent/settings.js` —— 一个初始为空的对象**：
  ```js
  // src/agent/settings.js 全文
  let settings = {};
  export default settings;
  export function setSettings(new_settings) { /* 清空后 Object.assign */ }
  ```
  ⇒ `settings.companion_mode` 是否为真，**完全取决于运行期注入进来的那份 settings 里有没有这个键**。

  ## 二、两条注入路径，一条带键、一条不带
  - **路径 A（`main.js` 直接启动）**：`main.js:2 import settings from './settings.js'`（根 settings.js，
    第 12 行 `"companion_mode": true`）→ `Mindcraft.createAgent(settings)` → `registerAgent` →
    子进程 `get-settings` 拿到完整对象 → `setSettings(...)` ⇒ **有键，白名单生效**。
  - **路径 B（面板创建 agent）**：`mindserver.js:291 socket.on('create-agent', async (settings, callback)` ——
    `settings` 是**前端发来的对象**，直接 `mindcraft.createAgent(settings)`（`:323`）。
    前端能构造哪些字段由 `src/mindcraft/public/settings_spec.json` 决定，而
    **该文件里没有 `companion_mode`** ⇒ 面板根本发不出这个键 ⇒ `isVisibleToModel` 第一行就 `return true`。

  ## 三、实测（真实导入，非读代码推断）
  ```
  $ node -e '…import commands/index.js + setSettings…'
  命令总数: 70
  A) main.js 启动（根 settings.js，companion_mode=true）→ 模型可见: 8
  B) 面板 create-agent（settings_spec 默认值，无 companion_mode）→ 模型可见: 70
  settings_spec 含 companion_mode: false
  ```
  对照佐证：`settings.js:12` 有 `"companion_mode": true`；
  `grep companion_mode src/mindcraft/public/settings_spec.json` → **无命中**；
  `SAFE_RUNTIME_SETTINGS`（auth_gate.js:139 附近）里也没有它
  ⇒ 面板既不能读、也不能写这个键，`set-agent-settings` 的 `{...agent.settings, ...safe}` 只能"保住"原有值，
  **从面板创建的 agent 从一开始就没有它**。

  ## 四、可见面扩大 = 攻击面扩大（不是"只是文档多几条"）
  命令**能不能执行**由 `permissions.js` 按发言人等级判（那层是好的），但：
  1. **模型只有在"看得见"的命令里才会挑**。设计意图（`commands/index.js:13-19` 的注释）说得很清楚：
     60 条命令让模型"绕开专用命令自己去试错"，所以要收敛到 7 条。
     现在它同时看见 70 条，等于把设计者刻意隐藏的高层动作重新交给模型选。
  2. 对 F-AI-201 **注入后果放大**：注入者不需要指定"用哪条命令"，只需描述意图，
     模型就会从 70 条里自选（`!digDown`/`!collectBlocks`/`!buildPlatform`/`!survey`/`!takeFromChest`…），
     命中率与破坏力都比只有 8 条时高得多。
  3. 与 F-AI-202 叠加：`!goal` 也在可见清单里，注入者可以引导模型自己给自己设目标。
exploitability: |
  攻击者：能在面板上点"创建 agent"的人（本机使用者），或者任何能触发 `create-agent` 的 socket 客户端
  （需 token —— 但 `speak` 那条已证明运行期改配置这个面是活的）。
  严格说这不是"远程未授权"，而是**配置漂移造成的默认失效**：用户以为自己在用"陪玩模式 8 条命令"，
  实际上从面板建出来的 agent 是 70 条全开。
  能达成什么：模型可被引导去调用设计上不该给它看的高层命令（采集/建造/挖穿/存取/地图侦察全套），
  使 F-AI-201 的提示注入后果从"8 条确定性动作"扩大到"70 条动作里自选"。
  拿不到什么：主人级 10 条（那层闸在 `canRunCommand`，与可见性无关）。
  影响半径：注入的可利用性 × 破坏面。
  诚实定级：medium（本身不是洞，是"安全开关默认失效"，但它显著放大 D4 其他两条）。
suggested_fix: |
  1. **把 `companion_mode` 补进 `src/mindcraft/public/settings_spec.json`**（布尔、default true），
     这样面板创建的 agent 也会带上它；同时把它加入 `auth_gate.js` 的 `SAFE_RUNTIME_SETTINGS`
     （它是"收敛工具面"的开关，允许运行期调整是安全的，方向是变窄）。
  2. **改判断方向为「默认拒绝」**（防将来再漏一个键 —— 这条比 1 更重要）：
     ```js
     export function isVisibleToModel(commandName) {
         // 只有显式开成 false 才全放行；键缺失按"陪玩模式"处理，即默认收敛
         if (settings.companion_mode === false) return true;
         return COMPANION_COMMANDS.includes(commandName);
     }
     ```
     这样"键忘了声明"的后果是**工具面变窄**（功能不灵但安全），而不是变宽（安全失效但功能正常）——
     与 `permissions.js:100` 的原则一致（"没登记的命令按主人级处理，默认拒绝"）。
  3. **在 `tools/settings_check.mjs` 里加一条断言**：`settings.js` 里每个键都必须出现在
     `settings_spec.json` 中（这条正好能自动抓住 F-GATE-001 与它以后的所有同类）。
  4. 若用户确实想全开：让面板显式提供该开关并把默认值写清，别靠"键不存在"这种隐式行为。
