evidence: |
  **F-SEC-205 的 token 文件在 Windows 上的实际 ACL 是这样的：同一台机器的其他本地账户
  既能读、还能改。** `mode 0600` 在 NTFS 上是空操作 —— 我实测了。

  ## 一、实测：`mode: 0o600` 在 Windows 上被忽略
  ```
  $ node -e "fs.writeFileSync('.tmp_probe/acl-probe.txt','x',{mode:0o600}); console.log(stat.mode & 0o777)"
  写入完成 mode: 666 == FS_WRITE_MODE (0o666)      ← 传了 0600，落地是 666
  ```
  然后看真正的判决者（NTFS ACL）：
  ```
  $ icacls .tmp_probe\acl-probe.txt
  .tmp_probe\acl-probe.txt S-1-4-48068235-...:(I)(W,D,DC)
                           BUILTIN\Administrators:(I)(F)
                           NT AUTHORITY\SYSTEM:(I)(F)
                           NT AUTHORITY\Authenticated Users:(I)(M)     ← 所有已认证用户：可改
                           BUILTIN\Users:(I)(RX)                        ← 所有本地用户：可读+执行
                           Mandatory Label\Low Mandatory Level:(I)(NW)
  ```
  三条要紧的：
  - **`NT AUTHORITY\Authenticated Users:(I)(M)`** = 任何已登录/已认证的账户对该文件有 **Modify**（读+写+删）；
  - **`BUILTIN\Users:(I)(RX)`** = 本机任意用户**可读**；
  - `(I)` = inherited，意思是这个权限不是文件自己设的，是**从父目录继承**来的 ⇒ 用户换一个目录也照样继承，
    `mode: 0o600` 一次都没能改变它。

  ## 二、公平地说：这个 caveat 已经有人写对了（76ee07b）
  patch-smith 在本任务开始前已经更正过表述，代码注释现在写着：
  > `// 注意：mode 0600 只在 POSIX 生效，**Windows/NTFS 上不保证只有本机用户可读**`
  > `// （那边由 NTFS ACL 决定）。所以这层不是权限边界，它的目的是"别再进日志"。`

  **所以我报的不是"把 0600 当权限边界"这个错误论断**（那已经修了）。我报的是它后面那半句没人做的事：
  既然已经承认"Windows 上不保证只有本机用户可读"，**那么"同一台机器的其他账户能不能拿它"这个
  问题就没有任何缓解**，也没有被量化。我现在把量化结果给出来：**能读，还能改。**

  ## 三、这条实际能造成什么（把边界说清）
  前置条件：**同一台 Windows 机器上还有第二个本地/域账户**（多用户共用、家人共用、或机器上有
  低权限服务账户/沙箱账户）。如果这是单用户独占机器，本条风险≈0 —— 这一点必须写清，不夸大。

  有第二个账户时，攻击者能拿到什么：
  1. **读** `.mindserver-token` → 拿到完整 token → 直接连 socket.io →
     用 `send-message` 指挥 bot、`set-agent-settings` 改运行期配置、`server-stop`/`shutdown` 关服。
     即 **agent 与服务端的完全控制**（`auth_gate` 之后的所有事件）。
  2. **改**（Modify 权限）→ 把 token 文件内容换成自己的值 →
     `start-panel.ps1` 下次会读到这个假 token 并拼进面板 URL ⇒ 面板打不开（握手被拒）。
     纯 DoS，但**现象是"面板时好时坏"，极难排查**（因为没人会怀疑一个隐藏文件被改过）。
  3. **删**（Modify 含 D）→ `start-panel.ps1` 走 `Test-Path` 的 else 分支，打印 WARN 后打开**不带 token** 的
     面板 URL ⇒ socket 被拒 ⇒ 面板空白。同样是难排查的"时好时坏"。

  ## 四、与"改前"的比较（别让这条被读成"修复没价值"）
  改前：token 打在 stdout → 被 `start-panel.ps1:189` 重定向进 `logs/mindcraft-console.log`
  ⇒ **日志是会被打包发给别人看的东西**，泄漏面远超本机。
  改后：token 只在 `mindcraft/.mindserver-token`（本机文件）
  ⇒ 泄漏面收窄到"本机其他账户"，**这是实打实的改进**。本条是"没改完"，不是"改错了"。
exploitability: |
  攻击者：同一台机器上的另一个本地账户（无需管理员）。
  在哪一步：直接读 `%ROOT%\mindcraft\.mindserver-token`（`BUILTIN\Users:(RX)` 允许读），
  然后用 `curl`/任意 socket.io 客户端连 `127.0.0.1:8080`，把 token 放进 `auth.token`。
  能达成什么：见上（完全控制 / 面板 DoS / 难排查的间歇故障）。
  拿不到什么：跨机器不可达（只绑 localhost，`server.listen(port,'localhost')`）；
  没有管理员权限时拿不到其他用户的进程内存。
  影响半径：本机 agent + Minecraft 服务端控制权（等价于"能指挥 bot 的人"）。
  为什么 medium 而不是 high：需要"同机第二个账户"这个前置条件，而本项目的设计前提是
  单人本机使用（`settings.js` 全 loopback、面板单用户模型）。在单人机器上它不成立。
suggested_fix: |
  **两条路，按"用户愿不愿意接受一次性的 ACL 命令"分**：
  1. **代码内收紧 ACL（推荐，一次 5 行，纯 Windows API 调用）**：写完 token 文件后立刻把
     ACL 收成"只有当前用户 + SYSTEM"：
     ```js
     import { execFileSync } from 'node:child_process';
     // 只留当前用户与 SYSTEM/Administrators，去掉 Authenticated Users 与 Users 的继承
     if (process.platform === 'win32') {
         const me = process.env.USERNAME;
         try {
             execFileSync('icacls', [TOKEN_FILE, '/inheritance:r',
                 '/grant:r', `${me}:R`, '/grant:r', 'SYSTEM:F', '/grant:r', 'Administrators:F'],
                 { stdio: 'ignore', windowsHide: true });
         } catch (e) {
             console.warn(`[mindserver] 收紧 ${TOKEN_FILE} 的 ACL 失败（${e?.code ?? e}）；token 仍可被本机其他用户读取`);
         }
     }
     ```
     注意：`execFileSync` 传**数组**（不走 shell），`USERNAME` 里不会有空格问题；
     失败必须 warn 而不是静默（否则又变成"以为收紧了其实没有"）。
  2. **不落盘（更彻底，但改动大）**：token 只留在内存里，`start-panel.ps1` 改为
     从 mindserver 的一个**仅回环、仅本进程可读**的通道取（如一次性 HTTP 端点 + 本机回环 + 随机路径），
     或干脆让面板走 cookie（先访问一次带 token 的 URL，token 由用户在控制台手输一次）。
     —— 这条会破坏"双击就能进面板"的体验，**需要用户拍板**，不建议今晚做。
  3. **无论选哪条，README 都要写清**：`mindcraft/.mindserver-token` 是凭据文件，
     在**多用户机器**上必须收 ACL；单人机器可接受现状。
  4. 若两条都不做：至少把注释里"它的目的是别再进日志"补一句
     "**并且在多用户机器上它不是隔离 —— 见 F-RT-001**"，让下一个人知道有这笔债。
