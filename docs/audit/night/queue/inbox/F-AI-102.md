evidence: |
  模型层的"失败"目前靠**一个字符串前缀**表达，而不是 ok/code 通道：
    :25  export const FAILED_REPLY = '[LLM_ERROR]';
    :29  export function failedReply(reason) { return `${FAILED_REPLY} ${String(reason ?? 'unknown')}`; }
    :33  export function isFailedReply(text) { return typeof text === 'string' && text.startsWith(FAILED_REPLY); }
  消费点已按契约接好（19 个适配器 `failedReply`，消费侧 `prompter.js:288/338/349/352/371/398`、
  `agent.js:629` 都调 `isFailedReply`）—— 这是第 31 条真修好的部分。
  但**契约本身仍是"魔法字符串"**：`sendRequest` 返回类型是 `Promise<string>`，
  任何一处新的消费点只要忘了 `isFailedReply()`，就会把一次失败当成"模型说的话"
  写进 history、对玩家说出来、并消耗一次响应预算（这正是第 31 条修掉的那个 bug 的形状）。
  出处：docs/audit/21-review-r2-verdict.md §6「次生风险（不是新 bug，是新代码里的已知弱点）」
  原文：**"第 31 条失败信号仍是 `'[LLM_ERROR]'` 字符串前缀（新增消费点必须调 `isFailedReply()`）"**；
  docs/audit/17-review-r1-verdict.md §4 次生风险第 2 条（同一条，两轮独立记录）。
  本轮在当前代码复核：**仍存在**（`_shared.js:25-35` 逐字未变；消费点 9 处均已正确调用 —— 所以现在**没有**活的 bug，
  本条是"防下一次"的结构债）。
exploitability: |
  当前无直接可利用性（所有已知消费点都调了 `isFailedReply`）。
  风险形态：一旦有人（包括今晚的我们）在 `agent.js` / 新命令 / 新的 flow 里读 `sendRequest` 的返回值
  却不用 `isFailedReply`，就复活第 31 条：玩家会看到 `[LLM_ERROR] openai request failed: …` 被当成台词说出来，
  且失败被记成一次正常对话写进 history → 下一轮模型基于假回答推理。
  影响半径：单个 bot 的对话与推理质量；很难事后发现（history 里看不出哪句是假的）。
suggested_fix: |
  两条路，任选（都不破坏现有契约，属增量）：
  ① **最便宜**：在 `_shared.js` 加 `export function assertNotFailedReply(text, where)`，
     并在 `agent.js:608`（写 history）、`:649`（RouteResponse 出口）、`prompter` 每个 `sendRequest` 调用后
     各插一行 —— 让"忘了检查"变成运行期立刻可见的告警（含 `where`），而不是静默行为。
  ② **更彻底**（第二批）：`sendRequest` 改成返回 `{ok, text, code}`，先把 19 个适配器的返回值包一层，
     消费点改 `.text` / `.ok`。工作量 ≈ 半天，别在今晚做。
  今晚只做 ①，并在 `_shared.js` 顶部把"新增消费点必须调 isFailedReply"写成**显式接口说明**
  （现在是写在 verdict 文档里，写代码的人看不到）。
