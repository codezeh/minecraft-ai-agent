  ## 二、大小写变体：Windows 的绿灯是**本机配置**给的，不是规则给的
  ```
  $ git config core.ignorecase
  true                                        ← Windows 上默认 true
  $ git check-ignore -v .ENV
  .gitignore:115:.env      .ENV               ← 被 .env 规则罩住（因为大小写不敏感）
  $ git -c core.ignorecase=false check-ignore -v .ENV
  （无输出）                                   ← 大小写敏感时**不忽略**
  $ git -c core.ignorecase=false check-ignore -v .env
  .gitignore:115:.env      .env               ← 对照组
  ```
  ⇒ 如果有人把这份仓库放到 Linux/macOS（或本机 `core.ignorecase=false`），
  一个 `.ENV` 就直接进库。**`core.ignorecase` 是本机 git 配置，不随仓库走**（不在 `.git/config` 里提交）。
  这条不是"建议改规则"，而是"知道边界"：想要平台无关就别依赖大小写折叠。

  ## 三、`git add -f` 完胜（实测，且 git 自己会提示这个用法）
  ```
  $ git add .env.redteam-probe
  The following paths are ignored by one of your .gitignore files: .env.redteam-probe
  hint: Use -f if you really want to add them.          ← git 主动教人绕过
  $ git add -f -n .env.redteam-probe
  add '.env.redteam-probe'                              ← -f 直接穿透
  ```
  （探针文件已删除，`git status` 复验无残留。）
  ⇒ **结论：gitignore 是"防手滑"，不是"防恶意"，也不是"保密"机制。**
  它防不住：`git add -f`、`git commit -a` 对已跟踪文件的修改、任何脚本里写死的 `-f`、
  任何已入库文件里被追加的密钥（规则只影响"未跟踪文件是否被自动跳过"）。

  ## 四、它同样防不住的几类真实泄漏路径（今晚都出现过）
  - 文件被打包/压缩发送（`backups/`、`tmp/`、日志目录）；
  - 文件被同步盘/网盘带走；
  - 密钥被写进**已经被跟踪**的文件（如 `settings.js`、`config/network.json`）—— gitignore 对它无效；
  - 密钥进了**终端输出/日志**（F-SEC-205 原案、以及今晚三次"口令进日志"的记录）。
