
  `onceWithCleanup` 抛的是 `Event blockUpdate:… did not fire within timeout of 500ms`。

  ## 二、主建造路径：有安全网，500ms 不会造成误判（这是好消息）
  `act_place.js:171-200`（`placeBlockAt`，`flow_build` 走这条）：
  1. 放置失败后先 `waitUntil(() => blockAt(bot,v).name === item, { timeoutMs: verifyMs, intervalMs: 80 })`
     —— **独立于 blockUpdate 包**，直接读世界确认方块有没有出现；
  2. 出现了 → `ok()`（成功）；
  3. 没出现且错误是 `blockUpdate|did not fire within timeout` → **再读一次**：
     读到了 → `ok({…, lateUpdate: true})`；没读到 → `fail('BLOCKED', '可以重试')`（**不是判死**）。
  ⇒ 即使 blockUpdate 因为卡顿晚到、500ms 就超时，后续的 `waitUntil`/`lateUpdate` 仍会把它认成成功。
  **这条路径上 hunk 3 是安全的。**

  ## 三、没有安全网的 3 个直连调用点（残余风险在这里）
  | 调用点 | 失败后的行为 | 误判后果 |
  |---|---|---|
  | `skills.js:1335-1336` | `if (!placed.ok) throw` → catch → log `PLACE_FAILED`、`return false` | 方块其实放下了，但上报失败；调用方可能重试 → 重复放置/浪费方块 |
  | `act_pillar.js:103` | `placeResult = pr.ok ? 'placed' : 'place-failed:…'` → 记录后**继续**执行（仍跳） | 仅记录偏差，实际影响最小 |
  | `tool_prep.js:317-320` | `if (!placed.ok) throw`（**throw 在 re-read 之前**）→ 外层 catch 落回"没有工作台" | **最脆**：误判 ⇒ 判定没有工作台 ⇒ 合成链路失败 |

  注意 `tool_prep.js` 那处**明明后面就有 `const t2 = bot.blockAt(spot); if (t2?.name === 'crafting_table')` 的校验**，
  但 `throw` 在前，所以永远走不到 —— 修法很简单：把 throw 挪到那次读回之后（3 行）。

  ## 四、量化：500ms 够不够（决定这条到底多严重）
  本项目 bot 连的是**本机服务器**（`settings.js:3 host: 127.0.0.1`），loopback RTT 量级 ~0.1–5 ms，
  500ms 是 **100–5000 倍余量**。blockUpdate 依赖服务端下一 tick（20 TPS = 50ms/tick），
  即使掉到 5 TPS（200ms/tick）也仍在 500ms 内。**只有服务端掉到约 <2 TPS 才可能误判。**
  而本机确实存在"重负载"场景（341 个 op bot 的历史、BlueMap 渲染）⇒ 不是纯理论，但也不是常态。
  **我没能把它复现成稳定故障**（需要造一个 <2 TPS 的服务器，属破坏性环境，不做）。
  所以定 **low**，并给出可观测判据而不是含糊其辞。
