> 测试者：gate-keeper（复核官）｜2026-11-06 01:40–02:0x

> 方式：**只读**。所有篡改都在 `docs/audit/night/tmp-pi/` 的独立夹具里做（用工具自带的 `--root`），
> **没有改动 `mindcraft/` 任何一个字节**。

## 判决（一句话，先给结论）

> **作为"漂移探测器"它可信（16 个用例里 11 个该报的都报了，还真的抓到过本仓一个真实的陈旧补丁）；
> 作为"防篡改防线"它不可信 —— 它跑在恶意补丁**已经落盘之后**、可以被 `--write` 一键洗白、
> 而且删掉整个 `patches/` 目录它会静默放行。**
>
> **在修掉 D1（检查晚于安装）之前，把它接进 gate 只会制造假安全感。**
> 换句话说：**`F-DEP-004` 目前只做到"事后能发现"，没做到"阻止注入"。**

## 一、它到底做了什么（读代码得出，不是猜）

| # | 检查 | 代码位置 | 判据 |

## 五、四个必须修的结构性问题（按性价比排序）

### 🔴 D1（最严重）：**检查跑在恶意补丁已经落盘之后**

`start.bat` 的实际顺序（行号为实测）：
```
73:    call npm ci                    ← postinstall = patch-package ⇒ 此刻补丁已被套进 node_modules
...
81:    if exist tools\patch_integrity.mjs (
82:        node tools\patch_integrity.mjs      ← 到这儿才检查
83:        if errorlevel 1 ( ... exit /b 1 )   ← 中止，但代码已经写进 node_modules 了
```

**两个叠加问题：**

1. **顺序反了**：`npm ci` 触发 `postinstall → patch-package`，把 `patches/*.patch` **无条件**套进
   `node_modules`；`patch_integrity` 之后才跑。**恶意补丁在检查之前就完成了注入。**
   闸能做的只有"报错并中止后续步骤"，**不能撤回已写入 node_modules 的文件**。
2. **整块都在 `if not exist "%ROOT%mindcraft\node_modules" (` 里面**（第 70 行起）⇒
   **只有"首次安装"才会检查**。第二次启动时 `node_modules` 已存在 ⇒ 整个块跳过 ⇒
   **被投毒的 node_modules 会被直接使用，且永不复查**。

⇒ 这两条合起来，正好绕开了 `F-DEP-004` 想防的那条路。

**最小改法（1 行移动，收益最大）**：把 `patch_integrity` 提到 `call npm ci` **之前**：
先校验 `patches/` 与基线一致（此时还没安装 ⇒ 版本检查会降级，需要 `--no-version-check`
或接受降级），一致后才允许 `npm ci`。这样"校验"就变成了**载荷的前置条件**而不是事后追认。

### 🔴 D2：**`--write` 可以一键洗白**

T9：篡改补丁 → `node tools/patch_integrity.mjs --write` → 基线被重写成"与篡改后内容一致" → **exit 0**。
T10：攻击者手工同步改 SUMS → 同样 **exit 0**。

原因：**基线（`SHA256SUMS`）和被保护对象（`patches/*.patch`）在同一个可写目录里，没有任何外部信任锚**
（无签名、无远端比对、无 TSA/时间戳）。⇒ 任何"能执行脚本"的人都能让这道闸变绿。

**这不是"写错了"，是这类方案的天花板**：本机自校验**永远只能防"意外漂移"，
防不住"有意篡改"**。要防有意篡改，基线必须来自攻击者改不动的地方（另一台机器 / 签名 / CI）。

**建议**：
- gate 路径**拒收 `--write`**（gate 只读，永不写基线）；
- `--write` 加显式二次确认（如必须 `--write --i-know` 且有 `SKIP_*` 之外的独立环境变量）；
- commit body 要求"补丁与基线必须在同一个 commit 里变更"，并在 review 时逐条比。

### 🟠 D3：**删除整个 `patches/` 目录 = 静默放行**

L66-69：
```js
if (!existsSync(PATCH_DIR)) {
    console.log('patches/ 不存在 —— 本仓没有补丁集，跳过。');
    process.exit(0);
}
```
T14 实测 **exit 0**。对一个**本来就有补丁集**的仓库，这是最省力的攻击：
不用植入任何东西，**只要把安全补丁删掉**（若某个补丁是安全修复，删掉即等于降级/解除防护），
闸不报、postinstall 也不会套用任何补丁，看似"一切正常"。

**建议**：判据改为"**存在 `SHA256SUMS` 就要求 `patches/` 必须存在**"，或引入一个
`.patches-required` 标记文件（仓库声明"我依赖补丁集"），缺目录即 FAIL。

### 🟠 D4：**根本还没接线（现在它不在任何门禁里）**

实测：
```
grep -rn "patch_integrity" → 只有 start.bat:81,82
package.json 的 gate = settings_check && preflight_regex_unit && preflight && lint_hard   ← 没有它
.githooks/pre-commit 跑 npm run --silent gate                                               ← 也没它
```
⇒ **committer 改坏 `patches/` 不会被任何提交前门禁挡住**。captain 已知这点（"还没接进 gate"），
这里只是把"接的时候要连 D1 一起修"钉成书面结论：**先修 D1 再接线，否则接上的是一道事后闸。**

## 六、次要观察（不用改也能接受，但要知情）

1. **`.patch.disabled` 完全不校验**（T11 新增也 exit 0）。因为 `patch-package` 不套用 `.disabled`，
   所以**不是执行面漏洞**；但意味着可以往里静默塞东西。建议至少入基线（只记哈希、不参与套用）。
2. **基线格式敏感**：正则 `^([0-9a-f]{64})\s{2}(.+)$` 要求**两个空白**。
   手工编辑基线时若用了单个空格，该行被**静默忽略** → 该补丁报"不在清单里"（T13 那类）。
   方向是"多报错"而不是"少报错"，可以接受；但 `--write` 生成的格式必须始终一致，别手改。
3. **`node_modules` 未安装时版本检查降级**（T8）。设计合理（干净克隆要能过），
   但要知道：**只跑内容检查时，这道闸对"补丁套不套得上"一无所知**。
4. **被禁用的补丁 `minecraft-data+3.97.0.patch.disabled`** 目前只打印提醒，不进基线。

## 七、结论与建议的落地顺序

**判决重申**：
- 11/16 用例该报的都报了，并且真的抓到过本仓一个 stale 补丁（**不是假绿**）⇒ **值得保留、值得接线**。
- 但它**挡不住它有意的攻击者**（T9/T10 洗白、T14 删目录），而且**在 start.bat 里的位置让它检查得太晚**（D1）
  ⇒ 现在把它接进 gate，会让人以为 `patches/` 被保护了。

**给 patch-smith 的最小改造清单（按性价比）**：

| 序 | 改动 | 成本 | 收益 |
|---|---|---|---|
| 1 | `start.bat`：把 `patch_integrity` 移到 `call npm ci` **之前** | 移动 6 行 | **把"事后追认"变成"前置条件"——最高性价比** |
| 2 | 接进 `npm run gate`（pre-commit 级） | 1 行 | 有自动触发点 |
| 3 | `patches/` 不存在但有 `SHA256SUMS` ⇒ FAIL | ~5 行 | 堵 T14 |
| 4 | gate 路径拒收 `--write` | ~3 行 | 防"顺手洗白" |
| 5 | （可选）校验 node_modules 里补丁**真的被应用** | 中 | 把"版本对"升级成"内容对" |
| 6 | （可选）`.patch.disabled` 入基线 | 小 | 堵静默藏货 |

**在 1、3、4 完成之前，`F-DEP-004` 应标"部分解决（仅事后可发现，未阻止注入）"，不要标已修。**
—— 这正是 captain 要的那句"把这句话判死"。
