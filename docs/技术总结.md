# 技术总结：导航层重写与工程化改造

本文是一次完整改造的技术总结，记录**做了什么、为什么这么做、验证到了什么程度、哪些判断被实测推翻**。
细节过程见 [`经验教训.md`](经验教训.md)，模块级设计依据见 [`自研申报.md`](自研申报.md)。

---

## 一、改造前的状态

导航层存在四套并存的实现，彼此职责重叠：

| 模块 | 定位 | 问题 |
|---|---|---|
| `heatmap.js`（1342 行） | 分层寻路 | 与 `task_hop` 重复 |
| `tile_map.js` | 16 格战棋格 | 真机数据证伪：那层只有 1 个可站立面 |
| `path_long.js` | 区块级 A* | 依赖 `tile_map` |
| `chunk_map.js` | 2.5D 单层地表 | 看不见洞穴、竖井、悬空 |

症状表现为长距离任务频繁卡死、垂直方向"假成功"、无法处理多层地形。
根因不是某个 bug，而是**没有单一事实来源**：四套规划器各自维护对世界的理解，互相冲突。

## 二、重写后的架构

收敛为单链路：

```
scanSphere (terrain3d)  →  plan3D (path_3d)  →  按 action 分发 (executor)  →  重扫重规划
```

### 2.1 `terrain3d.js` —— 真 3D 可站立面库

关键设计：**一个水平坐标 (x,z) 可以对应多个可站立面**。

2.5D 地图的根本缺陷是每列只能记一个高度，因此无法表达：
洞穴地面、桥面与桥下、水下地面、悬空平台。

存储用 SQLite，`surf(x, z, y, t)` 三元组 + 类型标记：

| 类型 | 含义 |
|---|---|
| `SOLID` | 普通可站立实心面 |
| `WATER` / `LAVA` | 液体顶面 |
| `BUILT` | 玩家建筑（可走，但代价高） |
| `LEAVES` | 树叶 |
| `CLIMBABLE` | 梯子/藤蔓（可置身其中上下移动，**不是落脚点**） |
| `SUBMERGED` | 沉在水下的地面（见 §4.3） |

### 2.2 `path_3d.js` —— 体素 A*

每步携带真实 `y` 和一个动作类型，而不是只有二维坐标。

代价模型（关键参数）：平走 1、上 1 格 2.5、上 2 格 8.5、下落 1 + 0.3/格、挖掘 5/格、攀爬 1.5/格。

安全约束（每条都对应一次真机事故）：
- 攀爬方块只生成 `climb` 边，**不生成 `walk` 边**（不能站在梯子上）
- 岩浆上方不作为落脚点
- `|dy| > 1` 时必须校验路径未穿墙
- 水中不允许大幅垂直移动

### 2.3 `executor.js` —— 唯一任务层

滚动时域：扫描 → 规划 → 执行前若干步 → 重扫。不追求一次规划到底。

三个必须的后置校验（都是"规划说到了、实际没到"换来的）：
1. **高度校验**：`moveToXZ` 只管 x/z，脚下是空气时位置不变，原来会假报成功
2. **距离校验**：`STUCK` 判据必须比对实际位移，不能只看 pathfinder 返回值
3. **落地校验**：目标格下方必须实心，否则会踩空

## 三、原子层与自检机制

### 3.1 分层职责

| 层 | 职责 | 特征 |
|---|---|---|
| 原子层（21 个 `atom_*.js`） | 单一副作用 | 错误码封闭在 `atom_contract.CODES` |
| 复合层（`task_*.js`） | 组合原子、管流程与降级 | 可失败重试 |
| 技能层（`skills.js`） | 暴露给模型 | JSDoc 写在函数体内（`docHelper` 取的是 `toString()`，函数体外的注释取不到） |

### 3.2 五道启动自检（`tools/preflight.mjs`）

不靠记性，靠机制：

| 审计 | 拦什么 |
|---|---|
| 规则审计 | 裸游戏常量必须带 `rule:Rx-xx` 来源引用 |
| 错误码审计 | `fail('XXX')` 用到的码必须在 `CODES` 里注册 |
| 新模块申报 | 新增 `atom_*/task_*` 必须在 `自研申报.md` 有记录 |
| 字段标准 | 距离字段必须带参照点（`distFeetToEntity` 而非裸 `dist`） |
| 文档漂移 | 代码比交接文档新时提示更新 |

**为什么做这些**：错误码漏注册这类问题在本项目出现过 4 次，每次都是运行时 `throw` 且报错不指向根因。做成审计后不再复发。

## 四、被实测推翻的判断（最有价值的部分）

以下都是**先有结论、后被数据推翻**，记录下来避免重犯。

### 4.1 "她不能潜水" —— 错的，能潜

先前结论：执行层没有潜水能力，路线应完全避开水面。

实测（15 格深水池，逐秒采样）：

```
起点 y=65.70
2s → 64.73   4s → 63.70   6s → 62.70
8s → 61.70  10s → 60.68  12s → 59.70
```

**稳定 1 格/秒，12 秒未停。**

且四种方式速度完全一致（什么都不按 / sneak / 看向下+前进 / 组合）——
查 `prismarine-physics` 证实：水中分支没有对 `sneak` 的特殊处理，
只有**梯子**分支才有 `sneak ? 0 : -ladderMaxSpeed`。

**结论修正**：水中下沉是默认重力，不需要按键。真实 bug 是 `executor.js` 里潜水等待写死 6000ms，
高差超过 6 格就永远沉不到。

### 4.2 "骑船走不通" —— 部分对的

`bot.mount()` 在 Paper 1.21.8 上被服务端静默忽略。实测穷尽四种包变体（含
[PR #4089](https://github.com/PrismarineJS/mineflayer/pull/4089) 的原版 `interact_at` + `interact` 一对），
全部无反应；已排除包结构、距离（客户端与服务端位置偏差 0.00 格）、被踢。

**但换一条路可行**：

| 步骤 | 做法 | 结果 |
|---|---|---|
| 上船 | `/ride <玩家> mount <载具>` | ✅ 成功，服务端回 `set_passengers` |
| 开船 | `bot.setControlState('forward')` | ✅ 前进 5.65 格 |
| 开船 | `bot.moveVehicle(0,1)` | ❌ 位移 0.00 |

**硬边界**：载具**浮在水面**时，服务端会在 29~45ms 内解除乘坐；
干地上的船与矿车正常。因此**乘船渡水实际不可用**，渡水应直接用导航（浮水前进）。

### 4.3 "水下地面可以走" —— 错的

库中 51,871 个实心面里，**24,735 个（47.7%）在水下**。

规划器把它们当普通落脚点，于是安排"下到水底"，而她浮在水面下不去 → 每轮报
`HEIGHT_MISS 该降到 y=58，实际停在 y=62`。

前两次修法（"正上方是水就禁"、"该列有水面就禁"）都失败：库只记液体顶面，水底上方没有记录；过度禁止会让规划无路可走。

**最终解法**：扫描时给水下的实心面打 `SUBMERGED` 标记，规划时施加**高代价**而非禁止。
效果：规划 y 范围从 `44~63` 收到 `58~73`，不再下潜；同时"只有水下通路"的极端情况仍能规划（不会退化成 `NO_PATH`）。

## 五、真机验证的价值：7 个 bug 的教训

`atom_climb` 与 `atom_tunnel` 交付时单元测试全过（37 项），但真机一测即暴露 7 个 bug。

### 5.1 为什么单元测试测不出来

模拟 bot 的位置是常量：

```js
entity: { position: { x: 0, y: 64, z: 0 } }   // 永不变化
```

因此所有**依赖状态随时间变化**的路径都是盲区：

| 类别 | 例子 |
|---|---|
| 等待/超时 | `waitUntil` 传 `{timeout}` 而非 `{timeoutMs}` → 静默用默认 1500ms |
| 谓词语义 | 返回 `false` 被当成"完成"（判据是 `!== undefined`）→ 每次只爬 0.7 格就返回 |
| 物理引擎 | 下梯子按 `sneak` 几乎不动（实测 Δ-0.83/4s），正确做法是**什么都不按**（Δ-2.93/4s） |
| 时序 | "ok" 不等于"有进展"：挖 0 格且位置不变时仍返回成功 → 无限空转 |

### 5.2 结论

**凡是"等一个状态变化"或"按键产生物理位移"的能力，必须真机验证。**
包括：攀爬、跳跃、挖/放方块、游泳、开关门、捡掉落物。

### 5.3 反向验证的重要性

新增"交接文档漂移检查"后，它显示 `✓ 不比代码旧`——但这只说明没报错，不能说明会报错。
故意提交一次代码改动，确认提示真的出现，再回滚。

**一个永远不响的检查等于没加。**

## 七、方法论小结

按重要性排序，都是这次改造中被反复验证的。

1. **先测物理事实，再下"能力不存在"的结论。**
   潜水就是被"测了一次没成功"误判成"没有能力"。先测窗口多长、速率多快，再判断是能力缺失还是参数不对。

2. **"命令成功"不等于"状态正确"。**
   删除文件要验证结果状态（拉取新 tree 确认文件真的不在了），而不是只看命令返回值。
   本项目在这一点上犯过两次同样的错。

3. **假 bot 测逻辑，真机测物理。** 两者不可互相替代。

4. **一个来源，一条链路。**
   四套规划器并存时，修一处忘三处。收敛后所有导航行为只有一个入口。

5. **约束靠机制，不靠记性。**
   错误码漏注册出现过 4 次，做成审计后归零。

6. **"协议不支持"要先穷尽替代路径。**
   "挂不上"和"开不了"是两个独立问题，捆在一起判断会过早放弃。

7. **检查项要做反向验证。** 见 §5.3。
