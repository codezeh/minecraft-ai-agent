## 一、Minecraft 的真实规则（纠正我之前的错误）

| 我之前的错误认知 | 真实规则 | 来源 |
|---|---|---|
| ❌「挖掉下面的原木，整棵树会塌下来」 | **完全不会塌**。方块悬空待着，不受重力（沙子/沙砾才受） | `[游戏数据]` 方块数据里没有 collapse 概念 |
| ❌「大树从顶往下砍，小树从下往上」 | 没有这个必要。**只受一个约束：臂展 4.5 格** | `[实测]` |
| ❌「树型（大/中/小）决定砍法」 | 树型与砍法无关，只与**需不需要垫高**有关 | 用户指出 |
| ✅「叶子要不要一起砍」 | **不用砍**。原木砍光后，叶子自动枯萎消失 | `[游戏数据]` `oak_leaves` 有 `distance:1..7` 状态；离原木超过 6 格就枯萎 |
| ✅「怎么判断天然树」 | ~~`persistent=true`~~ **这个判据无效**（实测自然树叶也有 persistent=true） | `[实测]` 见下方 |
| ✅「搭柱子够高处」 | 需要。丛林大树 20+ 格，地面站位够不到顶部；用 `allow1by1towers` 让 pathfinder 自动搭 | `[官方插件]` 用 pathfinder 的 movements 配置 |

### 实测数据：`persistent` 不能用来区分自然/人造

```
自然树叶: (-190,67,-263) persistent=true  distance=7   ← 自然但 persistent=true
自然树叶: (-189,67,-263) persistent=false distance=7
自然树叶: (-186,69,-249) persistent=false distance=3
```

**结论**：`persistent=true` 的真实含义是"这丛叶子锚定了不枯萎"，自然树冠边缘就是这种。
所以**唯一可靠的"是不是天然树"判据**仍然是：
**树冠（周围有 `_leaves`）+ 没有人工材料包住** —— 也就是现在 `classifyLog` 的做法（离线验证 97.6% 通过、0 误杀）。

**用户的要求"只要一个是不是自然树的判断"是对的**：树型/大小/砍伐方向全部删掉，只保留这一个判定。

## 二、单棵树怎么砍（正确的模型）

砍一棵树的本质是**一个覆盖问题**：

```
已知：这棵树的全部原木坐标（洪泛填充得到）
约束：
  - 臂展 4.5 格（生存模式）
  - 站位必须可站（脚位头位空、下方实心）
  - 够不到时可以用 pathfinder 自动搭柱子上来
求：把全部原木挖完，走的步数尽量少
```

**没有"顺序"问题**：因为方块不会塌，任意顺序都行。
唯一需要排的是**效率**：一个站位能覆盖几格，就一次挖完，再走。

所以单树计划 =
```
1. findFromVein(树干)          → 全部原木坐标（含分枝、2×2）
2. 按"可达站位"分组：           → 每组 = 一个站位 + 它覆盖的格子
     优先用已有地面站位
     覆盖不到的 → 标记"需要垫高"
3. 执行：对每组 → 走到站位 → 逐格挖 → 捡
4. 需要垫高的 → 让 pathfinder 用 allow1by1towers 自己搭上去
                 （搭的方块要记录，砍完拆掉——用户要求）
```

## 四、改造方案

### 方案 A：直接用官方插件（推荐）

```js
// 替换 678 行的 collect 核心
const blocks = bot.collectBlock.findFromVein(trunkBlock, 200, 32, 1);  // 全树原木
const targets = blocks.filter(b => !isProtected(b.position) && isNaturalTree(b));
await bot.collectBlock.collect(targets, { ignoreNoPath: true });
```

**优点**：洪泛填充 + GoalLookAtBlock + itemDrop 事件 + 背包满自动存箱，全部现成。
**代价**：需要给 pathfinder 配 `allow1by1towers`（已有）、需要保留树性判定和保护区判据。

### 方案 B：自己实现，但照官方做法

保留自己的原子化，但把三处换成官方做法：
1. 用 `findFromVein` 替代"按列聚类"
2. 用 `GoalLookAtBlock` 替代手写 `findStandSpot`
3. 用 `itemDrop` 事件替代固定等待

**优点**：保持现有架构和日志。
**代价**：要重写三处，且不如直接用官方稳。

**我倾向 A + 少量 B**：
- 核心采集用官方 `collect()`
- 保留我们的：树性判定（`classifyLog`）、保护区（`isProtected`）、锚点（`near`）、垫脚清理、工具准备（作为官方 `equipForBlock` 的兜底）

这样 678 行能砍到 ~150 行。
