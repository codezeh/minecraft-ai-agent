## 二、🔴 逻辑冲突点（这就是「砍几下就换树」的原因）

### 冲突 1（已用代码确认）：站位失败 → 整棵树作废

```js
// 第 392-398 行 —— 这里只查了「pos 这一格」的站位
const stand = findStandSpot(bot, pos);
if (!stand) {
    tree.done = true;          // 🔴 整棵树放弃，但失败的只是这一格
    blacklist.add(key(pos));
    onEvent({ type: 'plan-skip', kind: tree.kind, why: 'NO_STAND' });
    continue;
}
```

```js
// 第 427-429 行 —— 同理，走不到这一格就整棵放弃
tree.done = true;
onEvent({ type: 'plan-skip', kind: tree.kind, why: mv.code });
```

**两处都只针对「一格」，却把整棵树判死。**
这是「砍几下就换树」的直接原因——只要某棵树有一格站不到/走不到，剩下的格子全不砍了。

### 冲突 2（结构与代码都确认）：策略说「从树顶往下」，但站位查找要求「贴着目标」

```js
// tree_strategy.js —— 大树从树顶开始
for (let dy = height - 1; dy >= 0; dy--) out.push(...)

// task_collect.js —— 但 findStandSpot 只找目标格的紧邻可站格
const stand = findStandSpot(bot, pos);
```

**树顶那格通常没有可站邻格**（周围是树叶和空气），于是：
```
计划从树顶砍 → 树顶找不到站位 → 冲突 1 触发 → tree.done → 换树
```

两个设计互相打架，结果就是「大树砍不动，一直在换树」。

### 冲突 3：`findStandSpot` 找不到时没有「从上方够」的后备

现在只有：邻格可站 → 站过去挖。
缺：**站在目标上方/侧上方**（丛林树顶常见做法）→ 跳起来挖 / 向下挖。

## 三、🟡 低效点

| 位置 | 现象 | 影响 |
|---|---|---|
| `collectDrops` 每格都等 1.6 秒 | 8 个木头 = 13 秒纯等待 | 影响效率 |
| `plan.trees` 用完不重新侦察 | 附近砍光才扩半径 | 多走几步 |
| 每轮重建 `findAny` 闭包 | 轻微 | 可忽略 |

## 四、修复建议（按优先级）

### P0：站位/移动失败时，只在「格」级别放弃

```js
if (!stand) {
    blacklist.add(key(pos));
    tree.order.shift();     // 只丢这一格
    continue;               // 树还在，继续砍下一格
}
```

`tree.done` 只在 `order` 空了之后才设（第 419 行已经在做）。

### P1：给「从树顶往下砍」配一个能用的站位

树顶的站位应该允许：
- **站在目标格的侧下方**（仰角挖，`reachDistanceTo ≤ 4.3` 即可，实测 digBlock 已只看距离）
- 或**站到树冠上**（树叶可站，mineflayer 的 `standable` 现在把 leaves 当不可站，这里可能要放宽）
