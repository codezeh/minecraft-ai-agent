## 3. 现在的实际流程（原始版本）

```
task_hop 开始
  ↓ 扫描起点/终点周边区块
  ↓ planLong()  ← 拉直线 + 每 64 格取一点 + 地形差就往左右挪 8~32 格
  ↓ 对每个路点：
       walkSegment() → path_short → pathfinder 走真实地形
         ├─ 成功 → 下一个路点
         └─ 失败 → 切半（split）重试
              └─ 还是失败 → tileAStar() 在区块图上重算
                   └─ 但只取 path[1]（下一格中心）当临时路点
                        └─ 回去继续走
```

**核心问题：粗规划没有真正在地图上找路，只是"直线 + 左右避让"。真正的寻路（`tileAStar`）被当成急救，而且只取一格方向。**

于是每次都是局部修正 → 没有一次算完整路线 → 徘徊。

## 4. 代码里能看到的 4 个具体缺陷

### 4.1 改道时取到"身后"的格子中心

```js
// task_hop.js:100-101
const t = route.path[1];
plan.waypoints.push({ x: t.cx * 16 + 8, z: t.cz * 16 + 8 });  // 格子中心
```

她站在格子任意位置。若在格子东半部，格子中心在**她身后** → 先往西走 8 格。
且 `path[1]` 方向由 A* 决定，**未必朝目标**。

### 4.2 避让可能挪到身后

```js
// path_long.js:57（原始）
for (const off of [8, -8, 16, -16, 24, -24, 32, -32]) {
    const nx = x + px * off, nz = z + pz * off;   // px,pz = 垂直方向
```

左右对称试探，**不检查"偏移后是否更靠近目标"**。往左挪 32 格再折回 = 白走 64 格。

### 4.3 "没路"和"预算用完"混在一起

```js
// tile_map.js:128,166（原始）
while (open.size && nodes < maxNodes) { ... }
return { path: [], cost: Infinity, nodes };   // ← 超预算和真没路，返回值一样
```

调用方（`task_hop.js:96`）把两种都当"绕不过去"，直接放弃整段路。
**明明能去的地方，她说不去。**

### 4.4 斜穿墙角

```js
// tile_map.js:149-153（原始）
for (const [dx, dz] of [..., [1,1], [1,-1], [-1,1], [-1,-1]]) {
    const c = tileCost(ni) * (dx && dz ? 1.414 : 1);
    if (c === 0) continue;              // 只检查对角目标格
```

不检查两个正交邻格。Minecraft 玩家箱体 0.6 宽，**斜穿 1 格墙角会卡住**。

## 5. 关键约束（改的时候必须遵守）

| 约束 | 数值/来源 |
|---|---|
| **路点数必须少** | `MAX_WAYPOINTS = 4`。实测 pathfinder 单次调用 13~15 秒，与距离关系不大 |
| **近距离不走长规划** | `MIN_SEGMENT = 24` 格 |
| **避让阈值** | `AVOID_COST = 20`（水 6 不避，建筑 18 不避，陡坡 25 避） |
| **区块粒度** | 1 格 = 16×16 世界格 |
| **区块数据字段** | `{explored, y, h, water, lava, built, leaves, solid, samples}`（见 `chunk_map.js:115-126`） |
| **代价表** | 平地 1 / 丘陵 4 / 树林 5 / 水 6 / 建筑 18 / 陡坡 25 / 岩浆 0（禁行）/ 未探索 6 |

**注意**：`tileCost` 目前只用于两处——① 直线避让的阈值判断（`>= AVOID_COST` 才避）；② 区块 A* 的边权。所以**改代价数值影响很小**，别把精力花在这。

## 7. 备选方案（供新对话讨论，不是结论）

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. A\* 当主力** | `planLong` 先用 `tileAStar` 算完整路线，再压成 ≤4 路点 | 中等；需要路线压缩算法 + 降级路径 |
| **B. 只修缺陷** | 保留直线结构，只修 4.1~4.4 | 小；但不解决"没有一次算完整路线" |
| **C. 分层规划** | 粗网格远规划 + 细网格局部，参考 Baritone | 大；但 Baritone 是成熟参考 |
| **D. 相对导航** | 不用全局路线，每步只朝目标走，卡住就绕 | 小；但复杂地形容易绕晕 |

**注意**：`path_network.js` 曾有"路网骨架"思路（把可走区块连成连通块，长期规划沿骨架走），已在今天清理时删除。思路本身可能仍有价值，可从 git 历史恢复（删除于 commit `ab44890`）。

## 8. 外部参考

用户提到过 **FS-Planner**（Robotics and Autonomous Systems 198:105317，2025）：

- 论文：[arXiv:2505.24024](https://arxiv.org/abs/2505.24024)
- 开源代码：https://github.com/robotics-upo/Heuristic_path_planners/
- 核心：改进 Lazy Theta\* + **EDF（Euclidean Distance Field，欧氏距离场）** 代价项（`c = ‖Δs‖ + c_w / O`，O 是沿路径的 EDF 积分，已证满足三角不等式）+ 梯度邻居选择
- **用户注意过的点**：它的"EDF 是距离场，不是 EDF 调度算法"

**适配风险（我读论文后的判断，供参考）**：
- 它假设"离障碍越远越安全"，而 Minecraft 里**离方块远 = 可能掉下悬崖**
- 它要求**离线预计算的距离场**，我们的世界随时被玩家改动
- 它是任意角（视线可达即直连），而方块世界斜穿墙角不可行
