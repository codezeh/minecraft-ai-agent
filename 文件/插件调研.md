## 2. 最高优先级：不是插件，是 OP 权限

`ops.json` 是空的。而 mindcraft 的很多技能是**直接发原版命令**实现的：

| 文件 | 命令 |
|---|---|
| `src/agent/tasks/tasks.js` | `/tp`、`/give`、`/clear` |
| `src/agent/tasks/cooking_tasks.js` | `/fill`、`/setblock`、`/summon`、`/kill`、`/data merge` |
| `src/agent/library/skills.js` | `/setblock`、`/tp` |
| `src/agent/agent.js:102` | `/skin set URL ...` |

没有 OP（等级 2）时，这些命令**不会报错给 LLM，只会静默失败** —— 机器人会以为自己造好了房子/传送成功了，实际什么都没发生。这是目前最影响体验的一个问题，比装什么插件都重要。

**建议**：给 `deepseek` OP，或用 LuckPerms 精确授权。

## 3. 会直接搞坏机器人的插件（重要）

mindcraft 靠 mineflayer 的 `chat` 事件收消息（`src/agent/agent.js:187`），而这个事件依赖**字符串正则**匹配。实测源码 `node_modules/mineflayer/lib/plugins/chat.js:3-4`：

```js
const USERNAME_REGEX = '(?:\\(.{1,15}\\)|\\[.{1,15}\\]|.){0,5}?(\\w+)'
const LEGACY_VANILLA_CHAT_REGEX = new RegExp(`^${USERNAME_REGEX}\\s?[>:\\-»\\]\\)~]+\\s(.*)$`)
```

翻译一下它的容忍度：

- **能容忍**：最多 5 段前缀，如 `[Admin] (VIP) deepseek > 你好` ✔
- **必须是**这些分隔符之一：`>` `:` `-` `»` `]` `)` `~`
- **不能容忍**：`deepseek | 你好`（竖线）、`deepseek »» 你好`（两个 »，其实能，因为我写的是 `+`）…
  关键是不能出现**其他符号**充当分隔符，比如 `|`、`→`、`•`

**结论**：以下插件会改聊天渲染格式，可能导致机器人**完全收不到玩家消息**：

| 插件 | 风险 |
|---|---|
| EssentialsX **Chat 模块** | 高 —— 自定义格式，默认常带 `|` 之类符号 |
| InteractiveChat | 高 —— 重写聊天为可点击组件，且需要客户端 mod |
| 任何"聊天前缀/称号/rank"插件 | 中 —— 取决于分隔符 |

**如果一定要用**，把格式改成 `[前缀] 名字 > 消息` 这种，分隔符用 `>` 或 `:`。

## 16. 娱乐向插件特有的坑

1. **聊天刷屏会灌爆 LLM 上下文**
   小游戏死亡播报、VexBot 战况、crate 开箱都是高频广播。mindcraft 会把聊天内容喂给模型，
   刷屏既烧 token 又会干扰判断（它可能开始回应系统公告）。
   建议装了小游戏类插件后，把这些广播关掉或改到 action bar。

2. **聊天格式**（同第 3 节）—— 小游戏插件常带 `|` 分隔的公告格式。

3. **资源包**：MyFurniture / Slimefun 需要玩家接受服务器资源包，第一次进服会弹提示。

4. **性能叠加**：MythicMobs + EliteMobs + Slimefun 三个一起上会明显吃 CPU。
   这个服是 2G 堆内存（`-Xmx2G`），建议最多选一个大型内容包。

5. **难度**：当前 `difficulty=peaceful`，装了 BOSS/怪物类插件**必须先改难度**，
   否则敌对生物根本不生成，插件等于没装。

## 18. 插件 vs 模组：怎么一眼分辨（重要）

### 结论：上面列的**全部是插件**，不是模组

判据不是 Modrinth 页面上的分类，而是这三个字段（实测 CoreProtect / MythicMobs / Sodium 对比）：

| 项目 | loaders | client_side | server_side | 性质 |
|---|---|---|---|---|
| SkinsRestorer（已在跑） | bukkit,paper,spigot,fabric… | unknown | unknown | **插件** |
| CoreProtect | bukkit,folia,paper,purpur,spigot | **unsupported** | **required** | **插件** |
| MythicMobs | folia,paper,purpur,spigot | **unsupported** | **required** | **插件** |
| Sodium（对照） | fabric,neoforge,quilt | **required** | **unsupported** | 模组 |

`client_side: unsupported` + `server_side: required` = 纯服务端，jar 直接丢 `server/plugins/`，玩家不用装任何东西。

> 注意：Modrinth API 的 `project_type` 字段**不可用于判断** —— 它对所有项目都返回 `"mod"`，
> 连 SkinsRestorer 也是。别被这个字段误导。

### 但你的直觉有道理：其中 7 个是「双栖」项目

同一个 Modrinth 项目里**同时发布 Fabric/Forge 版和 Paper 版**，下载页两个 jar 都摆在那。
下错了就是一个模组，扔进 `plugins/` 毫无反应，服务端日志也不报错。

**必须认文件名：**

| 项目 | ✅ 要下这个（插件） | ❌ 别下这个（模组） |
|---|---|---|
| **PatPat** | `patpat-plugin-1.2.5.jar` | `1.3.1+1.21.8+neoforge` |
| **VeinMiner** | `veinminer-paper-2.6.0.jar` | `2.5.0` (fabric,quilt) |
| **Bending** | `bending-paper-3.13.1.jar` | `3.13.1` (fabric) |
| **Kenshin's Hide And Seek** | `KenshinsHideAndSeek-2.3.0+bukkit.jar` | — |
| **BuildPaste** | `BuildPaste_Plugin-…v2.1.0.jar` | `1.7.3` (fabric) |
| **Chunky** | `Chunky-Bukkit-1.4.40.jar` | `1.4.40` (fabric) |
| **Emotecraft** | `emotecraft-paper-for-MC1.21.7-…jar` | `…-fabric` / `…-forge` |

文件名里带 `plugin` / `paper` / `bukkit` 的就是插件；带 `fabric` / `forge` / `neoforge` 的是模组。

### 真正需要客户端 mod 的（服务端插件装了也只是"半套"）

| 项目 | 原因 |
|---|---|
| **Emotecraft** | 服务端插件只负责同步玩家动作，**不装客户端 mod 看不到表情** |
| **ItemSwapper** | 纯客户端操作增强（`client_side: required`） |

## 19. 先划清一条界线：哪些能用插件解决，哪些不能

你提的四件事，性质完全不同：

| 需求 | 插件能解决吗 | 原因 |
|---|---|---|
| 性能优化 | ✅ 能 | 服务端插件直接干预 |
| AI 动作更流畅 | ⚠️ 间接 | 只能通过降低服务端卡顿间接改善 |
| AI 说话更有风格 | ❌ 不能（对现有 bot） | 那是 mindcraft 的 prompt，插件碰不到 |
| AI 更聪明 | ❌ 不能（对现有 bot） | 那是模型选择，插件碰不到 |

`deepseek` 这个 bot 是 mindcraft 在 Node.js 里自己调 LLM API 的，**Minecraft 插件无法介入它的提示词或模型**。
所以后面两类，插件只能以"另开一个独立的 AI 角色"的方式实现，不是升级现有 bot。

## 22. AI 动作更流畅

没有插件能直接让 mineflayer 的机器人走得更顺 —— 动作是 bot 自己算的。
服务端插件只能通过"降低卡顿"间接改善，而你的服务端已经是 TPS 20 / MSPT 0.8ms，没有可改善空间。

真正影响 bot 动作流畅度的是这几个（都在 mindcraft 里，不是插件）：

| 项 | 当前值 | 说明 |
|---|---|---|
| `cooldown` | 3000 ms | 每轮响应的强制间隔。**这是"卡顿感"的最大来源** |
| `model` | deepseek-v4.1-flash | 单次往返约 1.8 秒 |
| `narrate_behavior` | true | 机器人会自动播报"Picking up item!"，刷屏且灌上下文 |
| pathfinder 默认值 | canDig/allowParkour/canOpenDoors 全为 true | **已是最优**，不需要调 |

也就是说，这块想改善只能动 mindcraft 配置，插件无解。

# 第四轮：改善游戏内 AI 行为逻辑的方案（2026-10-20）

> 这一轮不再泛泛罗列插件，而是**拿我们自己实测撞到的失败模式**去对方案。
> 所有版本号均为 npm registry 实测值，查询时间 2026-10-20。

## 26. 先定位：我们的"逻辑差"具体差在哪

把这两天真实出过的问题归类，只有四类：

| 编号 | 失败模式 | 真实证据 |
|---|---|---|
| **F1** | 寻路卡死不返回，动作永久挂起 | `PathStopped ... at resetPath` 循环，`goToGoal` 无限重试，`executing` 卡 true → 命令全被阻塞 → 进程被杀 |
| **F2** | 生成的代码自己乱写破坏性循环 | 她自己写 `for dx/dz/dy … skills.breakBlockAt(...)` 清场，而不是调用现成技能 |
| **F3** | 报告"成功"但实际没做成 | 说"地板铺好啦"，但需要我用计分板逐格核实才知道真假 |
| **F4** | 单步动作太慢，长任务跑不完 | 手工平地实测 **27 秒/列**，50×50 需要 19 小时 |

**关键判断**：F1 是底层库缺陷；F2/F3 是"模型能力 + 工具设计"问题；F4 是执行策略问题。
**这四类没有一类能靠装一个 Minecraft 插件解决**——插件只能改世界规则，碰不到决策层。这一点和第 25 节结论一致。

## 27. F1（寻路卡死）：已确认上游无解，只能自己兜底

### 关键发现：pathfinder 已停止维护

| 包 | 最新版 | 发布日期 | 距今 |
|---|---|---|---|
| `mineflayer-pathfinder` | **2.4.5** | 2023-09-04 | **约 3 年无更新** |

我们用的就是 2.4.5（已是版本列表里的**最后一个版本**）。也就是说，卡死问题**不会有官方修复**，只能：

1. **我们已经在做的（正确做法，建议保留）**：`goToGoal` 加 180 秒硬超时 + `bot.pathfinder.stop()`；`pickupNearbyItems` 每件物品 8 秒上限。这是目前最有效的止血。
2. **项目自带的 `patches/` 机制**（之前没注意到）：
   `package.json` 里有 `"postinstall": "patch-package"`，`patches/` 下已有多份补丁，其中 `mineflayer-pathfinder+2.4.5.patch` 有 **265 行**。
   我逐行读过，它修的是：岩浆避让、门/活板门/栅栏门的开关、藤蔓与梯子攀爬、梯子顶端跳跃、放置方块后的世界状态同步。
   **注意：这个补丁完全没有涉及"卡死/重新规划"**。所以我们加的超时兜底是补丁覆盖不到的空白区，不是重复劳动。
   后续如果还想改 pathfinder 行为，正确姿势是：改 `node_modules/mineflayer-pathfinder/` 后跑 `npx patch-package mineflayer-pathfinder`，而不是直接手改（重装就丢）。

### 备选：换寻路引擎（唯一活跃的替代品）

| 项目 | 版本 | 发布 | 要求 mineflayer | 维护状态 |
|---|---|---|---|---|
| `@miner-org/mineflayer-baritone` | **4.6.2** | 2026-08-29 | ^4.35.0 | **活跃**（2025-02 起，20 个版本） |

能力上确实比 pathfinder 强，README 明确写了：A* 寻路、跑酷跳跃、**主动破坏挡路方块**、**主动放置垫脚方块**、游泳、梯子攀爬、**部分路径自动重规划**（`goal-reach-partial` 事件）。后者正是我们 F1 缺的能力。

**但我不建议现在换**，理由三条，都很硬：

1. **API 完全不兼容**。它是 `bot.ashfinder.goto(goal)`，goal 类型是自定义的 `goalExact/GoalNear/GoalXZ...`，和 pathfinder 的 `bot.pathfinder.goto(new goals.GoalNear(...))` 不是一套。我们 `skills.js` 里所有寻路调用都要重写，`mineflayer-collectblock`（内部依赖 pathfinder）也会失效，采集功能会一起坏。
2. **要求 mineflayer ≥ 4.35**，我们是 4.33.0；且它自带自定义物理引擎（`mineflayer-physics-reworked`），换物理模型的风险极高——之前 RCON 传送导致 `Invalid move player packet` 物理不同步的教训还在。
3. **它自己也承认会卡**：README 的 Known Issues 写着「Parkour 在复杂序列上偶尔会卡住」「出水要试好几次」。**换了不等于没有 F1**，只是换了一种卡法。

**结论**：F1 保持现在的"超时兜底"方案，不换引擎。如果要换，应当单开一个分支做对照实验，不要在主力配置上动。

## 28. F2（模型乱写破坏性代码）：靠"工具设计"而不是靠插件

这是本轮**性价比最高**的改进方向。核心思路：**当模型需要写循环时，说明我们没给它足够好用的原子函数。**

我们已经验证有效的三招，可以继续推广：

| 做法 | 已生效的证据 |
|---|---|
| 把关键函数塞进 `always_show_skills`，强制出现在 prompt 里 | 加入 `prepareBuildingSite` 后，她的代码变成一行调用，不再写循环 |
| JSDoc 里直接写"**不要**自己写 breakBlockAt 清理循环" | 上一轮的验证：给 `buildHouse` 加这句后，破坏性代码消失 |
| 函数返回结构化结果（`{placed, exists, blocked, failed}`）而不是 bool | 我能一眼看出 `placed:78, blocked:0, failed:2`，无需猜 |

**待办（低成本、可验证）**：
- 把"危险函数"和"安全函数"在文档里显式分层，让模型优先选安全版。`skills.placeBlock` 是 break-then-place 的破坏性版本，我新增的 `placeBlockWithoutBreaking` 还没进 `always_show_skills`，模型看不到它就会用回危险版。
- 给 `breakBlockAt` 的 JSDoc 顶部加一行醒目的"这是破坏性操作，盖房时禁止使用"。

## 29. F3（谎报成功）：这是架构问题，不是插件问题

她报告"成功"之后，我用计分板核实时发现结论可能是假的（其中一次还是我自己的探针方法有问题，已更正）。

**根因**：mindcraft 里"动作成功"是**模型自己写在 `log()` 里的文字**，没有任何自动校验。模型说 `Code finished.` 就算完成。

**可行的改进（都是改我们自己的代码，成本低）**：
1. **让技能函数内置自检**。我已经这么做了一次：`placeBlockWithoutBreaking` 放置后 60ms 用 `bot.blockAt` 复核，返回 `'placed'|'failed'`。这个模式应该推广到所有写操作。
2. **给模型一个"核实"命令**，比如 `!verifyBlock(x,y,z,type)`，让它完成任务后必须自查一遍再汇报。
3. 长期看，可以让 `skills.buildHouse` 返回 `verified: true/false` 字段，模型汇报时会把数字带出来（它现在确实会把 `placed:78` 念出来，说明这条路径通）。

## 30. F4（动作慢）：策略问题，已验证解法

手工逐格平地 27 秒/列 → 改 `/fill` 指令批量操作，50×50 从"19 小时"变成**几十秒**，且已验证结果正确（25 点抽样 0 空洞 0 残留）。

**这引出一个更重要的判断**：AI 在这个服务器上是 **OP level 4**。很多"慢"的问题，本质是我们在用肉体的方式做本该用指令做的事。凡是**批量、确定性、无需判断**的操作（平地、清场、取物），都应该走指令；凡是**需要观察和判断**的操作（找矿、盖造型、战斗），才交给 AI 的身体。

这条可以作为后续所有新技能的设计原则。

## 31. 其他可选增强（按性价比排序）

| 方案 | 类型 | 用时 | 风险 | 建议 |
|---|---|---|---|---|
| 补全 `always_show_skills`（把安全版函数暴露给模型） | 改我们代码 | 10 分钟 | 极低 | **立刻做** |
| 给 `breakBlockAt` 加破坏性警告 | 改 JSDoc | 2 分钟 | 零 | **立刻做** |
| `mineflayer-auto-eat` 升级 3.3.6 → **5.0.3** | npm | 20 分钟 | 中（跨 2 大版本，API 可能变） | 可做，需备份对照 |
| 把 mineflayer 4.33 → 4.39 | npm | 30 分钟 | 中高（4 个 patch 可能失效） | 暂缓，收益不明 |
| `@miner-org/mineflayer-baritone` 替换寻路 | 重构 | 半天以上 | **高** | 不建议，除非单开分支 |
| `mineflayer-web-inventory` 2.2.0 | npm | 15 分钟 | 低 | 纯调试用，想要可视化背包可装 |
| `mineflayer-death-event` 2.0.0 | npm | 10 分钟 | 低 | 让她死亡时能知道并汇报，消除 F3 的一种 |
| Skript / SkBee（服务器脚本） | 插件 | — | 低 | 与 AI 决策无关，改的是世界规则 |

## 32. 一句话结论

**"改善 AI 行为逻辑"这件事，80% 的收益在我们的代码里，不在插件市场。**

- 真正的底层缺陷（pathfinder 卡死）**上游已停止维护，没有人会帮我们修**，只能维持超时兜底；
- 唯一活跃的替代品（baritone）**API 不兼容且自带卡顿**，换它风险大于收益；
- 剩下的问题（乱写代码、谎报成功、动作慢）**全部可以通过"把好用的原子函数写出来 + 强制模型看见 + 内置自检"来解决**，而这正是我们这两天一直在做且已经验证有效的路。

下一步建议就做 §28 和 §29 里标"立刻做"的三项，都是十几分钟、零风险、可验证的。

## 34. 按「能不能真的用」分三类

### A 类：值得一试（低风险，直接对上我们的痛点）

**1. `mineflayer-schem` 1.5.2 — 按原理图盖房（最推荐）**

这个直接解决我们"盖房子盖得丑/盖不对"的问题：
- 支持 `.schematic` / `.schem` / `.litematic` / NBT，1.8–1.20+
- **自动去最近箱子取材料**——正好接上我们做的存箱子逻辑
- 自动处理朝向方块、楼梯、半砖
- 有进度事件 `builder_progress` / `builder_error` / `builder_finished`
- 支持多 bot 协作

用法：你先在单机里用 WorldEdit / Litematica 做一个房子存成 `.schem`，扔进去让它照着盖。
比让模型自由发挥画火柴盒可靠得多，而且**进度和错误都是事件推出来的，不是模型嘴上说的**（正好治 F3 谎报）。

风险：要求 mineflayer `^4.20.1`（我们 4.33 ✓）；它示例里也 `loadPlugin(pathfinder)`，和现有寻路不冲突。

**2. `mineflayer-auto-eat` 升级 3.3.6 → 5.0.3**

唯一一个我们真的"版本落后"的包（跨 2 个大版本，3.5 年前 vs 1.2 年前）。风险中等，但可对照回滚。

**3. `mineflayer-death-event` 2.0.0**

她死了能立刻知道并汇报，而不是继续演"我还活着"。10 分钟能接完，直接消除 F3 的一种。

### B 类：有价值但风险高，不建议现在动

**`mineflayer-cicerone` 2.1.0** —— 功能设计上最诱人：
- 动作级 **`revert()` 回滚**：挖了的方块能填回去，放了能拆掉
- 智能选工具（避开耐久 ≤ 5 的工具，挖矿优先精准采集）
- 路径树可序列化成 JSON

**但它是 2026-07-25 才首次发布的新包**，7 天内连发 7 个版本（1.0.0→1.0.1→…→2.0.0→2.1.0），之后停更。这种发布节奏说明**还没稳定**。而且它要求 `mineflayer ^4.37.1`（我们 4.33），是**独立的导航体系**，不是 pathfinder 的替换。

`revert()` 这个能力确实是我们没有的（我们的 `placeBlock` 拆了就拆了），但为它付出换导航体系的代价，现在不值。

**`@miner-org/mineflayer-baritone` 4.6.2** —— 上一轮已分析，维持"不建议"。

**`@nxg-org/mineflayer-pathfinder` 0.0.26** —— 名字像新一代，但版本号还是 0.0.x，2024-01 首发、2025-12 后停更。**0.0.x 版本号说明作者自己都不认为稳定**。

### C 类：与"改善行为逻辑"无关

`mineflayer-mouse`（反检测）、`mineflayer-viaproxy`（跨版本）、`mineflayer-web-inventory`（调试）、`mineflayer-headless-render` / `firstperson`（画面）、`mineflayer-mcefly` / `elytrafly`（鞘翅）——这些能加玩法，但不改决策逻辑。

## 35. 研究框架那条路：确认走不通

`MineDojo` / `Optimus-2` / `JARVIS-1` / `Voyager` 这些是**学术研究框架**：Python + PyTorch + 训练好的策略网络 + 模拟器环境。它们不是能 `npm install` 进 Node 项目的东西。想在本地跑起来需要 GPU 训练环境，而且它们的目标是基准测试分数，不是"在你家服务器上陪我玩"。

**我们这条路（LLM + 工具库 + 指令批量操作）在"可玩、可改、低成本"上是更合适的选择**，不用羡慕论文。

## 36. 一句话总结

生态里能装的东西很多，但**真正对我们有用且风险可控的只有一个：`mineflayer-schem` 按原理图盖房**。

它同时解决了两个问题：
- 房子盖得丑 → 照着原理图盖，效果取决于你做的图，不取决于模型发挥
- 谎报成功 → 进度和错误是**事件**推出来的，不是模型说的话

其余的：`auto-eat` 可升级对比；`cicerone` 的 revert 设计值得抄（以后自己实现）；`baritone` / `@nxg-org/pathfinder` 维持不动。
