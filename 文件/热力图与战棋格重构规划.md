## 0. 一句话结论

**核心错误不是"参数没调好"，是"用一个标量描述一片地形"这个建模方式错了。**
你说的「把坡 3D 化」是对的，我要更正一处：我们现有数据是 **2.5D（每列只有顶面）**，
真正的 3D 需要改扫描器；但即使只做到 2.5D 梯度，也能修掉今晚所有失败。

## 1. 我采纳的（并说明为什么对）

### 1.1 中位高度/极差代表不了通行性 —— 完全正确

实测（她周围 5×5 区块，`tools/diag_cost_vs_fine.mjs`）：

| 区块 | 地图判定 | 代价 | 实际可站 | 最大连通块 |
|---|---|---|---|---|
| (-8,-15) ← 她脚下 | 陡坡 | **25** | **89%** | 46% |
| (-6,-15) | 陡坡 | **25** | **100%** | 9% |
| (-8,-14) | 建筑区 | 18 | 71% | 36% |
| (-6,-14) | 陡坡 | **25** | 57% | 18% |

她站在 **89% 面积能站** 的地上，地图判「陡坡 25」（平地的 25 倍）。
根因就一行：`if (info.h > 18) return '陡坡'`，而 `h` 是 16×16 格内的**极差**——
一个区块里有山有平地，h 必然大，但它不代表走不过去。

### 1.2 「陡坡」这个类别应该取消 —— 正确

理由（我补充的物理依据）：

```
她跳 1.25 格 → 上 1 格不费力
上 2 格       → 要垫一块（她有 600+ 方块）
上 3 格以上   → 要挖/垫多次，代价急剧上升
```

**所以"能不能上"是连续的，不是二值的。** 用累积代价表达，高山的代价自然涨到
让绕行更划算——**不需要一个专门的"陡坡"类别去禁掉它**。你的判断和数学一致。

### 1.3 删掉热力图 —— 方向对，但**不能直接删**

你问「功能是不是已被战棋格全面代替」。诚实回答：**接近了，但还差三件东西**。

`heatmap.js` 里有五类功能，逐条对照：

| 功能 | 战棋格能替代吗 | 处理 |
|---|---|---|
| 4 格精度代价网格 `buildHeatmap` | ✅ 能（我们已有 1 格精度） | 删除，用 1 格精度取代 |
| 分层规划 `planHierarchical` | ✅ 能（滚动窗口已取代） | 删除 |
| `planRoute`/`goToPositionPlanned`/`renderAscii` | ✅ 能 | 删除，`!plan` 改用 `planNextHop` 预览 |
| `facingOf`（朝向中文名） | ❌ 无关地形 | **搬走**（搬到 `world_model.js` 或独立小工具） |
| `isPlayerBuiltBlock`/`NOT_GROUND` 等 | — | **本来就是 `world_model.js` 重导出**，直接改 import 来源即可 |
| `collectHazards`/`mergeHazardBlobs`（岩浆/火焰枚举+膨胀） | ❌ 战棋格没有 | **搬走**（搬进 `world_model.js`，它已经是方块知识的 owner） |
| **洼地检测（接雨水算法）** | ❌ 战棋格没有 | **必须补进新算法**——她掉坑里就是这个场景 |

**结论**：你的判断成立，但顺序必须是「先搬走 3 项、再删」，否则会静默丢功能。

## 2. 我反驳/修正的

### 2.1 「把坡 3D 化」→ 我们现在只能做到 2.5D，原因很具体

`scanChunkFine` 每列**只记最上面那层**地表：

```js
for (let y = from; y >= SURFACE_TO; y--) {
    const b = column.getBlock(...);
    if (AIR.has(name)) continue;
    ...record and break;      ← 记到第一个实心就停
}
```

所以：
- ✅ 能算：相邻两列各自高度之间的坡度、粗糙度、梯度分布
- ❌ 算不出：洞穴、隧道、悬空平台、桥下（同一个 (x,z) 有多层可站）

**这就是为什么今晚她站在 y=50 的洞里、地图却说她那块地在 y=79。**
区块级地图永远不知道她在洞里——这一点必须靠**实时方块**（洪泛/pathfinder）才能知道。

真正的 3D 要改成「每列记所有空气-实心边界」：
- 典型地形每列 2~5 个边界 → 每区块约 1000 条记录 → **约 3 KB/区块**（现在是 384 B）
- 4095 区块 = 12 MB，可接受；10 万区块 = 300 MB，需要分精度淘汰
- 扫描器要重写，导入时间约 ×4

**我的建议**：v1 只做 2.5D 梯度（成本低、能修掉今晚全部问题）；
把「多层可站」列为 v2，等 v1 验证过再决定。**这一条请你决定。**

### 2.2 「陡坡没必要」的边界：仍然需要一条硬禁行

不是"陡坡"，是**岩浆**。它和坡度无关，是"踩了会死"。
所以分类保留 `lava = 禁行`，其余全部连续代价。

### 2.3 「所有高度逐个连一起之后的坡」——我理解成梯度剖面，请你确认

我的理解：不是只看相邻两格的高差，而是看**沿一条线累积起来**的爬升。

```
10 格水平、每格上 1 格  → 总爬升 10，每格只需跳一下     → 可走（累）
10 格水平、一格上 10 格  → 总爬升也是 10，但中间是墙     → 不可走
```

两种情况的「总爬升」一样，但可走性天差地别。所以指标不能用总量，要用**分布**：

- `walkPct`：相邻格对里 `|Δy| ≤ 1` 的比例（这才是"走得上"的）
- `stepP50 / stepP90 / stepMax`：高差分位数
- `roughness`：Δy 的标准差（粗糙度）
- `gradPer100`：每 100 格水平距离的累计爬升（"逐个连一起"的坡）

**如果我的理解偏了，请你纠正——这决定第 3 节的核心公式。**

## 3. 新算法设计

### 3.1 局部步进代价（连续，无类别）

对相邻两格 a→b（各有自己的地表高度 `ya`、`yb`）：

```
Δy = yb - ya

cost(Δy):
  Δy ≤ 0        : 1 + 0.3·|Δy|                   下坡便宜
  0 < Δy ≤ 1    : 1 + 1.5·Δy                     跳一下
  1 < Δy ≤ 2    : 2.5 + 6·(Δy-1)                 垫一块
  Δy > 2        : 8.5 + 12·(Δy-2)                挖/垫多次，急剧变贵
```

对照：
| Δy | 代价 | 含义 |
|---|---|---|
| -3（掉 3 格） | 1.9 | 可以跳下去 |
| 0（平走） | 1 | 基准 |
| +1（上一格） | 2.5 | 跳 |
| +2 | 8.5 | 垫一块 |
| +5 | 44.5 | 挖+垫，明显不划算 |
| +10 | 104.5 | 极贵 → 绕行自动胜出 |

**没有"陡坡"分支，高山靠累积代价自然变贵**——这就是你说的"只有特别高的高山才要绕行"。

### 3.2 区块级汇总（给长距离规划用）

从 1 格精度数据算，存进区块记录：

| 字段 | 含义 | 用来干什么 |
|---|---|---|
| `walkPct` | `|Δy| ≤ 1` 的相邻对占比 | 主判据 |
| `stepP90` | 高差 90 分位 | 判断有没有"墙" |
| `roughness` | Δy 标准差 | 粗糙度（你说的） |
| `gradPer100` | 每 100 格累计爬升 | "逐个连一起的坡" |
| **`throughBlobPct`** | **最大 4 连通「全可走」块占比** | **最关键，见下** |

`throughBlobPct` 是**你早先批准但一直没做的那条**（"按边记连通性"）：
一个区块里，找「相邻格全都能走（Δy≤1）」的最大连通块。
块越大、越贯通两侧 → 这区块真的能穿过去。

**字节数**：只加 5 个标量 ≈ 20~30 B/区块，4095 区块 ≈ 100 KB。**不需要新 blob。**

### 3.3 三档分工（把边界写死，避免再混）

| 场景 | 用什么 | 精度 | 数据来源 |
|---|---|---|---|
| 全局路线（>64 格） | 区块级 A*（新代价） | 16 格 | SQLite 持久地图 |
| 近场执行（≤64 格） | `planFine`（1 格） | 1 格 | 同上，1 格精度 |
| **卡住判定** | **实时洪泛**（live blocks） | 1 格 | `bot.blockAt` |

**第三条是关键**：地图永远不知道她在洞里，所以"我是不是被困"只能问实时世界。
今晚第 7/8/9 次修就是在这条上反复踩——现在写进文档，避免再犯。

### 3.4 洼地检测（补 heatmap 的能力）

从 1 格精度算：若某格的地表比**四邻都低 ≥2 格**，且连通块很小 → 标记 `basin`，
代价 ×3（她掉坑里就是因为这种地形没被标记）。

```sql

ALTER TABLE chunk ADD COLUMN step_p90      INTEGER;
ALTER TABLE chunk ADD COLUMN roughness     REAL;

ALTER TABLE chunk ADD COLUMN through_blob  REAL;

```

`classifyChunk` / `tileCost` 改为：

```
1) 有 1 格精度指标 → 用 walkPct / throughBlob / stepP90 算代价（连续）
2) 没有            → 退回 h 判据，但阈值 18 → 30（实测 h=26~32 的区块 57~100% 能站）
3) lava 覆盖 → 禁行（唯一硬禁）
```

## 5. 覆盖率问题（必须先解决，否则新算法只对 85 个区块生效）

现状：**85 / 4095 区块有 1 格精度**，其余退回旧判据 —— 新算法会"一半生效一半不生效"。

三个方案：

| 方案 | 做法 | 代价 | 结果 |
|---|---|---|---|
| A | `.mca` 导入时按 256 列重算 | 一次性 **约 3~4 分钟**（现在 47s × 4） | 4095 区块全部有精细指标 |
| B | 规划到哪儿补扫哪儿 | 每次约 40ms | 永久稀疏，远距离仍退回旧判据 |
| **C（建议）** | A 做一次 + B 维持新鲜度 | A 一次性 + B 常态 | 全量覆盖 + 走到就更新 |

我建议 **C**。补扫机制已经有了（`scanFineArea`，每段 9 区块 40ms）。

## 9. 风险 / 明确不做

| 风险 | 说明 | 应对 |
|---|---|---|
| **2.5D 天花板** | 洞穴/悬空/隧道完全看不见 | 局部决策一律用实时洪泛；v2 再谈多层 |
| 区块 A* 仍可能"看起来能走实际不能" | 16 格粒度 vs 1 格现实 | 滚动窗口每 64 格重算 + 失败边惩罚（已实现） |
| 删 heatmap 影响 `skills.js` 十余处 | 可能连带破坏 `collect` / `build` | 分 4 步迁移，每步跑 preflight + 全套测试 |
| `.mca` 重导入 3~4 分钟 | 期间不能开 bot | 停服做，或选单个区域先验证 |

**明确不做**：
- 不做真 3D 多层扫描（v2 再议）
- 不改 pathfinder 内部（那是它的活）
- 不做跨维度（下界/末地）
