## 申报 01 · 2026-10-24 · L2 编排层（plan / runSteps）

- **要解决的问题**
  复合技能里"决定下一步做什么"和"执行这一步"糊在一起。`task_collect.js` 707 行、3 条挖掘路径、4 处 `collectDrops`，就是这个病的症状。后果：报错只能定位到"整个采集失败"，无法回答"第几步、哪个原子、什么码"。

- **已检索的候选**

  | # | 候选 | 结论 |
  |---|---|---|
  | 1 | 项目内已有执行器 | **无**。`grep -rn "runSteps\|stepIndex\|taskQueue\|sequence" src/agent/` = 0 命中 |
  | 2 | `behavior3js`（行为树） | 不选。为长周期 AI 设计，状态与 tick 概念重；我们的需求是"一次性步骤序列 + 每步读世界校验"，抽象不匹配，还得引入新 DSL |
  | 3 | `xstate`（状态机） | 不选。适合有生命周期、需要持久化的状态；一次采集是短生命周期线性序列，状态机是降维打击 |
  | 4 | `bull` / 进程外队列 | 不选。单 bot、单进程、几十步，用不上外部队列与重试基础设施 |
  | 5 | 直接抄 `mineflayer-collectblock` 的 `Targets` | 不选。它是"目标集合 + 逐个消费"，没有"每步前置断言/后置校验/降级动作"，正是我们要补的东西 |

- **为什么都不够**
  需要的抽象只有三件事：**纯函数产出步骤序列**、**逐条执行并在每步读世界校验**、**失败返回步骤号**。上面每个候选都比这个重，且没有一个和我们的 `atom_contract` 信封对齐。引入它们要付"学新抽象 + 写适配层"两份成本。

- **拟自研范围**
  - 一个文件（`src/agent/library/step_runner.js`），约 60~90 行
  - 无新依赖
  - 不改任何现有出口；`task_*.js` 通过它跑，行为不变
  - 契约见规划 §5.3（`steps[]` / `{ok, code, data:{doneSteps, failedStep}}`）

- **回收条件**
  若将来出现多 bot 并发、或需要跨进程持久化任务队列，则改引入现成方案，本模块废弃。

- **结论：已批准**（2026-10-24，用户在 P0 授权时选择「批准自研 step_runner」）

## 申报 08 · 2026-10-24 · atom_locate.js（定位：她/玩家/实体/方块在哪）

- **要解决的问题**
  全库有 **196 处**直接读 `bot.entity.position` / `bot.players[name].entity.position`，各写各的判空。
  典型后果：「玩家在 48 格外」这件事在 5 个地方被处理成 5 种样子——有的报"看不见"、有的崩、
  有的静默返回 null。而"看不见"和"不在线"是两回事，现在混在一起。

- **已检索的候选**

  | # | 候选 | 结论 |
  |---|---|---|
  | 1 | `atom_perceive.playerPos()`（已有） | 不够。只查 `bot.players[name].entity`，返回 null 就结束，无距离、无最后已知位置、无维度判断 |
  | 2 | **`task_follow.js` 的 `PlayerTracker` + `resolveTarget`（已有）** | **采用并上提**。它已把「可见 / 只剩记忆 / 离线 / 完全没线索」四态分开，只是埋在跟随逻辑里，别的模块用不到 |
  | 3 | `mineflayer` 的 `bot.players` / `bot.entities` | **采用**，作为数据源 |
  | 4 | 走地图（`chunk_map`）推算玩家位置 | 不选。地图是离线快照，不适合"人现在在哪" |

- **为什么都不够 / 怎么复用**
  **不重写逻辑**：`PlayerTracker` / 四态判定直接上提到原子层，`task_follow` 改为调用原子。
  新增只有四件它现在缺的：
  1. 统一返回信封（`ok/fail` + 错误码），而不是内部 `{kind:...}` 裸对象
  2. 距离字段（`distFeetToEntity` / `distEyeToBlock`）
  3. 支持实体、方块（最近的一个），不只玩家
  4. **RCON 数据源**（见下，这是关键补充）

- **改名与范围调整**（2026-10-24，用户拍板）
  原定名 `atom_locate`（定位），改为 **`atom_query`（查询信息）**。
  理由：它返回的不只是坐标，还有在不在线、可不可见、距离、信息年龄、维度。
  叫"定位"会让人以为只给一个点，进而又在调用点自己补状态判断——那正是要消灭的重复。

- **RCON 接入**（2026-10-24 用户质疑后核实）
  用户质疑："怎么会超出跟踪范围？F3 不是什么都能读到吗"。核实结果：
  - **F3 显示的是自己的坐标**，不显示他人位置
  - **客户端协议确实拿不到**：玩家超出跟踪范围（约 48 格）后服务端发 `entity_destroy`，
    `bot.players[name].entity` 变 null（`mineflayer/lib/plugins/entities.js:288-297`）
  - **但服务端始终知道**：实测把玩家 `tp` 到 500,500（bot 在 -8,-4），
    `data get entity <name> Pos` 仍返回 `[500.5d, -59.0d, 500.5d]`

  所以 `atom_query` 采用**两级数据源**：RCON 优先（任意距离精确），客户端兜底（48 格内）。
  返回里带 `source: 'rcon' | 'client' | 'memory' | 'none'`，让上层知道数据可信度。

- **拟自研范围**
  - `atom_query.js`：约 280 行
  - `rcon_client.js`：约 140 行（见申报 09）
  - 无新依赖（用 node 内置 `net`）

- **回收条件**：若 mineflayer 未来提供"最后已知位置"或服务端位置查询的官方 API，
  本模块退化/删除。RCON 客户端若被上游库覆盖，也一并回收。

- **结论：已批准**（2026-10-24，用户"接，原子技能改为：查询信息"）


## 申报 25 · 2026-10-27 · executor.js（唯一导航任务层）

- **要解决的问题**
  导航层有**四套规划器并存**（tile_map 战棋格 / path_long / chunk_map 2.5D / heatmap 已删），
  加**四条互相兜底的执行链**（战棋格方向 / 3D 规划 / 兜底走 8 格 / 3D 失败就挖柱）。

  今晚为同一件事改了 29 次，失败点从 y=45 挪到 y=68、y=116 —— 这是结构病，不是 bug。

- **第一性原理**
  她只有两种走路原语：
    ① 水平移动（含跳 1 格、掉落）
    ② 改变地形（挖掉挡路的 / 垫出落脚点）
  其它（路线、代价、分层、地图）都只是为这两件事服务的决策。

- **已检索的候选**

  | # | 候选 | 结论 |
  |---|---|---|
  | 1 | 继续在旧 hopTo 上打补丁 | **不选**。29 次修改都在挪失败点 |
  | 2 | 只保留 pathfinder，不要规划 | **不选**。它只看视距内（约 128 格），且 64 格外一律 NO_PATH |
  | 3 | **一条链路：扫球 → 3D 规划 → 按 action 分发 → 零兜底** | **选这个** |

- **拟自研范围**
  - 一个文件 `src/agent/library/executor.js`，约 330 行
  - `walkTo(bot, dest, opts)` 唯一入口
  - `execStep` 按 3D 路径的 `action` 分发：

- **保留的已验证资产**
